### perf

Gate 5 is measured, not passed (2026-10-25 log, TESTING.md "Benchmark", README "Performance"): `tools/bench.py` runs vanilla (the unmodified jar, the launcher's JVM, JFR method tracing) and the port on the same generated world with the same options, and `rustcraft --benchLevel CAPTURE` is the offline benchmark of a bench's capture, whose mesh digest an optimization must leave as it was. On llvmpipe the held view's frame rate is the same in both (the driver's); the port starts 4 times faster, uses 2.5 times less memory, ticks 5 times faster and compiles a section 3 times faster, but loads worse. Next, in order:
- **Compile less, and off the frame.** While the new view's chunks come, the port compiled 2,844 sections where vanilla compiled 501: every dirty visible section compiles in the frame it's marked, again each time a neighbour's light or a light update marks it, where vanilla's queue cancels a task that hasn't started (`RenderSection.rebuildSectionAsync`'s `cancelTasks`) and so compiles the latest state once. Two steps: first, leave a section that was marked this frame for the next (unless the player's change marked it, which vanilla compiles at once), and count it in `has_rendered_all_sections`; then compile on worker threads like vanilla's executor. What stops the second is `RenderSectionRegion`'s level, which isn't `Sync`: the light engine's layers are `Rc<RefCell<DataLayer>>`s and the tint caches are cells. A region would copy its 27 sections' light (with the sky light's lookup above a missing layer, `SkyLightSectionStorage.getLightValue`) and tint from a `Sync` view of the chunks' biomes.
- **Chunks and light on the game thread are 2 times vanilla's** (175 µs a chunk against 80, light 428 µs a chunk against 202): profile `handle_level_chunk_with_light_in` and `ClientLevel::update` in `--benchLevel`.
- The compile itself (`perf` of `--benchLevel`): `BiomeManager.getBiome`'s zoom for each of a tint blend's 25 columns (8%), the neighbour sections' reads through `SimpleBitStorage`, the light engine's `section_states` map (SipHash).
- `chunk_loading_state` rebuilds a set of the loaded chunks and one of the empty sections from the view area's columns every frame (SipHash); Java keeps them as chunks come and go (`updateLoadedChunks`, `updateEmptySections`). The occlusion graph's `sections_waiting_for_chunk_loads` is a std `HashMap` whose iteration order decides which sections propagate first: Java's is a fastutil map with its own order (which shows only in the graph's walk, not in what it finds).
- `inactivityFpsLimit` (`FramerateLimitTracker`), with the window's focus and the player's last input.
- The `terrain` session's split counted all of perf's `[JIT]` samples as the client's, which is mostly llvmpipe's JIT-compiled vertex code (the port, which runs no JIT, has 43% of its render thread there, vanilla 44%); `bench.py` now counts JIT code the JVM's perf map doesn't name as the driver's, from the `flat` session on.

### 2026-10-23 (net): The connection on a thread of its own, like Netty's: keep-alives answered while the game thread stalls

- Ported the connection's threading (PORTING.md, "The connection's threads"): `Connection` is an `Arc` shared by the game thread and its event loop thread (`EventLoopGroupHolder`'s `Netty Client IO #N`, with a second thread reading the socket for it), which splits, decompresses, decodes and hands on what arrives, runs what other threads hand it in order (writes, protocol changes, compression, closing), and times out after 30 seconds of silence. `send` writes at once on the loop and hands the write to it from elsewhere; `setupInboundProtocol`, `setupOutboundProtocol`, `setupCompression` and `disconnect` wait for the loop like Java's `syncUninterruptibly`. - Listeners are two halves: the game thread's (Java's handlers whole) and the half Netty's thread hands packets to (`NettyHalf`), whose handlers are Java's up to `ensureRunningOnSameThread`, which queues the packet for the game thread (`PacketProcessor`, now a locked queue that knows its thread, with `GameThreadListener` naming a game-thread listener for other threads).
