# Porting rules

How Java becomes Rust in this repo. The port should read side by side with `vanilla/<version>/src/` and match vanilla bit for bit, which TESTING.md checks.

## Layout and names

- One Java file becomes one Rust file at the same path, in snake_case: `net/minecraft/util/Mth.java` → `src/net/minecraft/util/mth.rs`. Each file starts with `//! net/minecraft/util/Mth.java`.
- Class names stay as they are, acronyms included (`Mth`, `ARGB`, `UUID`). Methods and fields become snake_case (`wrapDegrees` → `wrap_degrees`).
- Static methods and constants become associated functions and consts (`Mth::sin`, `Mth::PI`). Static methods of an interface become free functions in its module (`random_source::create`), since a trait has to stay object safe.
- Nested classes live in their outer class's module: `RandomSupport.Seed128bit` → `random_support::Seed128bit`.
- Rust has no overloading, so overloads get a suffix that tells them apart:
  - The Rust type, when they differ by type: `clamp_i32`, `clamp_f32`.
  - What they add, when they differ by arity: `next_int_bounded`, `length3_f64`.
  - The golden test is the mapping table: each `golden.check` line pairs a JVM descriptor with its Rust function.
- Constructors are `new`. Overloaded constructors follow the same rule (`from_seed128bit`).
- A Rust module named like its parent (`net/minecraft/util/Util.java` → `util::util`) keeps the name, with `#[allow(clippy::module_inception)]` on its `mod`.
- A Java name that's a Rust keyword stays, as a raw identifier: `MutableBlockPos.move` → `r#move`. Enum constants keep Java's names, underscores included (`Rotation::CLOCKWISE_90`).
- JDK behaviour the game depends on lives under `src/java/`, mirroring the JDK's packages (`java::lang::math::Math`, `java::util::uuid::UUID`). Its internal classes do too, under `src/jdk/` (`jdk/internal/math/DoubleToDecimal.java` is `jdk::internal::math::double_to_decimal`, which `Double::to_string` calls), keeping only the paths the game reaches (`toString`'s LATIN1 one).
- HotSpot code the JDK runs instead of Java follows the same rule under the class that calls it: `src/hotspot/cpu/x86/stubGenerator_x86_64_sin.cpp` → `src/java/lang/math/hotspot_x86/stub_generator_x86_64_sin.rs`. Assembly ports one call per instruction (`__ mulsd(xmm1, xmm0);` → `xmm1.mulsd(xmm0);`) on the register model in `hotspot_x86/assembler.rs`, and keeps OpenJDK's GPLv2 notices. A stub whose jumps nest becomes `if`s (sin); one that jumps back and forth between its blocks becomes a loop with one `match` arm per label, in the C++'s order, and a `jmp!` macro for its jumps (pow). `python3 tools/hotspot_port_check.py` checks that each port has its stub's instructions in the same order; CI runs it.
- Anything not ported yet is named in the file's header comment and marked pending in its golden test.

## Libraries

Libraries whose classes the game's math and packets run through are ported like the game, from their published sources, which `tools/setup_vanilla.py` puts next to the decompiled game (`vanilla/<version>/src/org/joml/Matrix4f.java` → `src/org/joml/matrix4f.rs`). So far that's JOML, the vector and matrix library, Netty's buffers (`netty-buffer`), Guava's `ImmutableMultimap`, `IntMath.gcd` and `DoubleMath.fuzzyEquals`, Gson's tree, reader and writer ("Gson" below), and the parts of fastutil's `DoubleList` the voxel shapes read (from its bytecode: fastutil publishes no sources with the game). Mojang's authlib publishes no sources, so `setup_vanilla.py` decompiles it with Vineflower like the game (`vanilla/<version>/src/com/mojang/authlib/GameProfile.java`), and Brigadier, the command parser, the same way (`vanilla/<version>/src/com/mojang/brigadier/StringReader.java`). Their classes have hundreds of methods, so only the ones the client calls are ported, and the golden suite lists them. Translated files keep the library's licence notice when it asks for one (Netty's and Guava's Apache notices, like HotSpot's GPL ones).

Which ones the client calls comes from its bytecode: `javap -c -p` over every class in `client.jar`, keeping the `org/joml/` invocations. A call through a subclass or an interface (`Matrix3x2fStack.translate`, `Matrix3x2fc.transformPosition`) runs the class's own method unless the subclass overrides it.

- JOML's read-only interfaces (`Matrix4fc`, `Vector3fc`, …) are only implemented by its own classes, so they become shared references (`&Matrix4f`), and their constants live in their module (`matrix4fc::PROPERTY_IDENTITY`).
- Constructors: the no-argument one is `new()`, the one taking the fields is `from_xyz`/`from_xyzw`/`from_values`, and copies are `from_<type>` (`Matrix3f::from_matrix4f`).
- Overloads taking components instead of a vector get `_xyz` (`add_xyz`), a scalar `_scalar`, an axis and angle `_axis`/`_axis_xyz` (`rotate_axis(angle, &axis)`), another type its name (`mul_matrix3f`).
- A method that writes to a `dest` argument gets `_into` and returns `dest` (`invert_into(&mut dest)`). Its fluent overload passes `this` as `dest` and returns `&mut Self`. Rust can't alias the two, so the fluent one writes into `self` from a copy of it, which is only the same as JOML when JOML reads all of `this` before writing `dest`. Check that it does. Where JOML gives the fluent overload a body of its own (`Matrix4f.translate`), or a method reads back what it just wrote (`rotationAround`), port it on `&mut self` as it is. The golden suite checks both overloads.
- `Matrix4f` keeps JOML's `properties`, which methods take shortcuts on. The shortcuts can give different bits than the full computation (`identity()` leaves an identity with -0.0 in it alone), so they're part of the port, and of the encoded state.
- JOML's `Math.fma` is `a * b + c`, rounded twice: the fused `java.lang.Math.fma` needs `-Djoml.useMathFma`, which the game doesn't set. Never use `mul_add`.

Netty:

- `ByteBuf` is one struct: AbstractByteBuf's indexes and bounds checks over UnpooledHeapByteBuf's array, read and written big-endian (`src/io/netty/buffer/byte_buf.rs`). The game only sees `ByteBuf`'s API, and Netty's other buffers (pooled, direct, composite, slices) only differ in where the bytes live and how they grow. Its capacity is the array's length, and grows like `Unpooled.buffer()`'s (`AbstractByteBufAllocator.calculateNewCapacity`), which the golden suite checks. `retain` and `release` are Rust's ownership, and `alloc()` is the one allocator.
- A getter and its setter overload (`readerIndex()` and `readerIndex(int)`, `capacity()` and `capacity(int)`) become `reader_index` and `set_reader_index`. Overloads by argument type get the type: `readBytes(int)` is `read_bytes`, `readBytes(byte[])` `read_bytes_array`, `readBytes(byte[], int, int)` `read_bytes_array_range`, and `writeBytes(ByteBuf)` `write_bytes_buf`.
- A call that throws halfway leaves the buffer as Java's does: `writeBytes(byte[], int, int)` grows the array before it checks the source's range, and `VarInt.read` has consumed the bytes it read when it throws. The golden cases record the buffer after a throw too.
- `slice(int, int)` is a copy of the range, all of it readable, which can't grow. Java's slice shares the parent's array, which only differs when either is written to after, and the game only reads a slice (`ByteBufCodecs.lengthPrefixed`). Like Java's, it's checked against the array, not the writer index.
- `ByteBufInputStream` and `ByteBufOutputStream`, which the game reads and writes NBT through, borrow the buffer for as long as they live, and implement `java::io`'s `DataInput` and `DataOutput`. Making an input stream marks the buffer's reader index, as Java's constructor does.

The JDK:

- `java.util.HashMap` is ported with its table (`src/java/util/hash_map.rs`), since a map's iteration order is behaviour wherever the game writes what it iterates: a `CompoundTag` writes its tags in its map's order. A table is a `Vec` of bins, each a `Vec` of its entries in their linked order, grown and split like `resize`, and `new HashMap<>(map)` sizes its table for the size, like Java's. `new HashMap<>(initialCapacity)` is `from_initial_capacity`, which sets the threshold the first `put` makes the table from (the smallest power of two at least the capacity) and panics on a negative one. Its tree bins (a bin of 9 in a table of 64 or more) aren't ported yet and panic.
- `java.util.HashSet` is a `HashMap` of its elements to Java's `PRESENT`, so the port is the ported `HashMap` with `()` values (`src/java/util/hash_set.rs`), which iterates like its keys. `AbstractSet`'s `equals` (the same size, and every element of the other one in it, in any order) and `hashCode` (the sum of its elements'), and `AbstractCollection`'s `toString`, are its own. Elements are `java::lang::object::HashCode`, like the map's keys (`Identifier` is).
- `java.io.DataInput` and `DataOutput` are traits of the methods NBT calls, and `DataInputStream.readUTF` and `DataOutputStream.writeUTF` (modified UTF-8) are functions every implementation calls, like Java's.

Brigadier:

- `StringReader` reads Java's string by UTF-16 units: its cursor, lengths and `peek` are units, and a read string is made from units, so a cursor splitting a pair reads U+FFFD where Java has a lone surrogate (the goldens leave those cases out). A copy shares the string.
- `CommandSyntaxException` holds its message as a `Message` (a trait: Brigadier's `LiteralMessage`, or the game's `Component`, whose text comes through the language) with the input and cursor; `get_message` adds the context (`at position 4: @e[x<--[HERE]`) like Java's. Its exception type isn't kept: no ported caller reads it. The exception types are generic in their arguments (`DynamicCommandExceptionType<String>`), Java's `Object`s.
- The game sets `CommandSyntaxException.BUILT_IN_EXCEPTIONS` to its own `BrigadierExceptions` at startup, so the reader's errors are the game's translations; here the reader calls `BrigadierExceptions` directly.

Guava:

- `ImmutableMultimap` is what `builder()`, `of()` and `copyOf` make, an `ImmutableListMultimap`: each key in the order it was first put, with its values in the order they were put. It's a `Vec` of keys with their values, searched from the start, which iterates in that order. Its `equals` is its `asMap()`'s, so the keys' order doesn't matter but each key's values' does, and its `hashCode` is the sum of its entries'. `copyOf` of an immutable multimap is the multimap itself.
- A class forwarding to a Guava collection (authlib's `PropertyMap`, a `ForwardingMultimap`) holds it and forwards the methods the game calls.

## Object model

- Interfaces become traits. An interface-typed value becomes `Box<dyn Trait>` when owned and `&mut dyn Trait` (or `&dyn Trait`, like a `Position`) when borrowed.
- An enum becomes a Rust enum. When its constants take constructor arguments (`Direction`'s data values, name, axis and normal), those live in a static table indexed by the constant, one line per constant like Java's. Its nested enums live in its module (`direction::Axis`). `values()` is a `VALUES` const and `values()`, and `valueOf` is `value_of`, which panics where Java throws.
- Generic code that calls `hashCode` on any value, like Guava's collections, takes values that are `java::lang::object::HashCode` (`String`, `Property`). Other types have a `hash_code` method of their own.
- `toString` becomes `Display`, so `to_string()` works. `equals` becomes `PartialEq`: derived when Rust compares the fields the way Java does (ints, or floats with `==` in `Vec2`), written out when it doesn't (`Vec3` compares with `Double.compare`, so -0.0 differs from 0.0 and NaN equals NaN). `hashCode` is `hash_code()`, with `java::lang::float::Float` and `java::lang::double::Double` for floats' bits. A Java `equals` that returns true for the same object first only differs for a NaN component, where Rust has no identity to check.
- An argument Java lets be null is an `Option` (`Direction.getNearest`'s fallback, `Direction.Axis.test`).
- An interface implemented only by its own constants becomes an enum (`Axis::XP`; `Axis.of` would make another, but nothing calls it). Its overloads that differ by type get the type (`rotate_matrix4f`).
- A class that extends another to add state holds its parent as a field and derefs to it: `Matrix4fStack` is the `Matrix4f` it derefs to, plus the saved copies. So does one that adds no state: `BlockPos` holds the `Vec3i` it derefs to, and `MutableBlockPos` the `BlockPos`. The methods a subclass overrides are its own and return its type (`BlockPos.offset` returns a `BlockPos`). A parent's method that calls an override in Java (`BlockPos.above(int)` reaching `MutableBlockPos.relative`) calls the parent's own in Rust, which is fine while both give the same values: `MutableBlockPos`'s overrides only make sure a copy comes back instead of the cursor, and every Rust result is a copy anyway.
- A class that wraps another and forwards its API to it (`FriendlyByteBuf` around a `ByteBuf`) owns it and derefs to it. Its static methods that take the wrapped type, next to instance methods of the same name, get `_from` for readers and `_to` for writers: `readUUID()` is `read_uuid` and `readUUID(ByteBuf)` `read_uuid_from`, `writeUUID(ByteBuf, UUID)` `write_uuid_to`. An overload that adds a maximum gets `_max` (`readUtf(int)` is `read_utf_max`).
- An abstract class is the same: `BlockHitResult` holds its `HitResult` and derefs to it, and the abstract `getType` is `BlockHitResult`'s own. How the game holds either kind of hit (`Minecraft.hitResult`) gets settled with `EntityHitResult`.
- Protected members become `pub(super)`, visible to their package: `Vec3i`'s setters, which only `MutableBlockPos` calls. A `toString` that prints the receiver's class name (`MoreObjects.toStringHelper(this)`) becomes a helper taking the name, which each subclass's `Display` passes (`BlockPos{x=1, y=2, z=3}`).
- An `Iterable` or `List` argument becomes a slice (`AABB.clip`'s boxes, `&[AABB]`), and an `Optional` result an `Option`.
- Iterables and streams become iterators, built with `iter::from_fn` on the anonymous `AbstractIterator`'s fields. One that only copies its arguments says so with `+ use<>`: edition 2024's `impl Trait` otherwise borrows every argument for as long as the iterator lives, so a caller couldn't pass temporaries (`BlockPos.between_closed`, which `between_closed_aabb` calls with the corners it works out). Java's that hand out one cursor over and over (`BlockPos.betweenClosed`'s `MutableBlockPos`) yield copies of it, which is what a caller that uses each element at once, or copies it with `immutable()`, sees. A caller that keeps the cursor itself needs care when it's ported.
- Immutable value classes (`Vec3i`, `Vec3`) are `Copy` structs whose methods take `&self` and return new values. Where Java returns `this` (`offset(0, 0, 0)`), the port returns a copy, which is the same value. A getter handing out a shared read-only object (`Direction.getUnitVec3f`'s `Vector3fc`) returns a `&'static` reference.
- A getter that hands out a mutable object (`PoseStack.last()`) becomes `last()` returning `&` and `last_mut()` returning `&mut`. So does one whose read-only view a caller casts back and writes to: `MatrixUtil.checkProperty` adds properties to the `Matrix4fc` that `Transformation.getMatrix()` hands out, so `PoseStack.mulPose(Transformation)` takes `&mut Transformation` and goes through `get_matrix_mut()`.
- State a getter works out on first use (`Transformation`'s decomposition) lives in a `OnceLock`, so the getter takes `&self`. Cloning such an object stands for copying a Java reference to it when nothing else about it changes: the lazy state comes out the same whenever it's worked out.
- A constant the game compares by reference (`rotation != Transformation.IDENTITY`) carries a private flag that only the constant sets and its clones keep.
- A class whose instances Java interns, so the game compares them by reference, is a value that compares its fields: `ResourceKey.create` hands out one key for each registry name and identifier, so comparing references is comparing the pairs. Its `hashCode`, an identity hash, isn't ported, and neither is that of a record holding one. A type argument that only says what the key is for (`ResourceKey<T>`) is dropped, like `PacketType`'s.
- Global state that isn't ported yet becomes a parameter, like a back-reference: `Projection.getMatrix` asks `RenderSystem`'s device whether depth runs from 0 to 1, so `Projection::get_matrix` takes `z_zero_to_one`.
- An interface that fills in another interface's methods with defaults (`BitRandomSource`) becomes functions that implementors forward to. A Rust trait can't provide another trait's methods.
- A back-reference, i.e. an object pointing at its owner, becomes a parameter. `MarsagliaPolarGaussian` holds its `RandomSource` in Java; in Rust, the owner passes itself in.
- Concurrency guards that `&mut self` already rules out, such as an AtomicLong checked by a ThreadingDetector, become plain fields.
- A sealed interface whose classes the game tells apart with `instanceof` becomes an enum with a variant holding each class's struct (`Tag::Compound(CompoundTag)`), and the methods every class implements dispatch through it. Interfaces between it and the classes (`NumericTag`, `CollectionTag`) are traits the classes implement, and their `instanceof` is a method of the enum (`as_numeric_tag()`).
- Overloads adding an accounter get `_accounted` (`NbtIo.read(DataInput, NbtAccounter)` is `read_accounted`, `FriendlyByteBuf.readNbt(NbtAccounter)` `read_nbt_accounted`), ones adding a count `_count` (`TagType.skip(DataInput, int, NbtAccounter)`, `NbtAccounter.accountBytes(long, long)`), and `ListTag.add(int, Tag)` is `add_at`, next to the `add(Tag)` it inherits from `AbstractList`.
- An interface each class implements in an anonymous class held in a constant, and a factory for other ones (`TagType`: each tag's `TYPE`, and `createInvalid(id)`), becomes an enum of them, `Copy` and compared like Java's references (`TagType::Invalid(id)`). Its methods call the class's code (`ByteTag::load`).
- Java's `finally` that has to run when the body throws becomes a guard whose `Drop` does it: `NbtAccounter::push_depth_until_dropped` pops the depth even when a load panics, which leaves the accounter as Java's. What a guard does in `drop` must not panic, which would abort a thread that's already panicking.
- A getter that hands out a value it holds, which Java shares by reference, lends it here (`CompoundTag.getCompound` returns `Option<&CompoundTag>`), and one that makes a new value when there's none (`getCompoundOrEmpty`) returns a `Cow`. Callers changing what they got from such a getter are settled when one comes.
- Deep class hierarchies (`Entity → LivingEntity → Player → LocalPlayer`) are settled in "Entities" below.

## Codecs

The network codecs are objects Java builds out of other objects and lambdas, so they get rules of their own, and so do the methods taking them.

- `StreamCodec<B, V>` is a trait with two associated types, `StreamCodec<Buffer = B, Value = V>`. A codec has one buffer, Java's `B`. Java passes a codec of a buffer's parent class where a codec of the buffer is wanted (`StreamCodec<? super B, T>`); here that's a codec whose buffer the wanted one is `AsMut` of. Every buffer is `AsMut` of itself and of the buffers it wraps (`FriendlyByteBuf` is `AsMut<ByteBuf>` and `AsMut<FriendlyByteBuf>`), and a direct call derefs a wrapper (`BlockPos::STREAM_CODEC.decode(friendly_buf)`). A codec Java makes generic in its buffer takes the buffer of the codec it wraps (`ByteBufCodecs::optional`). A `composite` takes the buffer it's used on, which the static's type pins; a nested one may need it spelled out.
- A static codec field is a module `static` of type `StaticStreamCodec<B, V>` (a `LazyLock` of a boxed codec, made on first use), which an associated const refers to: `BlockPos::STREAM_CODEC`. An `IntFunction` field is the same with a boxed `Fn(i32) -> T` (`Direction::BY_ID`), passed on as `Direction::BY_ID.as_ref()`. Codecs share other codecs by reference, since `&C` is a codec.
- Java's anonymous classes implementing a codec are `stream_codec::of(encoder, decoder)`, or a struct inside the function that makes them. A trait method's codec (`map`, `cast`) and one a `CodecOperation` makes (`ByteBufCodecs::list()`'s `Collection`) are named structs: `impl Trait` in a trait method hides that the codec is `Send` and `Sync`, which a static needs, and a closure can't return `impl Trait`.
- The functional interfaces (`StreamDecoder`, `StreamEncoder`, `StreamMemberEncoder`, `CodecOperation`) are traits that every closure of the right shape implements, so lambdas and method references pass as they are (`stream_codec::of(LpVec3::write, LpVec3::read)`). A codec isn't a `StreamDecoder` too, since Rust can't have both blanket impls: where Java passes a codec as a decoder, pass `|input| codec.decode(input)`. Other functional interfaces (`IntFunction`, `ToIntFunction`, `Function`) are closures.
- `ByteBufCodecs`, an interface Java only uses for its constants and static methods, is a unit struct like `Mth`.
- Overloads: `composite`'s get their number of fields (`composite3`), ones returning a `CodecOperation` instead of a codec get `_operation` (`collection(IntFunction)` is `collection_operation`), ones adding a maximum `_max` (`collection_max`, `list_max`), and `lengthPrefixed(int, BiFunction)` is `length_prefixed_decorated`. Its decorator, Java's `BiFunction<B, ByteBuf, B>`, takes the outer buffer by reference and the slice or scratch buffer by value, and `alloc().buffer()` is `unpooled::buffer()`: the scratch buffer's capacity never shows, since only its bytes are copied out.
- A codec's collection is any Rust collection it can extend and iterate over by reference: a `Vec` for an `ArrayList`. Java's collection constructors throw on a negative capacity, which a count read from a buffer can be, so codecs making lists take `ArrayList::new` from `java::util::array_list`, which panics there too. A Java `HashSet` or `HashMap` is `java::util`'s port of it, since encoding writes in its iteration order, which its table decides, and `HashSet::new` or `HashMap::new` passed as an `IntFunction` is `from_initial_capacity` (`ByteBufCodecs.collection(HashSet::new)`, `ByteBufCodecs.map(HashMap::new, …)`). A map is any Rust collection of entries it can extend with `(key, value)` (Java's `put`) and iterate over by reference as `(&key, &value)`, and its key and value codecs share one buffer. A Guava `ImmutableMultimap` (`GAME_PROFILE_PROPERTIES`'s) iterates in the order its keys were first put, which `com::google::common::collect::immutable_multimap` keeps.
- `OptionalInt` is `Option<i32>`, and a codec's `encode` takes the value by reference, while getters and `map`'s functions return owned values (a getter clones where Java would share).
- A method taking a `StreamDecoder<? super FriendlyByteBuf, T>` (`FriendlyByteBuf.readOptional`) is generic in the decoder's buffer, `impl StreamDecoder<I, T>` where `Self: AsMut<I>`, so a decoder of a `ByteBuf` or of a `FriendlyByteBuf` passes. A static one generic in its buffer (`readNullable(B, StreamDecoder<? super B, T>)` with `B extends ByteBuf`) takes `B: AsMut<ByteBuf> + AsMut<I>`, and reaches each with `AsMut::<ByteBuf>::as_mut(input)`. A value they write that Java lets be null, or passes as an `Optional`, is an `Option<&T>`, and `T` may be a trait object, as Java's may be an interface (`writeNullable` of a `&dyn CustomQueryAnswerPayload`). A `Consumer` is an `FnMut`, an `IntFunction` an `Fn(i32) -> T`, and a `ToIntFunction` an `Fn(&T) -> i32`.

- `mapStream(Function)`, which wraps a connection's `ByteBuf` in the buffer a codec reads (`FriendlyByteBuf::new`) and shares its bytes, takes the buffer for the call and hands it back after (`From<FriendlyByteBuf> for ByteBuf` is Java's `unwrap()`), even when the call panics, so a throwing read leaves the buffer where Java's does.

## DataFixerUpper

DataFixerUpper (the game's codecs library, decompiled by `setup_vanilla.py` into `vanilla/<version>/src/com/mojang/`) is ported like the game's code, under `src/com/mojang/serialization/` and `src/com/mojang/datafixers/`, as far as the game's codecs reach.

- `DataResult` is an enum of its two records, `Success` and `Error`. An error's message is the string, made when the error is, where Java keeps a `Supplier` it calls when asked; they only differ when what the supplier reads changes later, which a ported caller's must not. The applicative machinery (`App`, `K1`, `Applicative`, `DataResult.Instance`) isn't ported: `ap`, `apply2`, `apply2stable` and `apply3` are written out the way its default methods curry the function and apply it to each argument in turn, which makes the errors' messages join in the arguments' reverse order.
- `Lifecycle` is an enum, compared by value, where Java's are instances compared by reference; only `setLifecycle`'s choice to keep the result it has tells them apart, with the same outcome.
- `DynamicOps<T>` is an object-safe trait, so codecs take `&dyn DynamicOps<T>`. Its `T` is an `OpsValue` (NBT's `Tag`, Gson's `JsonElement`): a value that clones, compares and prints, whose `convert_to` is its ops' `convertTo`, so `convertTo`, `convertList` and `convertMap`, which are generic in the other ops' type, are free functions (`dynamic_ops::convert_to`). Java's streams and the consumers of them (`getStream`, `getList`, `getMapValues`, `getMapEntries`, `createList`, `createMap`) are `Vec`s, which is all the game's codecs do with them, and a `ByteBuffer` is its bytes. A default an ops overrides and falls back on (`NbtOps.getByteBuffer` calling `DynamicOps.super.getByteBuffer`) is a free function the trait's default calls too (`dynamic_ops::get_byte_buffer`).
- `MapLike` is a trait whose values borrow the map, and `entries()` collects its stream. `ListBuilder` and `RecordBuilder` are traits whose methods change the builder in place where Java returns it, which every encoder the game's codecs reach does; their `withErrorsFrom(DataResult<?>)` takes the result mapped to `()`. `AbstractStringBuilder` is `StringBuilder`, generic in what its subclass builds (`StringBuilderOps`); `RecordBuilder.MapBuilder`, the default `mapBuilder()`, isn't ported, since `NbtOps` and `JsonOps` have their own.
- **Codecs.** Java's `Codec<A>`, `Encoder<A>`, `Decoder<A>`, `MapCodec<A>`, `MapEncoder<A>` and `MapDecoder<A>` have methods generic in the data's type, which a trait object can't have, so the traits are generic in the data's type `T` (`Codec<T>`, `MapCodec<T>`…), and the value's type `A` is `Valued`'s associated `Value`, which a codec's encoder and decoder share. Each codec is a struct implementing them for every `OpsValue` `T` (`Xmap<C, F, G>`, `ListCodec<C>`, `FieldOf<C>`…). A codec held as a value, where a static, a dispatch's choice or a recursive codec needs one, is a `BoxedCodec<A>` or `BoxedMapCodec<A>`, which holds the codec once for each kind of data as a trait object (`dyn Codec<Tag, Value = A>`), and `OpsValue::boxed_codec` picks the one for `T`. Java's default methods that make codecs are `CodecExt`'s and `MapCodecExt`'s, implemented for every codec and map codec of NBT (every codec is one), so `INT.list_of().field_of("a")` reads like Java. A combinator implemented in Java with `of` of two halves keeps both halves' semantics in one struct (`flatXmap`'s decoder `flatMap`s, its encoder `flatComap`s), and `MapCodec.of`'s keys are the encoder's then the decoder's.
- `encode` takes the value by reference, getters return owned values, and a decoder's rest of the input is cloned where Java hands back the input. A map encoder writes into `&mut dyn RecordBuilder<T>`. Compressed maps (`KeyCompressor`, an ops whose `compressMaps()` is true) aren't ported and panic: neither `NbtOps` nor `JsonOps.INSTANCE` compresses.
- `RecordCodecBuilder`'s applicative (`App`, `K1`, `Products`, `Instance`) is plain Rust: `record_codec_builder::map_codec((field…), constructor)` (or `create` for its codec) of 1 to 16 fields, each `map_codec.for_getter(getter)`. Encoding writes the fields in order, like the applicative's encoders. Decoding reads every field: one field is `lift1`'s `flatMap` (its error as it is, lifecycle and all), more are what `ap2`, `ap3` and the `apN` compositions of them come to, the record made if every field has a value or a partial one, the messages joined in the fields' reverse order, the lifecycles added to `point`'s experimental one.
- `KeyDispatchCodec` holds its functions as `Arc<dyn Fn>`s choosing a `BoxedMapCodec` of the dispatched value; a type that's an enum's variant maps in and out of the enum (Java's cast). `recursive` is an `Arc<RecursiveCodec<A>>` made with `Arc::new_cyclic`, whose function gets a `RecursiveRef` (a `Weak` to it) and is called on first use, like Java's memoized supplier.
- `NbtOps`' list collectors are an enum (`ListCollector`) of the four classes: merging a tag of an array's kind keeps the array, anything else makes it a list. `CompoundTag.shallowCopy` copies the map like `new HashMap<>(tags)`, which sizes its table for the size, so the copy can iterate in another order.

## Text components

- **A `Component` is a shared `MutableComponent`** (an `Arc`, which derefs to it): Java's interface has one class the client reads, shared by reference. The static factories (`Component::literal`, `translatable`, `keybind`) make the `MutableComponent`, which `append` and the `with…` methods change in place, and `into()` shares. Its contents are an enum of Java's classes (`ComponentContents::Text`, `Translatable`, `Keybind`, `Score`, `Selector`, `Nbt`, `Object`); a translation's arguments, Java's `Object`s, are `TranslationArgument` (a string, a number's box, a boolean or a component).
- **Records of an interface are an enum's variants** (`ClickEvent`, `HoverEvent`, `FontDescription`), and their map codecs read the variant and write it through a getter that panics on another (Java's cast). A dispatch's choice is the variant's `BoxedMapCodec`. A kind not ported yet (a dialog click) has `map_codec::unported`, which fails to decode saying so, and goldens don't make one.
- **Scores, selectors and NBT are the server's to resolve** (`resolve`, which runs commands' searches, isn't ported); the client decodes what a server sends unresolved and shows what Java's client shows: nothing for a score or NBT, the selector's text. What decodes is what parses, so their strings go through the command parsers, ported for it: `EntitySelectorParser` with every option's reading and applicability (not the entity tests it collects), `NbtPathArgument.parse`, `BlockPosArgument.parse`, `MinMaxBounds`' readers, and SNBT (`TagParser`, a selector's `nbt` and a path's patterns). `CompilableString` is the string with its parse.
- **`createLegacyComponentMatcher` serves three kinds** (a component's contents, an NBT component's data source, an object's kind), each a `LegacyType`: the enum of its classes, which knows each class's map codec and a value's class.
- **An item component's value is kept as the data it was read from** (`DataComponentPatch`, as NBT through `ExtraCodecs.NBT`): the component types' value codecs aren't ported. So an item shown on hover decodes wherever Java's does, and also where Java's codec would reject a value, which a vanilla server doesn't send; a patch's `toString` prints the data, where Java prints each value's class. The items and the component types are tables of names in their registries' order (`Items::NAMES`, `DataComponents::TYPES`, checked against vanilla's registries).
- **A player's head (`ResolvableProfile`) prints by identity** in Java (it has no `toString`), so the port prints its class's name, and the component suite records no `toString` of a component holding one.
- **`Style.EMPTY` is told apart by reference** in Java (`isEmpty`, `applyTo`); here the constant carries a flag only it and its clones have, and the codec's constructor and `checkEmptyAfterChange` make it where Java does.
- **Static codecs** are `StaticCodec<A>` (a `LazyLock<BoxedCodec<A>>`) behind an associated const (`TextColor::CODEC`), and `shared()` hands one out to build other codecs with (`Identifier::CODEC.shared().field_of("id")`). Codecs that reach each other (a hover event's text is a component) are made on first use, like Java's memoized recursive codec.
- **JSON.** `JsonOps` is the JSON half of every codec (`BoxedCodec` holds a codec for each of NBT and JSON). Java streams a `JsonNull` member or element as `null`; here it stays `JsonElement::Null`, which reads the same, and `convertTo` panics on one, where Java dereferences the `null` (a translation's argument list holding a `null`). A `ResourceKey` the error messages print (`byNameCodec`'s) is written out, and `RegistryOps` is a delegating ops over the client's `RegistryAccess`, which no codec ported yet looks into.
- **Translations** come from `en_us.json` and `deprecated.json` in the vanilla jar, read once (`Language`); the client's `ClientLanguage` reads the same file from the vanilla pack. A key binding's name shows as `KeybindResolver`'s default, the name itself, until key mappings come.
- **Visiting a component's text** is `FormattedText::visit` (pieces of text) and `visit_styled` (each with its style, the component's own over its parent's); `get_string` joins the pieces.

## Gson

Gson 2.14.0, the game's JSON library, is ported from its sources (which `setup_vanilla.py` puts next to the game's, `vanilla/<version>/src/com/google/gson/`) under `src/com/google/gson/`, as far as the game reads and writes JSON: the tree, the streaming reader and writer, `JsonParser`, and `Gson.toJson` of a tree. Its type adapters, reflection, `fromJson` and pretty printing aren't.

- **`JsonElement` is an enum of Gson's four classes**: `Null` (`JsonNull.INSTANCE`), `Primitive(JsonPrimitive)`, `Array(Vec<JsonElement>)` (all a `JsonArray` holds) and `Object(JsonObject)`. A `JsonObject` is a `Vec` of its members in `LinkedTreeMap`'s order: the order names first came, a name added again keeping its place, a removed one leaving the others in order. `equals` is `PartialEq` (an object's in any order, like `AbstractMap`'s), `toString()` is `Display` (a lenient `JsonWriter` that writes nulls), and only `JsonPrimitive` has `hash_code`: `JsonNull`'s is an identity hash.
- **A primitive holds Java's value**: a `Boolean`, a `String`, or a `Number`, `java::lang::number::Number`, which has Gson's `LazilyParsedNumber` (a parsed number's text, which each conversion parses: `Float.parseFloat`, `Integer.parseInt` falling back to `Long.parseLong` and the `BigDecimal`'s integer part…) and `BigDecimal` (`java::math::big_decimal`: digits and a scale, parsed with `NumberLimits`' limits, converted like Java's, printed in its scientific form) besides the primitives' boxes. The JDK's parsers are ported with their grammars and messages: `Float.parseFloat` takes surrounding whitespace, hex, `NaN`, `Infinity` and a type suffix (`jdk::internal::math::floating_decimal`), and `Integer.parseInt` and `new BigDecimal` any Unicode decimal digit. `JsonPrimitive.equals` compares two numbers that aren't both integral as doubles, which throws for a `LazilyParsedNumber` whose text isn't a number; Java returns true for the same object first, which a clone stands for, so two of the same text are equal.
- **Errors are values where callers catch them.** The reader, `JsonParser`, the writer and `Gson.to_json` return `Result<_, Throwable>`: `java::lang::throwable::Throwable` is Java's exception as its class's binary name, its message and its cause, since `ByteBufCodecs.lenientJson` catches `JsonSyntaxException` and `JsonOps` reads results. The JDK's parsers return a `NumberFormatException` of their own, and `BigDecimal.longValueExact` an `ArithmeticException` (`JsonOps.convertTo` catches it). A getter that throws where nothing catches (`getAsInt` of a string that isn't a number, `getAsJsonObject` of an array) panics, with Java's `toString()` of the exception.
- **The reader is Java's state machine over Java's buffer.** `JsonReader::new(&str)` reads the string's UTF-16 units into the same 1024-unit buffer the way a `StringReader` hands them out, so lines, columns and what a token across the buffer's end does are Java's (a number of 1024 units or more reads as an unquoted string), and so are the three strictnesses, the nesting limit and every lenient extension. A Rust string can't hold a lone surrogate, so an escape of one (`"\ud800"`) reads as U+FFFD.
- **Parsing.** `JsonParser::parse_string` is `parseString` (lenient while it reads the value, then the default strictness's check that nothing follows it), which `LenientJsonParser` calls, and `StrictJsonParser::parse` reads with `Strictness::STRICT`. Both read an empty document as JSON null. `JsonElementTypeAdapter` reads with an explicit stack of the arrays and objects open, like Java's, so nesting can't overflow the call stack.
- **Writing.** `JsonWriter` writes into a `String`, compact only. `Gson` holds what `toJson(JsonElement)` reads (HTML escaping, nulls, the non-execute prefix, the strictness), made by `GsonBuilder`: `GsonBuilder::new().disable_html_escaping().create().to_json(&element)` is `lenientJson`'s.

## Packets and protocols

- `Packet<T>` is a trait for the listener `T` that handles the packet, and a protocol's codec reads and writes `Box<dyn Packet<L>>` for its listener `L`. Java's protocols take packets of the listener's parents too (`Packet<? super L>`, like the cookie packets in login), so a packet implements `Packet<L>` for every `L` of its kind: `impl<L: ClientLoginPacketListener + ?Sized> Packet<L> for ClientboundHelloPacket`. Calling a `Packet` method on a concrete packet then names the listener: `Packet::<dyn ServerHandshakePacketListener>::r#type(packet)`.
- Listener interfaces are traits with their handlers (`handle_intention(&mut self, &ClientIntentionPacket)`), and `handle(&self, listener: &mut T)` calls one. A listener's default `flow()` and `protocol()` would fill in its parent's methods, which a Rust trait can't, so they come with `PacketListener`'s methods and `Connection`.
- `PacketType<T>`'s type argument only tells the compiler which packet class has the type, so it's a plain `PacketType`. The `*PacketTypes` constants are `LazyLock<PacketType>` statics, and `type()` (`r#type`) returns the shared one, `&'static PacketType`.
- A packet's private constructor reading a buffer is `from_friendly_byte_buf`, and its private `write` is `write`; `packet::codec(write, from_friendly_byte_buf)` makes its `STREAM_CODEC` like Java's `Packet.codec`. A record's `toString` is `Display` (`ClientIntentionPacket[protocolVersion=777, …]`), and its `hashCode` adds each component's to 31 times the ones before.
- A record's array component (a cookie's payload) is an `Arc<Vec<i8>>`, a reference to the array like Java's. The record's `equals` compares it by reference, which is `Arc::ptr_eq`: a clone of the packet shares the array and equals it, and another packet with the same bytes doesn't. Its `hashCode` and `toString` hash and print the array's identity hash, which changes from run to run, so they aren't ported.
- An interface whose implementations are records (a custom query's payload) is a trait with `Display` as a supertrait and Java's `equals` and `hashCode` as methods, `equals(&self, other: &dyn Trait)` and `hash_code`, since `PartialEq` can't be a supertrait of a trait a `dyn` holds. `dyn Trait` is `PartialEq` through `equals`. A packet holding one as `Box<dyn Trait>` writes its own `PartialEq` out, since `derive` tries to move a boxed trait object to compare it.
- A custom packet payload (`BrandPayload`, `DiscardedPayload`) implements `CustomPacketPayload`, a trait like the custom queries' payloads, and a packet holds one as an `Arc<dyn CustomPacketPayload>`, Java's shared reference: its getter hands out a clone of the `Arc`, which a codec's `map` needs, and `equals` goes through the payloads'. `CustomPacketPayload.Type`'s type argument only tells the compiler which payload has the type, so it's a plain `Type`, and `TypeAndCodec` holds its codec as one of any payload, which shares what it reads and casts what it writes back to its payload, panicking where Java's lambda throws `ClassCastException`. `codec(FallbackProvider, List)`, which overloads `codec(StreamMemberEncoder, StreamDecoder)` with the same arity, is `codec_with_fallback`, and `FallbackProvider` is a functional interface every `Fn(Identifier) -> C` implements.
- `FriendlyByteBuf.readEnum(Class)` and `writeEnum(Enum)` take an enum that implements `java::lang::r#enum::Enum`: its constants in order (`ENUM_CONSTANTS`, Java's `getEnumConstants()`) and `ordinal()`. `read_enum::<Action>()` stands for `readEnum(Action.class)`.
- `IdDispatchCodec`'s `add` takes a codec of its values themselves. `ProtocolCodecBuilder` boxes each packet its codec reads and casts what it's given to write back to the packet's class (`Upcast`), the cast Java's generics make without saying.
- `ProtocolInfo`, `ProtocolInfo.Details`, `SimpleUnboundProtocol` and the context wrapper are traits and types made once each by `ProtocolInfoBuilder`, held in statics as `StaticProtocolInfo<L>` and `StaticSimpleUnboundProtocol<L, B>`. The context wrapper, Java's `Function<ByteBuf, B>`, is an `Arc<dyn Fn(ByteBuf) -> B>`, since each packet's codec holds it. A protocol without a context has Java's `Unit` as its context, which is `()`. `build_unbound` moves the builder in, where Java copies its list.
- Netty's `DecoderException` and `EncoderException` that `IdDispatchCodec` wraps a packet's exception in are panics, which carry no class, so the packet's panic goes on as it is.
- **Registries.** A `RegistryAccess` is the client's static registries the port has (`BuiltInRegistries`, so far the attributes', each `Attributes` registers in Java's order) and the ones the server sent, each a `Registry` of its elements' keys in id order. A `Holder` is its key. Java's `Holder.Reference` hashes by identity, so a Java map of holders iterates in another order every run; here a holder hashes its key's identifier, and only maps whose order nothing reads hold them (`ClientboundSetTimePacket`'s `ClockUpdates`).
- **An entity's synced data.** `EntityDataSerializer` is an enum of `EntityDataSerializers`' constants, numbered in the order Java registers them, and a `DataValue`'s value an `EntityDataValue`, a variant for each serializer's type. A serializer whose type isn't ported yet reads as `EntityDataValue::Unported`, which skips the rest of the frame, since nothing says how long its value is, and `ClientboundSetEntityDataPacket` stops reading after it: like an `Unported` packet, which vanilla answers nothing to, but the values before it still arrive.

## Netty handlers

- A handler in the game's pipeline (`Varint21FrameDecoder`, a `ByteToMessageDecoder`; `Varint21LengthFieldPrepender`, a `MessageToByteEncoder`) is a struct whose `decode` or `encode` leaves out the `ChannelHandlerContext` it doesn't use. Its output list is a `Vec` of what it makes (`Vec<ByteBuf>` for frames), and releasing buffers in `handlerRemoved` is Rust's drop.
- What Netty does around a handler (cumulating what arrives, calling `decode` again while it makes progress, releasing the message after `encode`) belongs to the pipeline, which is `Connection`'s. The golden cases drive a decoder the way Netty does (TESTING.md).

## The connection's threads

- **The connection has its own thread, Netty's event loop.** Java's `Connection` is the last handler of a Netty pipeline that Netty runs on an event loop thread, which reads, decodes and writes while the game thread draws. The port's `Connection` holds the socket and the handlers (splitter, decompression, the packet decoder and bundle packer; the packet encoder, compression, the prepender), and its event loop runs on a thread `EventLoopGroupHolder::remote()` starts for it (`Netty Client IO #0`, like the group's). The loop takes, in order, what the socket read and the tasks other threads hand it (Netty's `execute`): Rust's sockets block, so a second thread reads the socket and hands the loop what came, where Netty's selector would wake it. The game thread only sleeps between frames, at vanilla's default frame rate limit of 120 (`Minecraft::run`).
- **The connection is shared like Java's**, an `Arc<Connection>`: what both threads touch is atomic or behind a lock (`packet_processor::lock`, which takes a lock a panic left behind too), and the pipeline's handlers only run on the event loop. `send` from the event loop writes at once, and from any other thread hands the write to the loop, which keeps the order the game sent in (`Connection.send`: every client send flushes, so `flushChannel` and `tick`'s flush have nothing left). Setting a protocol up, compression, and `disconnect` run on the loop too, and wait for it like Java's `syncUninterruptibly` and `awaitUninterruptibly`, so what was sent before goes out first. A disconnection's details are set as the channel closes, so the game thread never finds it closed without them. Encryption, which sits before the splitter, comes with online mode.
- **A listener is two halves.** Java's listener is one object both threads call; a Rust listener holds the game (`Rc<Minecraft>`), which only the game thread can touch. So the game thread's half is the listener as Java writes it (`ClientPacketListener`, an `Rc<RefCell<…>>`, which the connection ticks and tells about the disconnection), and it makes the half the event loop hands packets to (`SplitListener::netty_listener`, a `Box<dyn NettyListener<T>>`, the `NettyHalf` of its module), which implements the same listener trait. The connection calls `packet.handle` on that half, like `channelRead0`, and its handlers are Java's up to `PacketUtils.ensureRunningOnSameThread`: a handler Java runs on Netty's thread runs there, and one that calls `ensureRunningOnSameThread` first queues a copy of its packet for the game thread's half, which `Minecraft.runTick` takes at the start of each frame (`PacketProcessor`, a `Mutex`ed queue like Java's concurrent one). On the game thread the same call lets the handler go on, so the game thread's half keeps Java's handlers whole. A handler adding a game protocol packet adds a line to the Netty half too, which the compiler asks for: Java's handler up to that call, `self.common.on_game_thread(&self.this, packet)` for most.
- **What both halves touch is the listener's `Shared`** (an `Arc`): the deferred packets and the transfer flag, the enabled features, the chunk batch calculator, whether the listener is closed. The handlers Java runs on Netty's thread are `Shared`'s methods, which either half runs: Netty's, or the game thread's for a packet inside a bundle, whose sub-packets Java hands to the listener on the game thread.
- **The game thread's listener is named, not shared.** Other threads name it with a `GameThreadListener<T>` (`packet_processor`), which the connection and the queued packets hold, and the game thread looks it up when it handles one; it lives as long as something names it, like a Java reference, and is let go of on the game thread.
- **Handlers on Netty's thread, Java's and the port's:** `handleKeepAlive`, `handleDisconnect` and a discarded payload's `handleCustomPayload` (the common ones; `handleTransfer` sets its flag there before it asks for the game thread); `handleEnabledFeatures` and `handleResetChat` (configuration); `handleChunkBatchStart`, `handleChunkBatchFinished` and `handlePongResponse` (game), with `handlePlayerCombatEnd`, `handlePlayerCombatEnter`, `handleDebugSample` and `handleLowDiskSpaceWarning`, whose packets aren't ported yet; every login handler; and the status listener's. Every other handler ported calls `ensureRunningOnSameThread` first.
- **The login's end is the one handler split further.** `handleLoginFinished` runs on Netty's thread in Java, and makes the configuration listener, which holds the game: its Netty half switches the state and queues the packet for the game thread's half, which makes the listener, sets the configuration protocol up and sends what Java sends. The packet is terminal, so nothing is read meanwhile, and the client's packets go out in Java's order.

## The connection and the client's listeners

- **A terminal packet stops the decoder or the encoder** until the next protocol's is set up, like `ProtocolSwapHandler`: what arrives after `finish_configuration` waits in the frame queue (Java's `FlowControlHandler`) until the game thread handles the packet and sets the game protocol up.
- **`Connection.send(Packet<?>)` names the packet's listener:** `send::<dyn ServerGamePacketListener>(packet)`. The encoder casts it to its own protocol's, and panics like Java's `ClassCastException` for another's. A packet that implements `Packet<L>` for every listener of a kind (the common packets) is sent with the listener of the protocol it's sent in; `ClientCommonPacketListenerImpl<S>` is generic in that server listener `S`.
- **The pipeline's errors are panics it catches**, like Netty's `exceptionCaught`: a packet that doesn't decode, or a handler that fails on the Netty thread, disconnects with `Internal Exception: …`; a handler that fails on the game thread goes to the listener's `on_packet_error`, like `PacketProcessor`'s.
- **The game thread's objects are `Rc`s with interior mutability**: each listener's game thread half (`Rc<RefCell<…>>`) and the game (`Rc<Minecraft>`, its fields in cells). A listener keeps a weak reference to itself (`this`) for `ensureRunningOnSameThread`, which is Java's `this`. A handler holds its listener borrowed, so what it calls must not borrow it again: `Minecraft::disconnect` closes the listener only when nothing has it borrowed, and the listener calling it closes itself first.
- **An abstract listener class is a struct its subclasses hold** (`ClientCommonPacketListenerImpl` in `common`), and `client_common_handlers!` writes the interface's handlers on each concrete listener to forward to it with `this`.
- **Bundles go through the packer the protocol asks for.** A protocol with bundles (the game protocol's clientbound side, `withBundlePacket`) has a `BundlerInfo<T>` for its listener's packets, and the connection puts a `PacketBundlePacker` after that protocol's decoder, which hands on the packets between two delimiters as one bundle. Java tells the delimiter by reference, the one instance its `unit` codec decodes to, which here is its type. A bundle's sub-packets are an `Arc`, shared by the copy a handler queues for the game thread, like Java's `Iterable`.
- **A packet the port can't decode yet is `Unported`** (`network::protocol::unported`, which has no Java file): its codec skips the rest of the frame, and its `handle` does nothing. The protocols list every one of vanilla's packet types in vanilla's order, so ids match, with `Unported` for the classes not ported yet; that's only right for packets vanilla answers nothing to (GOAL.md). A terminal packet is never `Unported`. The codec counts what it skips by type, which the client prints as it exits (`Unported packet minecraft:…: N`), and the soak reports.
- **A disconnection's reason is a `Component`**, like Java's `DisconnectionDetails`: the reasons the client gives itself are translations (`DisconnectionDetails::translatable("disconnect.timeout")`, `generic_reason` for `disconnect.genericReason` with Java's `Internal Exception: …`), and a server's is its component. `reason_text()` is what the disconnected screen would show (`getString`).
- **A server's resource pack, with no screen to ask.** Java asks the player with a screen (`PackConfirmScreen`) unless the server's setting in the server list answers already, and until the player answers it sends nothing: in configuration the server waits for a final answer before going on (`ServerResourcePackConfigurationTask`), so an unattended vanilla client never gets into the world. The port has no screens, so it answers the prompt itself (`answer_pack_prompt`, the screen's callback), with the answer that keeps the player on the server, which the pack's required flag decides. A required pack gets "Proceed": the server's setting becomes enabled and the pack is accepted (`ACCEPTED`); declining it would disconnect (`multiplayer.requiredTexturePrompt.disconnect`, and the server kicks a player declining a required pack). An optional pack gets "No": `DECLINED`, and the server's setting becomes declined, so later optional packs are declined without asking, like Java's after "No". A URL that isn't `http` or `https` gets `INVALID_URL` first, like Java's. Downloading and applying packs (`DownloadedPackSource`'s manager, a resource reload) isn't ported: an accepted pack is answered as a download that failed (`FAILED_DOWNLOAD`, which the server takes as final and doesn't kick for), and the client logs it. `DownloadedPackSource::push_pack` hands the answers to the listener, which sends them in its protocol (`Connection.send` names the protocol's listener).
- **A level, a player and a screen the port doesn't have yet are stand-ins in their Java files**: `ClientLevel` is what the login said, `LocalPlayer` stands still where the server puts it, and the screens are the few states a headless client has. Each file's header says what it leaves out.

## Blocks and block states

The game compares blocks and states by reference and numbers them in the order `Blocks` registers them, so here they're handles into the registry that numbering makes.

- A `Block` is its id in `BuiltInRegistries.BLOCK`, `Copy`, and derefs to its `BlockData`: what Java's object holds, `BlockBehaviour`'s fields (which it derefs to), its state definition, its default state, its class and the fields its class adds that are ported. `Blocks::STONE` is a const: the `blocks!` macro numbers each field after the blocks the fields before it hold (a `ColorCollection` 16, a `WeatheringCopperCollection` 8), and checks each registration lands where its field says.
- A `BlockState` is a reference to its block's `StateDefinition` and its index there, `Copy` and 16 bytes, and needs no registry to answer for its values, so states work while `Blocks` is still registering. Its id is the block's first id plus the index. A definition is made once for each block and kept for the game's lifetime (leaked). Its states are the cartesian product of its properties' values, the properties sorted by name and the last varying fastest, so an index is a mixed-radix number of value indexes, and `setValue` changes one digit: the state Java's neighbour table holds. What `BlockStateBase` keeps of each state (its light, map colour, whether it occludes or ticks…) is a table by id, which the registry makes with the blocks, like Java's static initializer and `initCache`.
- Registering reads earlier blocks (`ofLegacyCopy(base)`, a stair's base state, `X.defaultMapColor()`), so the registry being built, Java's global `BuiltInRegistries.BLOCK`, is a parameter of `Blocks`' registrations (`registry`, a `Registrar`), which lends out the blocks registered so far. The registry is a static made on first use.
- `Property` is Java's `Property<?>`, with values as `Comparable`s (a boolean, an int or an enum constant), and `TypedProperty` gives `state.get_value(BlockStateProperties::FACING)` its type. Properties are statics, compared by address like Java's references (`property::same`). An enum a property takes implements `PropertyEnum`: its class's binary name, `StringRepresentable`, and `Display` as its `toString`. A property made with a filter over its enum's constants lists the constants the filter keeps, in their order.
- A class extending `Block` is a `BlockClass` static: its binary name, its parent, and the methods it overrides that are ported (`isRandomlyTicking`, being an `EntityBlock`), which a call looks up the chain like Java's dispatch. `XBlock::new(properties)` is Java's public constructor (with the arguments that are ported before the properties) and makes a `BlockData`. `new_with(properties, class, definition)` is the constructor its subclasses call: the most derived class and its `createBlockStateDefinition` go down the chain to `Block::new_with`, the way Java's `Block` constructor calls the most derived override. A virtual method a constructor asks (`CropBlock.getAgeProperty`) goes down the chain the same way, and stays in the block's fields when a method asks it later.
- `Properties` holds Java's lambdas as Rust functions of the state (`light_level`, `map_color_fn`, `emissive_rendering`, `post_process`), and its predicates taking a level as values that say which they are (`StatePredicate`, `ViewBlocking`): Properties' defaults, which read the block's shapes or tags, `Blocks`' named ones, or functions of the state alone. A level argument none of vanilla's functions read is left out. A default `isViewBlocking` asks the `Properties` it was made for, which a copy made with `ofFullCopy` keeps asking. A lambda reading another block when a state is made (`COPPER_BLOCK.weathering().pick(state).defaultMapColor()`) is worked out when the block is registered: it's a constant.
- What isn't ported is left out of `Blocks`' registrations and named in its header (`sound`, `isValidSpawn`, `requiredFeatures`), and each class's header names its constructor arguments that aren't ported, which don't decide its states.

## Entities

- **A class's fields are a struct that holds its parent's and derefs to it**: `LocalPlayer` holds a `Player`, which holds a `LivingEntity`, which holds an `Entity`. A field Java's subclasses read (`horizontalCollision`, `xxa`) is `pub`.
- **Java's virtual methods are a trait per class** (`EntityClass`, `LivingEntityClass`, `PlayerClass`), whose default methods are the declaring class's code, written as functions of its module (`entity::r#move`, `living_entity::travel`). A subclass's override is a function of its own module that can call the parent's like `super` (`player::travel` calls `living_entity::travel`), and the concrete class (`LocalPlayer`, the only one so far) implements every trait, forwarding each method to the most derived override along its chain. A method that passes the entity on as a `&dyn EntityClass` (to the level's collision queries) has `where Self: Sized`, and the functions take `this: &mut impl EntityClass`.
- **The level is a parameter** (`&dyn Level`), since an entity's `level` field is a back-reference to what owns it. `Level` is what an entity's tick asks of it besides collisions (`CollisionGetter`), until the world track's `ClientLevel` implements both.
- Entity data an entity syncs (the shared flags, the pose, no gravity) are plain fields until entity data is ported; setting the pose resizes the entity like `onSyncedDataUpdated(DATA_POSE)`.
- What isn't ported in a method an entity's tick runs panics where it would change the outcome (bouncing, gliding, pistons, auto-jump, fast lava), and is named in the file's header where it only feeds rendering or sound (the walk animation, the body's rotation, step sounds, water's splash).
- Fluids are read through `EntityFluidInteraction`, which an entity holds like Java's: its trackers are per fluid (still and flowing water apart, Java's `Holder<Fluid>`), and its accumulators per tag. Fluid tags, like block tags, answer from vanilla's data pack (`Fluids::is_tag`, `tags/fluid_tags.rs`). A fluid's behaviour (`getHeight`, `getOwnHeight`, `getFlow`, `getShape`) is a method of `Fluids` that dispatches to its class's module (`flowing_fluid`, `empty_fluid`); `FlowingFluid.shapes`, which keeps the first shape made for each state whatever its height there, is a thread-local that `Minecraft::new` empties, a new game's like a new JVM's.
- An `EntityType` is its id in `BuiltInRegistries.ENTITY_TYPE`, `Copy` like a `Block`, and derefs to what Java's object holds (`EntityTypeData`); `EntityTypes` registers every type on first use, and the registry falls back to the pig like Java's `DefaultedRegistry`. An entity knows its type (`Entity::get_type`), and the player is `EntityTypes::PLAYER`.
- Block tags come from the server in Java (`update_tags`), which isn't ported: `BlockState::is_tag` answers from vanilla's data pack until it is, which is what a vanilla server sends.

## Voxel shapes

- A `VoxelShape` is an `Arc` of what Java's object holds: its voxels (`Arc<dyn DiscreteVoxelShape>`), its subclass with its fields (`Kind::Array`, `Cube` or `Slice`, which `getCoords` and `findIndex` match on), and its cache of face shapes (`OnceLock`s, so `getFaceShape` takes `&self`). The game compares shapes by reference (`shape == Shapes.block()`, `first == second` in a join), and `VoxelShape`'s `equals` is `Object`'s, so `==` is `Arc::ptr_eq`, and `Shapes::block()` and `empty()` hand out clones of the one static. A made shape never changes, so it's shared across threads like Java's statics.
- `DiscreteVoxelShape` is a trait whose provided methods are the abstract class's own, and `BitSetDiscreteVoxelShape` and `SubShape` implement it. `instanceof` is `as_any`. `fill` is `BitSetDiscreteVoxelShape`'s, with `&mut self` while a shape is made: nothing fills a `SubShape`.
- A shape's coordinates are fastutil's `DoubleList` (`it::unimi::dsi::fastutil::doubles`), a trait of what the shapes read, with `DoubleArrayList` and the shapes' own lists (`CubePointRange`, `OffsetDoubleList`, `NonOverlappingMerger`). Its `equals` is `AbstractDoubleList`'s (elements by `==`, after the same list or the same array). fastutil publishes no sources with the game, so it follows the bytecode.
- `IndexMerger`'s `IndexConsumer` and the shapes' line and face consumers are `FnMut`s, and `BooleanOp`, an interface only its sixteen constants implement, is an enum.
- Guava's `IntMath.gcd` and `DoubleMath.fuzzyEquals` are ported under `com::google::common::math`, and `java.util.BitSet` under `java::util::bit_set` (what the shapes call: `get`, `set`, `clear(from, to)`, `nextClearBit`, `isEmpty`, `clone`).
- `DiscreteVoxelShape.rotate`, which hands back the shape itself for the identity, is a function of the shared shape (`discrete_voxel_shape::rotate`). The maps of rotated shapes (`Shapes.rotateHorizontal`…) are `EnumMap`s in Java, which iterate in their keys' order: a `Vec` of the entries in that order here, which `Shapes::get` searches. `rotateAttachFace`'s `Map.of`, which only `get` reads, is a `Vec` too. A block's own map of properties by direction (`PROPERTY_BY_DIRECTION`) is an array in its map's order; where Java's is a `HashMap` of directions, whose order changes from run to run, any order gives the same union.
- A block class's shape methods are `BlockClass` fields (`get_shape`, `get_collision_shape`, `get_visual_shape`, `get_block_support_shape`, `get_interaction_shape`, `get_occlusion_shape`, `is_collision_shape_full_block`), functions of the block's data, the state and, as Java's take them, the level, the position and the collision context. `BlockState`'s methods (`get_shape_in`, `get_collision_shape_in`, `get_visual_shape`…) look the override up the chain like the other overrides (`BlockClass::find`) and fall back on `BlockBehaviour`'s defaults, which are functions of `block_behaviour` (`get_collision_shape`, `get_visual_shape`, `get_block_support_shape`, `get_occlusion_shape`, `get_shade_brightness`) that an override calling `super` calls too. Java's `this.getX(state, …)` inside a block is the state's method, since the state's block is `this`. Every class's overrides are ported.
- Shapes a class works out for each state when it's made (`getShapeForEachState`, `makeShapes`) are a `Vec` by state index in the block's fields, and `getShapeForEachState(Function, Property...)` (`Block::get_shape_for_each_state_ignoring`) works each out once with the ignored properties at their first values and shares it with the states that only differ in them, like Java's map. Static ones are `LazyLock`s. A constructor argument a block's shapes come from is ported with them (an amethyst cluster's `height` and `width`, a growing plant's `shape`, a pipe's `size`, a flower bed's `shapeHeight`, a skull's `type`), passed down the chain like Java's `super(…)`.
- A `CollisionContext` is what the shapes ask of it: `EntityCollisionContext` keeps the entity's answers (descending, its bottom, the item in its main hand by its id, and what powder snow and fluids ask of the entity itself: its fall distance, whether it's a falling block, walks on powder snow, or stands on a fluid as a living entity), none for a context without an entity. `instanceof EntityCollisionContext` is `as_entity_collision_context`.
- What a block's shape asks of its block entity it reads through `BlockGetter::get_block_entity` (borrowed, without making one: a level or chunk's, none for what keeps none): a shulker box's lid as far as it's open, a moving piston's block where it is so far. A moving piston's block entity reads Java's thread-local `NOCLIP` (which entity a piston is moving, whose moving block doesn't collide with it) from a thread-local too.

## Chunks

- A section's values are a `PalettedContainer<T>`, generic in its values (block states, a biome's `Holder`), which need to be `Clone + PartialEq + Hash`: Java compares them by reference, which for the values a registry hands out is comparing them. Its `Strategy` is shared by the containers it makes, in an `Arc`, and the registry it numbers values by is an `Arc<dyn IdMap<T> + Send + Sync>` (`Block.BLOCK_STATE_REGISTRY` through a `&'static` reference, which is an `IdMap` too).
- `Palette` and `BitStorage` are traits, but a container holds its palette and storage as enums of the kinds there are (`AnyPalette`, and a private `Storage`), which dispatch with a `match`: `get` is what every block lookup calls. Java's `Palette.Factory`, three method references in `Strategy`, is an enum of the three, so configurations holding one compare like Java's records.
- A full palette calls its container back (`PaletteResize.onResize`), which replaces the palette it was called on. The palette takes a `&mut dyn PaletteResize<T>` like Java's; the container hands it one that notes the bits asked for, and makes the new palette once `idFor` has returned, which is the same, since each palette returns `onResize`'s answer as soon as it has it.
- What only identity hashes decide stays out of the goldens: `CrudeIncrementalIntIdentityHashBiMap` hashes keys with Rust's fixed default hasher, which gives the same answers wherever Java's are the same from run to run (TESTING.md). `count`'s order, an `Int2IntOpenHashMap`'s in Java, is the order values first come in the storage.

- A section is a `LevelChunkSection` of a `PalettedContainer<BlockState>` and a `PalettedContainer<Holder>`, its biomes. The block states' strategy is one for the game's lifetime; the biomes' takes the registry the server synchronized, which `PalettedContainerFactory` holds a copy of as an `IdMap<Holder>` (Java's `asHolderIdMap()`). `Holder` and `ResourceKey` are `Hash` for the hash map palette, which hashes them by value where Java hashes the holder's identity: one holder for each key, so the same.
- A state's fluid (`BlockStateBase.fluidState`) is worked out when the registry's table is made, like Java's `initCache`, from each class's `getFluidState` override (`BlockClass::get_fluid_state`). A `FluidState` is a value of its fluid and its two properties' values (`FALLING`, and `LEVEL_FLOWING` for a flowing fluid), `Copy` and compared by value, which is Java's reference comparison since each combination has one state. `Fluid.FLUID_STATE_REGISTRY`'s ids aren't ported.
- A packet's `EnumMap` (the heightmaps) is a `BTreeMap` by the enum, which iterates in the constants' order like Java's. A built-in registry the client's registry access holds (`ByteBufCodecs.registry(BLOCK_ENTITY_TYPE)`) is read without the access, from the registry itself: a `BlockEntityType` is its id there, like a `Block`.
- A record holding arrays (`ClientboundLightUpdatePacketData`'s layers, `ChunkBiomeData`'s buffer) takes them by identity in Java's `equals`, `hashCode` and `toString`, so those aren't ported; the client only reads them.

- The client's level owns its chunks: `ClientLevel` holds a `ClientChunkCache`, whose `Storage` holds each `LevelChunk` in a slot by position modulo its width, and a chunk its sections, so reads go `level.get_block_state(&pos)` → the chunk → the section, borrowed all the way, without Java's references. Java's `Minecraft.level` is the `RefCell<Option<ClientLevel>>` the listener borrows to fill. What a Java level asks a `LevelHeightAccessor` (its dimension type's height) is a `Height` value the level and its chunks keep. `BlockGetter` doesn't extend `LevelHeightAccessor` here, so what only answers blocks (the shapes' `EmptyBlockGetter`) needs no height.

## Block entities

- **A block entity is one struct** (`BlockEntity`: its type, position, block state and removed flag) whose class's fields are an enum (`BlockEntityData`), a variant for each class whose data is ported (signs, banners, skulls, spawners, campfires, brushable blocks, shulker boxes) and `None` for the others: the client tells the classes apart with `instanceof` (the shapes, the renderers), as with a sealed interface. `loadAdditional` is each variant's `load_additional`, and `BlockEntityType::create` is the type's factory, which makes the variant its class's constructor would. What a class loads that isn't ported (item stacks, a head's profile, `components`) is named in its header and left as it was; it only feeds what the renderer shows of it.
- **Types are `BlockEntityTypes`' tables**: each type's valid blocks in `register`'s order (`VALID_BLOCKS`), and each block's type (`BY_BLOCK`), the one whose valid blocks have it, which stands for its class's `newBlockEntity` but for the moving piston's, which makes none.
- **A chunk owns its block entities** in fastutil's `Object2ObjectOpenHashMap` by position (`ChunkAccess.blockEntities`; `BlockPos` hashes like `Vec3i`), ported from its bytecode (`it::unimi::dsi::fastutil::objects`), so they iterate in Java's order. Each is in a `RefCell`, since a ticker or a block event changes one while it reads the level. `getBlockEntity(pos, IMMEDIATE)`, which makes one where its block makes one, takes the chunk mutably (`get_block_entity_immediate`, `ClientLevel::get_block_entity`); the shapes' and the renderer's reads don't make one (`get_existing_block_entity`, `BlockGetter::get_block_entity`, Java's `CHECK`), and a ticker changes the one there (`get_block_entity_mut`). A block entity's level back-reference is the chunk that holds it; what a class reads of its level when the chunk takes it (`setLevel`: a beacon's lowest block, a potent sulfur's game time) comes from the level's `SharedLevelState`.
- **Java tells block entities apart by reference** (a ticker holds its own); here each has an identity, a number no other block entity the game makes has, and a ticker names its block entity by position and identity: it's removed once the level holds another there, or none, which is when Java's is marked removed.
- **The tickers are the level's and its chunks'**, as Java's: a chunk keeps a wrapper for each position whose block entity ticks on the client (`tickersInLevel`, `RebindableTickingBlockEntityWrapper`), which it rebinds as the state changes and to `NULL_TICKER` when the block entity goes, and adds new ones to the level's list (`addBlockEntityTicker`) in a `SharedLevelState` the level shares with its chunks (Java's back-reference from a chunk to its level). A class's ticker is a `BlockClass` field (`get_ticker`, the client's `getTicker`), a function of the level and the position (`BlockEntityTicker`), which borrows its block entity from the level (`LevelTicking::block_entity`) where Java hands the object over.
- **A class's `updateShape`** is a `BlockClass` field like its shapes (`Block::update_shape`, `super_update_shape` for an override's `super`, `update_from_neighbour_shapes`), handed the level's random; Java also hands it the level's scheduled ticks, which on the client go nowhere (`BlackholeTickAccess`), so an override's `scheduleTick` is left out (only a draw from the random for one would be kept) and one that only schedules is its parent's. A class Java overrides it in whose override isn't ported (`UPDATE_SHAPE_CLASSES`, the 109 that do) keeps the state and says it isn't ported, which the soak reports; 41 are ported (the connecting blocks, doors and plants, the redstone wire's connections and `updateIndirectNeighbourShapes`, and the ones that only schedule ticks). `canSurvive` and `VegetationBlock.mayPlaceOn`, which updates ask, are fields the same way, with their own lists (`CAN_SURVIVE_CLASSES`, `MAY_PLACE_ON_CLASSES`): one not ported says so and answers true. An update that turns a block to air destroys it only on a server (`Block.updateOrDestroy`), so on the client that answer only matters for what isn't air. `Level.setBlock` without `UPDATE_KNOWN_SHAPE` sends the neighbours shape updates through the level's `CollectingNeighborUpdater` (`ClientLevel::neighbor_shape_changed`), its queues behind cells so an update runs with the level borrowed mutably; the server's block packets carry that flag, so on the client these come from pistons (and, once ported, the player's own placing and breaking). `updateNeighborsAt` and `neighborChanged` do nothing on a client's level.
- **What a block event or a ticker reaches of the game is a parameter**, `LevelTicking`: the level (mutably: a block event can make a block entity), the particle engine and sound manager (`LevelEffects`, as the animations'), and the player, the only entity the port moves (`LevelPlayer`: what a block reads of it, and its `move`), Java's `getEntities` and `players()`. A class's `triggerEvent` is a `BlockClass` field like its shapes; a block entity's is `BlockEntity::trigger_event`, by class.
- **`ValueInput` is `TagValueInput`**, the one implementation the client reads with: a compound read through the registries' ops, a value of the wrong kind or one its codec can't read reported to a `ProblemReporter` and taken as missing (a codec's partial value kept), as Java's. The reporter collects descriptions and logs them when dropped (`ScopedCollector`), or discards them.

## The level's ticking

- **What the level's tick reads of the game is a parameter**: `ClientLevel::tick` takes the packet listener's clocks (Java's `clockManager()`, `connection.clockManager()`), which `Minecraft::tick` borrows from the player's connection.
- **The world border's extents are an enum** (`BorderExtent`: `Static`, `Moving`), whose methods take the border's center and maximum size, which Java's inner classes read from their outer instance. A border's listeners and `setDirty` are the server's, and left out.

## The level's animations

- **What a block's `animateTick` reaches of the game is a parameter**: its `Level` is a `LevelWithEffects`, the `ClientLevel` (which it derefs to) and the `LevelEffects` the game hands the level's animate tick: the particle engine and sound manager (`ParticleEngine`, `SoundManager`, traits the game's will implement; `NoParticles` and `NoSound` until then), the camera's position, the options' particles and weather radius, the player, the environment attributes (the game renderer's) and the block colours. The level's tick takes them too, for the rain's particles and sound (`tickWeatherEffects`, a method of `LevelWithEffects`). `addParticle`, `addAlwaysVisibleParticle`, `playLocalSound` and `playPlayerSound` are its methods, ClientLevel's code.
- **`Level.random` is the level's, in a `RefCell`** (`get_random()`), since the blocks draw from it through the shared level as well as the level itself: borrow it for one draw at a time, never across a call that draws too.
- **A class's `animateTick` is a `BlockClass` field** (`animate_tick`), looked up the chain like the shapes; an override calling `super` calls `Block::super_animate_tick` with its own class. What its constructor takes for its particles (a torch's flame, a campfire's sparks, leaves' particle, chance and sound, an eyeblossom's type) is its block's fields; leaves keep theirs in one struct down their chain (`LeavesBlockFields`), each constructor setting its own.
- **`ParticleOptions` is an enum** of the options classes ported (simple types, block, colour, dust, dust transition), and a type is its id in `BuiltInRegistries.PARTICLE_TYPE` (`ParticleType`), `Copy` like a `Block`. A `SoundEvent` is its location's text and its range; a sound instance keeps its random as the seed of its `RandomSource.create(seed)`.

## Block models

- **JSON is Gson's tree.** Models and block states are read strictly, like `GsonHelper.fromJson` and `StrictJsonParser` read them, into `com::google::gson`'s `JsonElement` ("Gson" above). A number keeps its text, Gson's `LazilyParsedNumber`, and a getter parses it into the type it's asked for: a float is `Float.parseFloat` of the text, correctly rounded straight to a float, not a double narrowed. An object keeps its members in the file's order, a repeated name replacing the value in its place, like Gson's `LinkedTreeMap`. `JsonParser::parse_strict` is `StrictJsonParser.parse` with the exception as a string, which the readers pass on, and `GsonHelper`'s getters return `Result`s whose `Err` is Java's `JsonSyntaxException`.
- **DataFixerUpper's codecs** (`BlockStateModelDispatcher.CODEC`, `Variant.MAP_CODEC`, `Material.CODEC`, `Condition.CODEC`) are decoded by hand from that tree, the way they read it through `JsonOps`: `Codec.INT` takes a number's `intValue()` or a boolean as 1 or 0, `Codec.BOOL` a boolean or a number's byte, `Codec.STRING` only a string; `either` tries its first codec, then its second; a map codec leaves other fields alone; `optionalFieldOf` fails on a field that's there but doesn't decode.
- **Model states** are the 48 `BlockModelRotation`s and their uv-locked states, statics handed out as `&'static dyn ModelState`, which the bakery's caches key by address (`ModelState::key`) like Java's maps key them by reference.
- **The shared transformations, settled.** Java's `MatrixUtil.isIdentity` adds the properties it works out to the matrix it's asked about, which a shared matrix's every holder then sees, and later JOML calls take shortcuts on. For block models that's `BlockModelRotation`'s own transformation, which its constructor asks about (through `BlockMath.getFaceTransformation`) and owns here too, and its inverse face matrices, which only `FaceBakery` reads, asking `isIdentity` before anything else reads them. The properties only depend on the matrix, and asking again adds nothing, so `BlockModelRotation::new` asks once and they're read-only after: every holder sees them the way Java's do from their first bake on. `FaceBakery` asks about a copy. `getFaceTransformation` takes its transformation by `&mut` and hands back a clone of it where Java hands back the object. Holders of other shared transformations (`PoseStack.mulPose`, the block entities' statics) get settled the same way when they come.
- **The bake** runs on one thread. `ModelDiscovery`'s models are `Arc`s that keep their parent and cache what they inherit in `OnceLock`s (Java's slots), `ModelBaker.compute` caches an operation by its key's address, and baked models are `Arc<dyn BlockStateModel>`, told apart with `as_any`. A quad's `MaterialInfo` holds its sprite as an `Arc<TextureAtlasSprite>`, which the atlas's `Preparations` hands out, and the interner shares equal infos (the sprite by address). Item models, item transforms (`display`) and `builtin/generated` aren't ported; models read past `display`.

## Meshing

- **What the renderer reads of a state** (`getShadeBrightness`, `getRenderShape`, `skipRendering`, `getSeed`, the offset function with `getMaxHorizontalOffset` and `getMaxVerticalOffset`) comes from `BlockClass` overrides like the shapes, and `isLightPermeable`, `isSolidRender` and the occlusion shapes by face from `initCache`'s cache (below).
- **The level comes through traits.** `BlockAndLightGetter::get_brightness` and `BlockAndTintGetter::cardinal_lighting` are what the renderer reads of a level's light and dimension; Java's `getBrightness` asks the light engine (`get_light_engine`), which is the client's (`ClientLevel`'s chunk source's), and a test level may answer it itself with `LevelLightEngine::empty()` as its engine, like Java's `LevelLightEngine.EMPTY`. `getBlockTint` comes with the biomes' colours (`BiomeColors`, the world track's), and so does `BlockColors.createDefault`: until then `BlockColors` holds no tint sources and blocks draw untinted.
- `BlockModelLighter` drops Java's per-thread cache of the last 100 positions' light and shade, and `Block.shouldRenderFace` its cache of shape pairs: both only save work while a section compiles, over a level that doesn't change meanwhile. `LeavesBlock`'s `cutoutLeaves` is a static, like Java's.
- `ModelBlockRenderer` borrows its `BlockColors`, and its random source is a `SingleThreadedRandomSource` reseeded with each block's seed, Java's `createThreadLocalInstance(0)`.
- **Compiling a section** reads a `RenderSectionRegion`: copies of the 27 sections' block states, shared through the `RenderRegionCache` as `Arc<SectionCopy>`s, and of what the compile reads of the level, made with the task, since the compile runs on a worker thread and the port's level isn't shared between threads: the sections' light as the engine's visible layers show it (`SectionLight`, from each storage's `getLightValue`: the layer, the bottom of the next one up below a column's top, or a value everywhere), their biomes with the zoom and the blend radius (tints worked out as `calculateBlockTint` does), and the level's cached tints of the column, which the compile reads and adds to like Java's shared `BlockTintCache` and gives back with its mesh unless the chunk's tints were dropped since. Java's worker reads the level as it is then; a copy made when the task is made is what a task run at once would read, and every visible section dirtied after its copy is compiled again. A test that stands in for the level with a `&dyn BlockAndTintGetter` answering light and tints itself makes a region over it (`RenderSectionRegion::over`). `SectionCompiler`'s started layers are builders over the `SectionBufferBuilderPack`'s buffers, borrowed all at once (`buffers_mut`), and dropped before the translucent layer's quads are sorted into its buffer again. A `VisibilitySet`'s `BitSet` of 36 bits is a `u64`, all of whose bits `setAll` sets, like Java's one word.

## Light

- **The engines are Java's classes, with the chunk source as a parameter.** `LevelLightEngine` holds a `BlockLightEngine` and a `SkyLightEngine`; each holds a `LightEngine<S>` (the abstract class: its queues and its storage) and derefs to it, and the abstract methods (`checkNode`, `propagateIncrease`, `propagateDecrease`) are `LightEngineClass`, which `light_engine::run_light_updates` takes. Storages are the same: `LayerLightSectionStorage<M>` with `LayerLightSectionStorageClass` for `getLightValue`, `onNodeAdded`, `onNodeRemoved` and `createDataLayer`, and the methods that call those as functions of its module (`update_section_status`, `mark_new_inconsistencies`). The `LightChunkGetter` an engine holds in Java (the chunk source, a back-reference) is a parameter of what reads chunks (`run_light_updates`, `set_light_enabled`), and the client's chunk cache hands out its engine with its storage as that getter (`get_light_engine_mut`).
- **Layers are shared like Java's objects.** A `DataLayer` in the maps and the queue is an `Rc<RefCell<DataLayer>>`: the visible map is a copy of the updating one sharing its layers, a layer is copied before its first write since the last swap (`changedSections`), a queued layer put in the map is the same object, and `markNewInconsistencies` compares them by reference (`Rc::ptr_eq`). What the game reads (`getDataLayerData`) is a copy.
- **What a light engine iterates is fastutil's order where it shows**: `blockNodesToCheck` is the ported `LongOpenHashSet` (`it::unimi::dsi::fastutil::longs`), whose table's order decides the queues' and so how many entries a run takes. The other sets and maps are std's or sorted: only `markNewInconsistencies` iterates them, whose loops come out the same in any order, and `onLightUpdate`, which the renderer hears in any order.
- **A state's light comes from its class like its fluid**: `initCache` keeps `useShapeForLightOcclusion`, the occlusion shape with its faces and `isSolidRender`, `propagatesSkylightDown` and `getLightDampening`, with the collision shape's `Cache` (`isFaceSturdy` for each support type, `isCollisionShapeFullBlock`, `hasLargeCollisionShape`) and `isSolid`, from `BlockClass` overrides (`use_shape_for_light_occlusion`, `propagates_skylight_down`, `get_light_dampening`) and the class's shapes. The fluid and random ticking are worked out with the registry's table; the shapes' part (`StateShapes`) the first time a state's is asked for, in a `OnceLock`, since the shapes read other blocks' states, which Java's `initCache` can because it runs once every block is registered. The values are the same: a state's shapes never change, and none of them reads another state's cache.
- **Light updates are closures of the level.** Java queues `Runnable`s that close over the packet listener; all they touch is the level, so `ClientLevel::queue_light_update` takes a `Box<dyn FnOnce(&mut ClientLevel)>`, and the handlers' light code (`applyLightData`, `enableChunkLight`, `queueLightRemoval`) is the listener's associated functions of the level.

## Biomes and tints

- **A registry holds its elements' values where they're ported**: a `Registry` of a class the port has keeps its values in id order (`RegistryValues`, an enum of `Arc<Vec<T>>`, one variant per class), and `value::<Biome>(holder)` is `Holder.value()`. Java's registries compare by reference; two of these are equal when they share their values. A level keeps a copy of the biome registry, the synchronized one the login handed it, and its dimension type's value (`dimensionType()`).
- **The synchronized registries load like `RegistryDataLoader`'s network path**: `RegistryDataCollector` hands the server's entries to `RegistryDataLoader::load`, which decodes each element with its class's codec (`Biome.NETWORK_CODEC`, `DimensionType.NETWORK_CODEC`, `DamageType.DIRECT_CODEC`, `ChatType.DIRECT_CODEC`, `PaintingVariant.DIRECT_CODEC`, `WolfVariant.NETWORK_CODEC`) from the NBT the server sent, or from the known pack's JSON (the vanilla pack's `data/`), with registry ops whose context is the static registries and the synchronized ones being loaded (`RegistryOps::create_loading`). A registry whose class isn't ported is its keys. The holder codecs (`RegistryFixedCodec`, `HolderSetCodec`) find a registry through `DynamicOps::as_registry_ops` (Java's `instanceof RegistryOps`) and its `HolderGetter`: a frozen registry's elements, or a registry being loaded, which hands out a holder for any key. Tags aren't ported (`update_tags`): a tag is a named set of its key (`HolderSet::Named`), in any registry, where Java fails a load on a tag the server didn't send (`Unbound tags`) or a static registry lacks (`Missing tag`).
- **An element whose class isn't ported fully decodes what's ported**: `EnvironmentAttributeMap.NETWORK_CODEC` (a biome's and a dimension type's `attributes`) is a codec over the render track's `from_json`, its input converted to JSON (`convertTo`), which reads every value the attribute types take the same from NBT. The int providers the port has are constants and uniform ranges; the other six types fail to decode saying so (`map_codec::unported`).
- **A constructor that throws while a codec decodes** (`DimensionType`'s checks, inside `ExtraCodecs.catchDecoderException`) panics with Java's message, which the codec catches (`catch_unwind`) into Java's error.
- **A `ColorResolver` is a named function in a static**, `BiomeColors`' four, which a level tells apart by reference (`ColorResolver::same`, Java's identity map of tint caches), and `getBlockTint` takes a `&'static ColorResolver`.
- **The tint caches are the game thread's**: `BlockTintCache` keeps Java's chunks (the 256 latest, oldest out first), layers and latest chunk in cells, without the locks and thread-locals the section compile threads need; its source, Java's function of the level, is a parameter of `get_color`.
- **The colormaps are statics the reload sets**, like Java's (`GrassColor.init`), behind a lock; `GrassColorReloadListener` and the others read them through `LegacyStuffWrapper.getPixels` (`NativeImage.read` and `makePixelArray`).
- **A level's back-references are parameters of what reads them**: `BiomeManager` takes the level (its `BiomeResolver`) in `get_biome`, and the blend radius, which Java's level reads from the game's options, is the level's (`set_biome_blend_radius`, set on login).
- `Biome.BIOME_INFO_NOISE` is a `SimplexNoise` of a `WorldgenRandom` over a `LegacyRandomSource`, whose bits `WorldgenRandom` draws from the legacy source, so the port makes the noise from the legacy source itself.

## Native libraries and the renderer

The game renders through native libraries that LWJGL binds: shaderc compiles its GLSL to SPIR-V, SPIRV-Cross translates that to the GLSL the OpenGL backend hands the driver, and SDL3 opens the window and the GL context. The port calls the very same builds, so the shader text the driver gets is vanilla's, byte for byte.

- `org::lwjgl::system::shared_library_loader` is LWJGL's `SharedLibraryLoader`: a binding names its module and library (`functions!("sdl", "SDL3"; …)`), `Platform` maps the name (`libSDL3.so`, `libSDL3.dylib`) and its path in a natives jar (`macos/arm64/org/lwjgl/sdl/libSDL3.dylib`, `mapLibraryPathBundled`), and the loader finds that path in the first of the module's natives jars on vanilla's classpath that has it, as the class loader does (`vanilla/<version>/classpath.txt` lists `lwjgl-sdl-3.4.3-natives-linux.jar` on Linux, and both `-natives-macos.jar` and `-natives-macos-arm64.jar` on a Mac). It reads the library out of the zip (its entries are deflated, read with `miniz_oxide`), writes it to `target/natives/` unless the file there has the entry's size and CRC-32, and opens it with `libloading`. `setup_vanilla.py --natives macos-arm64` also fetches another platform's jars and lists them in `classpath-macos-arm64.txt`, where the loader's tests check what a Mac would find. Nothing from `vanilla/` or `target/` is committed.
- Each LWJGL class is a unit struct with the C functions as associated functions under their C names (`Shaderc::shaderc_compile_into_spv`, `Spvc::spvc_compiler_compile`, `SDLVideo::SDL_CreateWindow`), looked up once from the library by `shared_library_loader::functions!`. Where LWJGL returns through a `PointerBuffer`, the Rust function returns the value with the result code. Functions taking the library's raw handles are `pub(crate)`: passing one the library didn't make, or one it released, is undefined behaviour, which the callers (`GlslCompiler`, `SPIRVModule`, `GlPipelineRecompiler`, the GL backend) keep to.
- SDL3 is LWJGL's own `libSDL3.so` (SDL 3.4.14) rather than the `sdl3` crate: it's the build vanilla runs, it needs no C toolchain or system SDL3 (which Ubuntu's archive doesn't have) to build, and it loads like shaderc and SPIRV-Cross. OpenGL's functions come from `SDL_GL_GetProcAddress` through `glow`, after `SDL_GL_LoadLibrary` of the library LWJGL loads (`libGL.so.1` on Linux, `/System/Library/Frameworks/OpenGL.framework/Versions/Current/OpenGL` on macOS). `glClipControl`, which glow doesn't bind, is looked up the same way.
- Callbacks a C library calls (shaderc's include resolver) are `extern "C"` functions whose user data points at what Java's lambda closes over, which lives until the call returns. Include results live as long as their `ShaderSource`, like Java's, so the release callback does nothing.

- stb (images) is LWJGL's JNI library, `liblwjgl_stb.so`, with stb compiled in: its exports are the JNI entry points Java calls (`Java_org_lwjgl_stb_STBImage_nstbi_1load_1from_1memory__JIJJJI`), which take the JNI environment and class first and pointers as `jlong`s. LWJGL's generated code never reads the environment or class, so the port passes null for both. stb allocates through function pointers `LibSTB.setupMalloc` hands it, which the port points at the C library's allocator (Java's is jemalloc), freeing what stb returns through `stbi_image_free`.

Resources:

- A pack hands out `IoSupplier.create(path)`s, which the port reads whole. `Resource` finds its `.mcmeta` when the resource is found, and parses it when it's first asked for, where Java finds it then too.
- `.mcmeta` sections and atlas definitions are DataFixerUpper codecs over Gson's JSON in Java. Until those are ported, they're decoded by hand from serde_json's values, field by field as the codecs read them, with their defaults. A float field is serde_json's double narrowed to a float, where Gson parses the float from the text; the two only differ for a float that rounds differently through a double, which no vanilla file has, and block models (whose coordinates are floats) need the exact path when they come.
- An atlas definition's sources are an enum of the kinds ported (`directory`, `single`). A sprite source's output and `SpriteLoader`'s regions are Java `HashMap`s whose order only decides the order sprites are loaded and drawn in, into places that don't overlap, so the port keeps them sorted, or in the stitcher's order.
- `SpriteContents.originalImage` is `byMipLevel[0]`, the same object in Java, so the port keeps only the levels. The device objects an atlas makes (its texture and views, an animation's frame textures, `AnimationState`) are `TextureAtlas`'s, which owns them.
- `listResources`' `TreeMap`s are `BTreeMap`s of identifiers, which `Ord` orders like Java's `compareTo`. Packs' filter and overlay sections come with the pack repository: the vanilla pack has neither.

Renderpearl keeps vanilla's split: `com::mojang::renderpearl::api` is what the game calls (`GpuBackend`, `GpuDevice`, `CommandEncoder`, `RenderPass`, `GpuTexture`, `GpuBuffer`, `GpuSurface` as traits; `RenderPipeline` and its state as data), `frontend` turns pipelines into what a backend needs (`GlslCompiler`, `SPIRVModule`, `PipelineBuilder`), and `backend::opengl` is the OpenGL backend. Game code only sees `api`, so a Vulkan or Metal backend can come later without touching it.

- An interface the backends implement is a trait, and a backend casts what the API hands it back to its own type (`(GlTexture) texture`) through `as_any()` and `downcast_ref`. An interface's constants are its module's (`gpu_texture::USAGE_COPY_DST`), since a trait with constants can't be a `dyn`.
- Java's `GpuDevice` and `CommandEncoder` are the frontend's `FrontendGpuDevice` and `FrontendCommandEncoder`, which check each call before the backend runs it. Until they're ported, the backend's device and encoder implement the API's traits themselves, with the frontend's checks: the GL encoder makes each render pass a `FrontendRenderPass` (the API's `RenderPass`, binding uniforms by name) around its `GlRenderPass` (the backend's `RenderPassBackend`, by index), and the device's `compile_pipeline` is `GpuDeviceBackend.compilePipeline` with the pending pipeline finished at once.
- A backend object the frontend hands back to the backend (`BackendRenderPipeline`) is an `Rc<dyn Trait>` whose trait is `Any`, so the backend gets its `Rc` back with `downcast` (`(GlRenderPipeline) pipeline`), and compares it by reference with `Rc::ptr_eq` where Java compares references (`lastPipeline`). A uniform's value, Java's `Object` (a `GpuBufferSlice` or a `TextureViewAndSampler`), is `UniformValue`.
- Native memory a builder hands out views of (`ByteBufferBuilder.Result`, `MeshData`'s buffers) is copied out when it's built, and the result freed at once, as a caller that closes it before writing more does. Memory Java leaves uninitialised (malloc'd padding, `Std140Builder`'s skipped bytes) is zero, which no shader reads. Buffers are little-endian like LWJGL's native ones on x86.
- OpenGL runs on the thread its context is current on, so the GL backend shares its `glow::Context` with `Rc`, and its textures and buffers delete their GL names when they're dropped (Java's `close()`).
- A copy's callback runs when the encoder submits, after `glFinish`: Java queues it as a fenced task that `RenderSystem` runs once the fence signals.
- `SpvModule`'s reflection is data holding the SPIR-V words' offsets, and its setters take the module (`descriptor.set_binding(module, binding)`), where Java's objects write into the module's buffer themselves. What Java asks SPIRV-Cross on demand (decorations, types) is asked once, when the module is reflected.
- `RenderPipelines`' pipelines take sort keys in the order they're built, so they're the fields of one struct built on first use in Java's order (`RenderPipelines::get()`). Snippets take none, so each is a static. A pipeline's bind group layouts are a hash set in Java whose order changes from run to run (its records hash `UniformType`'s constants by identity), which nothing the game draws depends on, so they're a `Vec` without repeats.
- Java's hash collections whose order shows are the ported ones: `PIPELINES_BY_LOCATION` is a `java::util::hash_map::HashMap`, and the enabled GL extensions, which `DeviceInfo` lists and the game logs, a `java::util::hash_set::HashSet`.

Vulkan (`backend::vulkan`, vanilla's Vulkan backend):

- **Vulkan is `ash`**, loaded through SDL like the rest: `SDL_Vulkan_LoadLibrary` of the loader LWJGL loads (`libvulkan.so.1`; on macOS the MoltenVK in `lwjgl-vulkan`'s natives jar), and `ash::Entry::from_static_fn` over SDL's `vkGetInstanceProcAddr`, the one Java checks LWJGL's against. An extension's functions are `ash`'s loader for it (`khr::push_descriptor::Device`), which Java's LWJGL classes (`KHRPushDescriptor`) are. The features' pNext chains are raw memory like Java's (`VulkanPNextStruct`, `VulkanFeature` at a member's offset in `ash`'s struct).
- **VMA is LWJGL's `liblwjgl_vma`**, called through its JNI entry points like stb (`org::lwjgl::util::vma`), with the functions `VmaVulkanFunctions.set` hands it, so images and buffers land in the memory VMA picks for vanilla. Its structs are LWJGL's layouts, checked by their sizes.
- **The device is an `Rc<VulkanDevice>`**, which implements the API's `GpuDevice` (Java's `GpuDeviceBackend`) and which every texture, buffer, sampler and pipeline holds: dropping one is Java's `close()`, which queues its destruction on the encoder's `DestructionQueue` for two submits later. The encoder holds the device weakly; it's made last, as Java's constructor makes it.
- **A texture view's `VkImageView` is the texture's.** The API's views are values here (`GpuTextureView`), so a texture keeps an image view for each range of mip levels a pass or descriptor asks for, made on first use and destroyed with it.
- **A copy's callback** runs when the destruction queue comes round to its submit, as Java's does: two submits on. `Screenshot` submits until it has (once on GL, whose submit waits for the GPU only when a callback is waiting).
- **Only what the port's frame calls of the transient memory is ported**: staging, which new buffers' data, buffer writes and texture writes come from (`VulkanTransientMemory`, `TransientBlockAllocator`); the API's `TransientMemory` isn't ported, since the port makes buffers of its own each frame. A frame submits each time round, after the window's blit and before its present, as `Minecraft.renderFrame` does.

## The frame

- **The device lives as long as the game**, like Java's `RenderSystem` device: the client leaks the `Box<dyn GpuDevice>` it makes into a `&'static dyn GpuDevice`, which the game renderer holds and lends. `RenderSystem`'s other statics, the uniforms a pass binds by default (`bindDefaultUniforms`: the projection, the fog, the global settings, the lights) and the model view stack, are the render thread's (`thread_local!`), the only thread that touches them.
- **The game renderer owns what Java's `Minecraft` shares with it**: the level renderer (`Minecraft.levelRenderer`), the block atlas and the baked block models (`AtlasManager`, `ModelManager`), and the level's environment attributes (`level.environmentAttributes()`) until the level holds them. The level, the player and the listener's clocks are parameters of its tick and frame. The parts of `LevelExtractor` that pick the visible sections and the dirty ones are the level renderer's (`extract_sections`).
- **Render sections are their index in the view area's storage** (`RotatingSectionStorage`), which the occlusion graph's nodes, its octree's leaves and the visible sections are lists of. The graph's full walk runs when it's asked for instead of on a background thread. Sections compile like vanilla's: `compileSections` queues a task for each dirty visible section after the frame's draws (`compileAsync`), or compiles it on the render thread when the options put it first (`compileSync`, `prioritizeChunkUpdates`), and worker threads take the queue's pick (`SectionTaskDynamicQueue`), a newer task for a section cancelling the older. Java's workers stage their meshes in the uber buffers themselves, under `copyLock`; the port's hand them to the render thread, which puts them in at the upload in the order they finished, so only the meshes' places in the heaps depend on the threads' timing, never what a frame draws or in what order. A screenshot waits for an empty queue, no compile running and no mesh waiting (`hasRenderedAllSections`).
- **GPU buffers Java writes into rings** (`DynamicGpuData`'s transforms and chunk sections, the fog's and the lightmap's `MappableRingBuffer`s, the indirect commands) are buffers each frame makes with the same bytes. The uber buffers a layer's sections share are Java's: `UberGpuBuffer`'s heaps (128 MiB of vertices, 32 MiB of indices), each with its `TlsfAllocator`, a mesh's bytes written into the first heap with room at the next upload, so a mesh coming or going writes only its own bytes. Java copies them through a `StagingBuffer`; the port writes them straight into the heap (`writeToBuffer`), which leaves the heap holding the same bytes. Java's staged allocations iterate in an order its identity hashes decide, which only decides where they go in the heaps; the port uploads them in the order they were staged, and the multi-draws read the same vertices and indices wherever they are, which changes no pixel. Java frees a mesh's allocations when its section lets go of it; the dispatcher keeps each mesh it uploaded and frees the ones nothing else holds at the next upload.

## Where Java and Rust disagree on numbers

The golden tests caught each of these, or exist to catch them.

- **Overflow.** Java ints and longs wrap; Rust panics in debug builds, so use `wrapping_*`. The port's tests run unoptimized with overflow checks, so a wrap you missed panics instead of passing.
- **Widen where Java widens.** In `Mth.getSeed`, `x * 3129871` is an int multiply that wraps *before* the result widens to long.
- **`>>>`** is a cast to unsigned, a shift and a cast back. `>>` is an arithmetic shift in both languages.
- **`Math.min` / `Math.max` on floats:** a NaN wins and -0.0 is less than 0.0. Rust's `f32::min` returns the operand that isn't NaN, so use `Math::min_f32`.
- **`Math.floorDiv` / `Math.floorMod`** round toward negative infinity, so use `Math::floor_div_i32`. `div_euclid` gives different answers for negative divisors.
- **`Math.abs(Integer.MIN_VALUE)`** wraps, so use `Math::abs_i32`.
- **`clamp`:** Rust's `i32::clamp` panics when min > max and Java's doesn't. Write `max(min).min(max)`.
- **NaN bits:** `Float.floatToIntBits` turns every NaN into the canonical one. `floatToRawIntBits` is `to_bits`.
- **Strings** are UTF-16. `String.hashCode` runs over UTF-16 units (`JavaString::hash_code`), and lengths and indices count UTF-16 units too. `String.compareTo` returns the difference of the first units that differ, or of the lengths (`JavaString::compare_to`), not just its sign, and beyond the BMP its order isn't code point order. A `char` is a `u16`, since a Rust `char` can't hold half of a surrogate pair (`Identifier.bySeparator` can be asked to split at one).
- **Modified UTF-8** (`DataInput.readUTF`, NBT's strings) can decode to a lone surrogate, which Java's strings hold and Rust's can't: the port reads one as U+FFFD. The golden files can't hold one either (they're UTF-8), so that isn't checked, and the harness keeps encoded surrogates out of what it reads unless they come in pairs.
- **Decoding UTF-8** goes through `string::from_bytes_utf8`, the JDK's own decoder (`new String(bytes, UTF_8)`, which Netty's `ByteBuf.toString` runs). It replaces malformed input with U+FFFD differently from `String::from_utf8_lossy`: an encoded surrogate (`ED A0 80`) is one replacement, not three, and so is one cut short at the end (`ED A0`). Encoding a Rust string is its own bytes: Java writes a lone surrogate as `?`, and a Rust string can't hold one.
- **`byte[]`** is `Vec<i8>` or `&[i8]`, so reading an element sign-extends like Java's.
- **`new T[size]`** throws `NegativeArraySizeException` for a negative size. Check it before `vec![…; size as usize]`, which would try to allocate.
- **Shift amounts.** Java masks an int's shift to 5 bits and a long's to 6, and Rust's `<<` panics past the width, so a shift that can reach it is `wrapping_shl` (`VarInt.read`'s sixth byte shifts by 35, which is 3).
- **Same in both:** `(int)` casts from floating point (they saturate, and NaN becomes 0, like `as`), and float `%` (fmod).
- **Transcendental functions.**
  - On x86-64, HotSpot computes `Math.sin/cos/tan/log/log10/exp/pow` (and `tanh`, `cbrt`) with its own assembly, based on Intel's libm. The interpreter and both JITs call the same stubs. Functions without that (`asin`, `acos`, `atan2`, `hypot`, …) fall back to `StrictMath`, which runs the JDK's Java port of fdlibm, ported in `src/java/lang/fd_libm.rs`. The `libm` crate is no substitute: it ports musl, whose `atan2` differs from fdlibm's on one in eight random inputs. Nor is std's `f64::hypot` (glibc's), which gets 249 of the 8,253 `Math.hypot` goldens wrong.
  - glibc and fdlibm differ from the HotSpot routines in the last bit on some inputs. Vanilla itself gives different results on ARM.
  - Every call goes through `java::lang::Math`. `sin`, `cos`, `tan`, `log` and `pow` run ports of HotSpot's stubs (`src/java/lang/math/hotspot_x86/`). Port the others the same way when the game first calls them.
  - HotSpot's `log` and `pow` pick a table entry with `rcpps`, an approximate reciprocal that Intel and AMD implement differently, so `Math.log` and `Math.pow` can differ in the last bit between CPUs. The port runs the same instruction and matches vanilla on the machine both run on; a correctly rounded reciprocal instead puts 17 in 10 million results one ulp off. Only compare vanilla's outputs with the port's from the same kind of CPU.
  - On ARM (an Apple Silicon Mac), the JDK's HotSpot (25, the toolchain's commit) has stubs of its own only for `sin` and `cos` (`macroAssembler_aarch64_trig.cpp`), and computes `tan`, `log`, `log10`, `pow` and `exp` with its C translations of fdlibm (`sharedRuntimeTrig.cpp`, `sharedRuntimeTrans.cpp`), `StrictMath`'s answers. The port computes x86-64's everywhere (with a correctly rounded `rcpps`, which no x86 CPU gives, off x86), so on an ARM Mac it matches vanilla on an x86-64 machine, not vanilla on the same Mac, in the last bit of those functions. The game calls them rarely (`Mth`'s tables do its trigonometry); exact parity on an ARM Mac would need those stubs ported like x86's.
- **Vineflower and float literals.** Vineflower prints a double constant that fits in a float with an `F` suffix, so `long * 1.110223E-16F` reads as float math when the bytecode multiplies doubles. When an expression's type matters, read the bytecode: `vanilla/toolchain/jdk-25/bin/javap -c -p -cp vanilla/26.3/client.jar net.minecraft.util.Mth`.
- **A `for` loop's condition is evaluated each time round.** `for (int i = 0; i < random.nextInt(1) + 1; i++)` (beehives' drips, campfires' sparks) draws its bound twice for one pass, where a Rust range draws it once: write the loop as Java's (`while i < random.next_int_bounded(1) + 1`).
- **Mixed int and float arithmetic is float.** `pos.getY() + random.nextFloat()` adds as floats and widens after (an ender chest's particles); `pos.getY() + 0.5 + random.nextFloat()` adds as doubles. Read each expression's types before writing it.
- **Methods that never return.** Some vanilla methods never return on extreme inputs (`Mth.rotLerpRad` with a huge difference). Port them as they are; the golden suite keeps its inputs in range with `where()`.

## Optimizing

The port starts literal. An optimization is welcome as long as every golden test, trace, packet capture and screenshot still matches. The comparisons are the contract, not the shape of the code. These look free but change results:

- Fused multiply-add (`mul_add`), or reordering float additions and multiplications. Java rounds every operation in source order.
- Narrowing `f64` math to `f32`, or the reverse.
- Replacing a lookup table with the real function (`Mth.sin` is a 65536-entry table, not `sin`).
- SIMD reductions that sum in a different order.
- Iterating a `HashMap` where Java iterated a `LinkedHashMap`, or relying on any hash order. Java's order is deterministic, Rust's isn't.

These are free, and the benchmark (TESTING.md, "Benchmark") found them worth it:

- A map's hasher, where nothing iterates the map: std's SipHash costs more than the light engine's lookups themselves, so its layer maps hash with fastutil's `mix` (`hash_common::BuildMixHasher`), like Java's `Long2ObjectOpenHashMap`s.
- An index in place of a linear search, where the search only finds what the index finds: a registry's ids by key (`MappedRegistry`'s `toId`), which the tints ask 25 times a block.
- Borrowing a shared object where Java compares it by reference: `Shapes::block_ref()` and `BlockState::face_occlusion_shape` let `Block.shouldRenderFace` compare shapes without cloning their `Arc`s.
- Reading a copy's values once into an array, where nothing changes them meanwhile: a region's own section, which its compile reads most.
- Sharing a value Java interns: a `ResourceKey`'s names are an `Arc`, which a copy shares and a comparison checks first, and a key hashes a digest of its names made with it, so a biome's holder copied out of a palette or looked up in its registry copies and hashes no strings.
- Working out what a loop asks of each state once per palette value, where the answer is a function of the state: `ChunkSkyLightSources.fillFrom` reads each column through its sections' palettes' `EdgeFaces`, and asks `isEdgeOccluded` only where its shapes have to be joined.
- Borrowing the shared occlusion faces in the light engine, like the renderer's: `faceShapeOccludes` compares them with the block by reference.

Each needs the offline benchmark's mesh digest, or the goldens, to stay as they were.

## Porting a class

1. Read the Java in `vanilla/<version>/src/`.
2. Add the class to `oracle/golden/src/rustcraft/golden/Golden.java`: a `StaticSuite` for static methods, or a hand-written suite for stateful classes like `RandomSourceSuite`. Then run `python3 tools/golden.py`.
3. Port it, and end the file with its golden test: `golden.check(descriptor, function)` for each method, `golden.pending(name, reason)` for the rest, then `golden.finish()`.
4. Run `cargo test`. A mismatch prints the arguments, vanilla's answer and yours, with floats shown as bits and decimals.
