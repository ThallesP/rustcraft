# Testing against vanilla

The real game is the source of truth. Every check runs vanilla and the port on the same input and compares the outputs, from most precise to least:

| Layer | Vanilla side | Compared by |
| --- | --- | --- |
| 1. Function goldens | `oracle/golden/` calls real methods from `client.jar` | `cargo test` |
| 2. Tick traces | `oracle/client/` (a Fabric mod) records the player every tick of a scenario | `oracle-diff trace` |
| 3. Packets | `packet-proxy` records client ↔ vanilla server traffic | `oracle-diff packets` |
| 4. Screenshots | `oracle/client/` takes screenshots at scenario checkpoints | `oracle-diff image` |

Draw-call streams from the renderer (renderpearl) will become layer 5 once the port renders.

Everything vanilla produces lands in `vanilla/<version>/`, which is gitignored. `MINECRAFT_VERSION` pins the version.

## Commands

```sh
python3 tools/setup_vanilla.py                                    # once per version
python3 tools/golden.py && cargo test                             # layer 1
python3 tools/golden.py com.mojang.blaze3d.platform.NativeImage   # only these suites, keeping the other files
python3 tools/oracle_client.py run walk                           # layers 2 and 4, singleplayer
python3 tools/oracle_client.py capture walk --accept-eula         # layers 2–4 on a fresh vanilla server
python3 tools/oracle_client.py check-determinism walk --capture --accept-eula
python3 tools/port_client.py capture walk --accept-eula          # layer 3, the port on a fresh vanilla server
cargo run -p oracle-diff -- packets --join vanilla/26.3/oracle/walk/capture.jsonl target/oracle/walk/capture.jsonl
python3 tools/port_client.py check-join walk --accept-eula       # gate 1: the two lines above
python3 tools/port_client.py check-join walk --accept-eula --compression-threshold 256
python3 tools/oracle_client.py capture walk --accept-eula --ping  # the server list's ping, vanilla's
python3 tools/port_client.py capture walk --accept-eula --ping    # and the port's (rustcraft --ping)
cargo run -p oracle-diff -- packets vanilla/26.3/oracle/walk-ping/capture.jsonl target/oracle/walk-ping/capture.jsonl
cargo run -p oracle-diff -- dir vanilla/26.3/oracle/walk target/oracle/walk
python3 tools/port_client.py soak --preset normal --accept-eula   # the live client on a generated world (below)
python3 tools/port_client.py stall --accept-eula                  # the game thread stalled 40 s, still connected (below)
python3 tools/oracle_client.py capture walk --accept-eula --gl-profile macos --out vanilla/26.3/oracle-gl41   # a Mac's OpenGL (below)
python3 tools/port_client.py capture walk --accept-eula --gl-profile macos --out target/oracle-gl41
cargo run -p oracle-diff -- dir --strict vanilla/26.3/oracle-gl41/walk target/oracle-gl41/walk
python3 tools/oracle_client.py capture walk --accept-eula --backend vulkan --out vanilla/26.3/oracle-vulkan   # vanilla's Vulkan backend (below)
python3 tools/port_client.py capture walk --accept-eula --backend vulkan --out target/oracle-vulkan
cargo run -p oracle-diff -- dir --strict vanilla/26.3/oracle-vulkan/walk target/oracle-vulkan/walk
```

Wrap the ones that start a server, a client or the proxy in `flock /tmp/rustcraft-oracle.lock`: they use fixed ports, and the machine is shared.

`--accept-eula` accepts Mojang's EULA (https://aka.ms/MinecraftEULA) for the local server. Running a server requires it.

## Encoding rules

Shared by every file below:

- Floats are the lowercase hex of their raw IEEE 754 bits, as JSON strings: 8 digits for `float`/`f32`, 16 for `double`/`f64` (`1.0f` → `"3f800000"`). Comparisons are bit-exact, so `-0.0 != 0.0`. The one exception is that any NaN matches any NaN: NaN bits even differ between two runs of the golden generator, since the same operation can give NaNs of either sign depending on when HotSpot's JIT compiles it, which varies from run to run.
- `int`, `long`, `short` and `byte` are JSON numbers. A `char` is a number (its UTF-16 code unit). A `boolean` is a JSON bool.
- A `String` is a JSON string. Arrays and Java records are JSON arrays (records in component order). A `UUID` is `[most, least]`.
- Files are JSON Lines: one object per line.

## 1. Function goldens

`python3 tools/golden.py` compiles `oracle/golden/` against the client jar and writes one file per class to `vanilla/<version>/golden/<binary class name>.jsonl`, e.g. `net.minecraft.util.Mth.jsonl`.

The generator bootstraps the game first, like the game's own tests (`SharedConstants.tryDetectVersion()`, then `Bootstrap.bootStrap()`): some classes only load once the registries exist (`ConfigurationProtocols`, whose clientbound template holds the dialog packet), and some members need the game's version (`KnownPack.vanilla`). Bootstrapping changed no golden case, and it sends `System.out` to the log, so the generator prints its progress to the stream from before.

Static methods are covered by reflection. Every public static method whose parameter and return types have a generator (or that returns `void`) gets:
- edge cases (zeros, signed zeros, NaN, infinities, MIN/MAX, angles, powers of two, non-ASCII strings);
- 500 seeded random inputs;
- for `Mth.sin`/`cos`, every entry of their lookup table;
- for `Math.sin`/`cos`/`tan`/`log`/`pow`, which HotSpot computes with its own assembly, 20,000 more inputs each, spread over every path through it, since last-bit differences between libms are rare;
- for `Mth.atan2`, angles that read every entry of its tables;
- for `Math.hypot`, 6,000 more spread over every path through fdlibm's code, with its thresholds and the point where it switches formulas;
- for `MatrixUtil.eigenvalueJacobi` and `svdDecompose`, matrices like the ones `Transformation` decomposes, and ones where `approxGivensQuat` switches to a quarter turn. `eigenvalueJacobi` takes at most 1,024 steps (`where()`): billions would take minutes, and the game takes 5;
- for `Mth.rayIntersectsAABB`, the rays `AABB.clip` gets (below), as a start and a direction.

A random value is one of its generator's edges one time in eight, so edges also meet random partners, and otherwise a fresh one. The exception is an edge whose encoding is longer than 16,384 characters (`Values.MAX_DRAWN_EDGE`), which gets a fresh value instead. Those edges hold a string at a codec's limit of 32767 units, like a `KnownPack`'s parts, a brand or a property's value. The edges already cover each of them, and drawn at random they came back in most random lists and pairs: `ServerboundSelectKnownPacks`' file was 1.4 GB of them.

Arrays (`byte[]`, `int[]`, `long[]`) are JSON arrays of numbers, and each call gets its own copy, so `after` shows what a method wrote into one (`readBytes`, `readFixedSizeLongArray`). A `CharSequence` is a string, and a `Charset` is UTF-8, the only one the game's packets use, written as its name.

A `RandomSource` argument is a `LegacyRandomSource` seeded with the argument. Its next `nextLong()` after the call is recorded in `after` (one slot per argument), so how many values a method draws must match too. A static method taking it first is checked with `golden.check_random`; anything else (`Vec3.offsetRandom`) with `golden.check_mut`, to which `golden.rs` passes a `LegacyRandomSource` decoded from the seed and encoded as its next `nextLong()`. Any other argument a method wrote to gets its state afterwards in its slot (`MatrixUtil.checkProperty` adds to its matrix's properties). An empty slot means the argument didn't change, or is the returned object, which `result` already shows; the port's argument must then equal what it was or the result. A `void` method's result is null, so `after` is all it shows (`svdDecompose` writes its matrix's parts into four arguments). The port checks those with `golden.check_mut`, whose function takes every argument as `&mut`.

`Character.digit` is checked in radixes 10 and 16 on every char (`TextColor.parseColor` reads hex through `Integer.parseInt(…, 16)`). `java.lang.Float.toString` and `Double.toString` (the JDK's `FloatToDecimal` and `DoubleToDecimal`, which every `toString` printing a float goes through) get the edges and random values, and where their digits and format change: every exponent's smallest, middle and largest significands of either sign, each power of ten and an ulp either side, the plain and scientific forms' thresholds (1.0E-3, 1.0E7), the smallest subnormals, whole numbers, and 30,000 random values, half of them any bits and half in the game's magnitudes.

DataFixerUpper's `DataResult` has a program suite (`DataResultSuite`): 2,000 programs on results of ints, each made one of the six ways (`success` with or without a lifecycle, `error` with or without a partial value and a lifecycle) and run through ops (`map`, `flatMap`, `ap`, `apply2`, `apply2stable`, `apply3` with results made the same ways, `setPartial` both ways, `mapError`, `setLifecycle`, `addLifecycle`, `promotePartial`, `resultOrPartial`, `getOrThrow`, `getPartialOrThrow`, `mapOrElse`, `hasResultOrPartial`, `isSuccess`, `toString`), each step the op's output and the result afterwards, `["success", value, lifecycle]` or `["error", message, partial, lifecycle]`, a lifecycle `"Stable"`, `"Experimental"` or `["Deprecated", since]`. The functions are fixed ones of ints (`x * 2 + 1`, `a * 3 + b`…), whose overflow wraps.

`NbtOps.INSTANCE` has a suite of its own (`NbtOpsSuite`): every method on `NbtValues`' tags (each kind's edges and 300 random ones), with results as `DfuValues` encodes them (`["success", value, lifecycle]` or `["error", message, [partial] or [], lifecycle]`, a number `[box, value]`); merging into lists and arrays with tags of their elements' kind half the time, so arrays stay arrays or become lists; merging into compounds, ends and other tags with string keys and others, from a `LinkedHashMap` and from `getMap` of a compound; `getMap`'s `MapLike` (its `toString`, entries and lookups by string and by tag); `convertTo` itself; and 300 programs each of the list and record builders' ops (`add` of tags, results and keys that aren't strings, `withErrorsFrom`, `setLifecycle`, `mapError`), then two builds, the second of what the first left.

DataFixerUpper's codecs have a suite on NBT (`DfuCodecSuite`, `com.mojang.serialization.Codec`): the primitive codecs and codecs made with each combinator the text components reach (`listOf` with and without sizes, `either`, `xmap`, `comapFlatMap`, `flatComapMap`, `flatXmap` and `validate` with errors and partial values, `withAlternative` both ways, `fieldOf`, `optionalFieldOf` and its lenient and defaulted forms, records of 1 to 5, 11 and 16 fields, a map codec's `stable`, `xmap` and `flatXmap`, `dispatch` and `partialDispatch` with types that fail both ways, and `recursive`), each named by how it's made, and the game's codecs other suites don't reach (`Identifier.CODEC`: the game's identifiers, whose mutations are mostly strings that aren't one). A codec named N gets `N.encode` cases (a value onto a prefix: the end mostly, compounds and any tags) and `N.decode` cases (the result a `DataResult` of `[value, rest]`): its own encodings of 150 random values, each with one tag inside replaced, removed or added, and any tags. Values are by shape: numbers by class, lists as arrays, an `Optional` as its value or null, an `Either` as `["left", v]` or `["right", v]`, a record as its fields.

Text components have a suite on NBT (`ComponentSuite`, `net.minecraft.network.chat.ComponentSerialization`): 1,500 random component trees (literals, translations of keys `en_us` has and doesn't, with and without fallbacks, and arguments of every kind a server sends, key bindings; every style field, the click events a server may send and `open_file`, which it may not, shown text, a font no codec writes), each given as a spec both sides build it from (the suite's javadoc has the format) and checked by `toString`, `getString` (through `en_us.json`) and `ComponentSerialization.CODEC`'s encoding; then 1,482 tags decoded, the result's component recorded as a spec: those encodings, a third of them with one tag inside replaced or removed, hand-made tags (plain strings, lists, compounds with a `type`, an empty `extra`, colors out of range and misnamed, arguments that are primitives and compounds), and any tags. Contents and events not ported yet aren't made. The same suite runs `CODEC` on JSON: 600 components' encodings by `JsonOps` and the text `lenientJson`'s Gson writes of them, and 580 decodes of those encodings (some with a member replaced or removed) and of hand-made JSON parsed leniently (unquoted names, nulls as members and in a translation's arguments, which throw in Java and panic here, numbers past a long and NaN, which `BigDecimal` can't hold). Entity tooltips (`show_entity`) come only from hand-made tags: the UUID as four ints and as strings, valid and not, and entity types that aren't registered; Java prints their `EntityTooltipInfo` by identity, so random components don't hold one.

The packets holding components (`ClientboundDisconnectPacket`, `ClientboundSystemChatPacket`, `ClientboundServerDataPacket`, the title, subtitle and action bar texts, `ClientboundTabListPacket`) get `InstanceSuite.every` with a component generator (`PacketValues`: the suite's random components, encoded as specs). Their codecs read trusted NBT, which allocates what a random length says, so random buffers are kept to those whose tags read within the default quota (`NbtValues.readsLittleTags`). The walk capture's nine `system_chat` payloads and its `server_data` are decoded as extra inputs. So do `ClientboundResourcePackPushPacket` (UUIDs, URLs valid and not, hashes up to the 40 characters its constructor allows, an optional prompt: 7,004 cases), `ClientboundServerLinksPacket` (lists of links of each known kind or named by a component, valid and invalid URLs: 4,847; an `Either` is encoded like `DfuCodecSuite`'s, `["left", v]` or `["right", v]`, a component or an enum constant inside as one) and login's `ClientboundLoginDisconnectPacket`, whose reason is JSON text (`lenientJson` and `fromCodec(OPS, CODEC)` on JSON's ops), so its random buffers need no filter (4,902). Their constructors taking a list or an `Optional` are skipped (the harness's only `Optional` argument is a `Transformation`'s): the codec's cases make the packets. `ClientboundSetTitlesAnimationPacket` (5,201) and `ClientboundClearTitlesPacket` (3,318) are plain. With login's disconnect, every packet of `LoginProtocols.CLIENTBOUND` has a generator, so its codec is checked whole (`ProtocolSuite`).

The component suite also makes 500 trees holding every kind of contents a server sends unresolved, apart from the first batch so the packets' generator's components stay as they were: scores (their names selectors that parse, and names that don't, which the codec's `either` reads as plain names), selectors with separators, NBT (paths of every node, each data source: entities by selector, blocks by coordinates, the command storage; the flags), objects (atlas sprites; players' heads by name, id and whole profiles, with skin patches), and items shown on hover (each with a count and a component patch Java's codecs read); and hand-made tags of each, valid and not (selectors, paths and coordinates that don't parse, a path ending in `[`, which throws in Java and panics here, both flags on, a data source named by `source`, unknown and transient component types, air and unknown items, counts out of range). A tree showing a player's head has no `toString` case (Java prints the profile by identity), nor one showing an item with components (Java prints each value by its class; the port keeps the values as data). 9,814 cases.

The parsers those contents hold have suites of their own. `com.mojang.brigadier.StringReader` (`BrigadierSuites`): 2,997 programs of reads (numbers at each type's edges, quoted strings with good and bad escapes, booleans, symbols, every kind of whitespace) on strings of what commands hold, each op's output and the cursor after, or the error's message with its context; `Character.isWhitespace` on every char. `EntitySelectorParser` (`SelectorSuites`): 8,195 cases, `parse` of names, UUIDs and selectors (each option's values good and bad, each applicability rule, 3,000 random selectors and 1,500 mutations), with selectors allowed and not, recording what the parse leaves (the getters, and the name, UUID, type, distance, position, box and order through reflection) and the cursor, or the error; and `EntitySelector.COMPILABLE_CODEC`'s decode of each. `NbtPathArgument.parse` (1,110 cases): every kind of node (its class and what it holds, by reflection), wrong paths, random ones, and paths ending in `[`, which throw. `Items.NAMES` and `DataComponents.TYPES` are `BuiltInRegistries.ITEM`'s and `DATA_COMPONENT_TYPE`'s keys by id (with whether each type is transient).

Gson has suites of its own (`GsonSuites`). An element is `["null"]`, `["boolean", b]`, `["number", box, toString]` (the box's simple name: what the parser reads is a `LazilyParsedNumber`), `["string", s]`, `["array", [element, …]]` or `["object", [[name, element], …]]` in the object's order, and a parsed one nested deeper than 40 is `["deep", depth, toString]`, under serde_json's recursion limit. An exception is recorded as the case's class, then as `[class, message]` again under the method's name and " message", so messages are checked too: the port's `Err`, or what a getter panicked with (Java's `toString()` of the exception). The files can't hold a lone surrogate, so cases whose input, result or message has one (a `\ud800` escape, a mutation splitting a pair) are left out.
- `com.google.gson.JsonParser`: `parseString` and `StrictJsonParser.parse` of 3,029 inputs: valid JSON of every kind (numbers at int's, long's, float's and double's edges and past them, big integers, huge exponents and scales, every escape, non-BMP characters, repeated members), every lenient extension and what's just past it, malformed input of every kind, nesting around the limit of 255, tokens across the reader's 1024-unit buffer (after whitespace that fills it, and strings, numbers, literals and comments around its length), errors after newlines and non-BMP characters, 300 random documents, and 2,000 mutations of those inputs (one to three characters inserted, deleted or replaced).
- `com.google.gson.stream.JsonReader`: 2,898 programs, one in each strictness for the hand-written inputs, a third of the deep ones, a quarter of the buffer ones and 400 mutations, a tenth with a nesting limit of 0 to 3. Each peeks the next token and reads it its way, skips it a fifth of the time, reads a number or a string as a string, an int, a long or a double, and now and then reads it the wrong way or asks `hasNext` or `toString` in between. `args` are `[strictness, nestingLimit, input, ops]`, and a step is the op's output with `getPath` and `getPreviousPath` after it, the last `{"exception": class, "message": message}` when it threw.
- `com.google.gson.JsonElement`: `toString()` of 2,141 elements (what the parser read, every primitive below, strings of each character under 128 and U+2028, objects and arrays with nulls, 300 random trees of those), and `equals` of each with its copy, its members shuffled, one changed or removed, its elements reversed, and a random element, then 400 pairs of primitives.
- `com.google.gson.Gson`: `toJson` of the same elements by `lenientJson`'s Gson (`disableHtmlEscaping`) and a default one (HTML-safe), both dropping null members; a third of them by one that writes nulls after the non-execute prefix, and every primitive by a strict one, which refuses NaN and infinities.
- `com.google.gson.JsonPrimitive`: the getters, `hashCode`, `equals` with the primitives of the same text in other boxes and six random ones, and what `getAsBigDecimal()` hands out (`intValue`, `longValue`, `longValueExact`, `floatValue`, `doubleValue`, `scale`), on 589 primitives: booleans, every box at its edges with NaN and infinities, parsed numbers valid and not (10,001 digits, scales of 10,000), `BigDecimal`s, numeric and other strings (hex, type suffixes, whitespace, Unicode digits, exponents past an int), 120 random JSON numbers and 200 random strings of Java's number grammar.

`java.lang.String`'s suite is hand-written: `hashCode` of every edge and random string, `compareTo` of every pair of edges, random pairs, and strings against their prefixes and one-character extensions, and decoding UTF-8 (`<init>([BLjava/nio/charset/Charset;)V`, the charset always UTF-8): every byte and every pair of bytes, every 3-byte lead with every second byte and a third either side of the continuation range, every 4-byte lead (and the leads past U+10FFFF) with every second byte, cut short after the third or not, then 2,000 random byte strings that are mostly UTF-8's lead and continuation bytes, and the edge and random strings encoded.

`java.net.URI`'s suite is hand-written too (`UriSuite`): a text component's `open_url` click event holds a URI, which `ExtraCodecs.UNTRUSTED_URI` parses with `Util.parseAndValidateUntrustedUri`. Its 3,971 strings are edges (empty strings, `#` and `?` alone, http and https URLs, ports empty, past an int and of other digits, user info, IPv4 addresses with leading zeros and parts past 255, IPv6 addresses compressed or not, too long or too short, with IPv4 tails and scope ids, registry-based authorities, opaque URIs, relative references, escapes well-formed or not and decoding to malformed UTF-8), 54 special strings (spaces, `` <>"{}|\^` ``, controls, non-ASCII and non-BMP characters, broken escapes, delimiters) in each of 22 places, a space, `%` and `<` at every position of two URLs, 600 random URLs, 1,100 mutations of those and the edges, and 500 random strings. For each, `parse` is `new URI(s)`'s `[scheme, rawSchemeSpecificPart, rawAuthority, rawUserInfo, host, port, rawPath, rawQuery, rawFragment, toString, isAbsolute, isOpaque, [schemeSpecificPart, authority, userInfo, path, query, fragment]]` (1,796) or `parseError` the `URISyntaxException`'s message (2,175), and `Util.parseAndValidateUntrustedUri` is `["success", toString]` or `["error", message]`. A message holds the input with its spaces trimmed and the index, as `jdk.internal.util.Exceptions` writes them under the JDK's default `jdk.includeInExceptions`. The port checks `URI.create` on the same cases: the same URIs, or a panic with the message. `acceptsCharacter` is, for 17 places (a scheme's first character and the rest, an opaque part, paths, a query, a fragment, user info, an authority, a host, a port, a scope id, an IPv6 address), the ranges of chars outside the surrogates that parse there, which checks `Character.isSpaceChar` and `isISOControl` on all of them. `hashCode()I` has every parsed string (2,140), and `equals` and `compareTo` 751 pairs: pairs differing in the case of schemes, hosts, escapes and the rest, in an empty or missing port and in the kind of authority, both ways round, then random parsed strings against themselves, their case flipped, their escapes' case changed, mutations of them and other parsed strings. No input holds a lone surrogate, which the golden files' UTF-8 can't carry and a Rust string can't hold.

Stateful classes get hand-written suites, which run seeded random programs of ops and record a step per op. A program ends at the first op that throws, recorded as `{"throws": …}`:
- `RandomSourceSuite`: each op's output, for every `RandomSource` implementation.
- `PoseStackSuite`: `[output, pose, normal, trustedNormals]`, the op's output and the top pose afterwards (`trustedNormals` is read by reflection). One program in four draws any float, NaN included. The last 256 programs also multiply by transformations, whose output is the transformation afterwards: `mulPose` adds to its matrix's properties.
- `Matrix4fStackSuite`: the current matrix after each op, for stack sizes from 1 to 20 and a few the constructor rejects.
- `Matrix3x2fStackSuite`: the same for the GUI's pose stack, with the ops the client calls on it (push, pop, translate, scale, rotate).
- `ProjectionSuite`: `[output, zNear, zFar, fov, width, height, invertY, matrixVersion]`. `getMatrix` needs `RenderSystem`'s device, so the suite installs a stand-in (a `GpuDevice` proxy that only answers `getDeviceInfo`) whose `isZZeroToOne` is the case's `args[0]`.

Value types (JOML's, and the game's below) get an `InstanceSuite`, which covers the constructors and instance methods it lists the same way. A case calls one method on a fresh receiver, which is `args[0]`, and `after[0]` is the receiver's state afterwards. Any other argument the method wrote to gets its state in `after` too, unless it's the returned object, which `result` already shows. A constructor is an `<init>` case whose result is the new object, and a static method listed with them (a record's factories) gets cases without a receiver. `equals(Object)` takes another object of the same class. The port checks them with `golden.check_method`, which fails a case when vanilla recorded an `after` slot the check can't see, or `golden.check_mut` when the method also writes to another argument. A suite can add cases for a member (`extraInputs`, each a receiver followed by the arguments), and write the class's public constants like a static suite (`withFields`).

JOML objects are encoded as their fields in declaration order: a `Vector2f` is `[x, y]`, a `Vector3f` `[x, y, z]`, a `Vector4f` and a `Quaternionf` `[x, y, z, w]`, a `Matrix3x2f` (or `Matrix3x2fStack`) `[m00, m01, m10, m11, m20, m21]`, a `Matrix3f` `[m00, m01, …, m22]`, a `Matrix4f` (or `Matrix4fStack`) `[m00, m01, …, m33, properties]`, and a `FrustumIntersection` its 24 private plane components `[nxX, nxY, nxZ, nxW, pxX, …, pzW]` followed by its `planes`, an array of six `Vector4f` (read by reflection). An `Axis` is the name of its constant (`"XP"`). A `GivensParameters` is `[sinHalf, cosHalf]`, like any record. A `Transformation` is `[matrix, decomposed, translation, leftRotation, scale, rightRotation, identity]`: its fields (read by reflection), the four parts null until it's decomposed, then whether it's the `IDENTITY` constant, which the game compares with by reference. An `Optional` (only `Transformation.compose` takes one) is its value or null, and so is an argument a method lets be null (a `Transformation`'s missing part). Transformations are made the ways the game makes them (block entities' parts, block model rotations, entities' parts, and matrices of those parts), from any JOML matrix, or decomposed already. The receivers and arguments come from JOML itself (identities, translations, rotations, scales, the camera's projections, products of those, and matrices built from components, NaN and infinities included), so their properties are ones the game's matrices can have. 2D poses are the GUI's (pixel translations, GUI scales, a map decoration's rotation), and frustums are mostly the camera's culling frustums (`Camera.createProjectionMatrixForCulling` times the view rotation) looking anywhere.

The game's own value types get `InstanceSuite.every`, which covers every public constructor, method and constant the class declares, like a static suite does: a member whose arguments have no generator, or whose result has no encoder, is written as skipped, so the port has to mark it pending (the codecs, and `Direction.orderedByNearest`, which takes an `Entity`). An inherited method whose answer depends on the receiver's class is added with `inherited` (`Vec3i.toString` prints `BlockPos{…}` for a `BlockPos`), and so is one a class forwards to an object it holds (`PropertyMap`'s `Multimap` methods), and `where` drops inputs like a static suite's. A `Vec3i` is `[x, y, z]` (ints), and so are a `BlockPos` and a `MutableBlockPos`; a `Vec3` is `[x, y, z]` (doubles), a `Vec2` `[x, y]` (floats), and a JOML `Vector3i` `[x, y, z]` (ints). An enum constant is its name (`"NORTH"`), an `EnumSet` (`Vec3.align`'s axes) the names of its constants in order, and a collection, stream, iterator or iterable the array of its elements, each encoded by its own class as it comes (the first 512). `BlockPos`'s iterables hand out one `MutableBlockPos` they move, so each element is encoded before the next is asked for. When working out an element throws (`randomBetweenClosed` drawing from an empty box), the call counts as throwing, so the port collects the elements inside the checked call. A `Position` argument is a `Vec3`, and an argument a method lets be null (`Direction.getNearest`'s fallback) gets null among its extra inputs. When every argument is an enum, the edges are every combination already, so there are no random cases.

An `AABB` is `[minX, minY, minZ, maxX, maxY, maxZ]` (doubles), an `AABB.Builder` its private fields `[minX, minY, minZ, maxX, maxY, maxZ, defined]` (floats and a boolean), and a `BlockHitResult` `[location, direction, blockPos, miss, inside, worldBorderHit]`, `HitResult`'s field first. A `BlockHitResult` is also the receiver of `HitResult`'s methods, since entities aren't ported. An `Optional` result is its value, encoded by its own class, or null. A parameter's generic type can pick its generator where the raw class can't: a `List<AABB>` or `Iterable<AABB>` is a list of boxes (an array), like a block's shape from `VoxelShape.toAabbs`.

Their values are like the game's: blocks around the walk scenario's spawn at any height, steps and offsets, blocks anywhere inside the world border, and any ints; the walk scenario's spawn and its deltas, entities' deltas, look vectors, block corners and centers, and any doubles; rotations. Edges include NaNs of both signs: x86's own NaN (`0.0 / 0.0`) is negative, unlike Java's canonical one, and `hashCode` has to make them the same. The extra inputs go where results flip: points exactly as far apart as the distance a strict `<` checks them against (and an ulp either side), vectors whose length is `normalize`'s threshold (along an axis, where the length comes out exact), ties for `getNearest` and `axisStepOrder`, subnormal dot products for `getApproximateNearest`, `fromYRot`'s multiples of 45 degrees, every degree of `isFacingAngle`, and `BlockModelRotation`'s 48 matrices for `Direction.rotate`. `Float.floatToIntBits` and `Double.doubleToLongBits` get NaNs with other payloads.

`BlockPos`'s blocks also include the largest and smallest coordinates `asLong` packs (26 bits for x and z, 12 for y) and one past them, and its extra inputs go where its answers change: every block at those limits for `asLong`, blocks packed into longs for `of`, `getX(J)` and the rest, points on `clampLocationWithin`'s bounds and an ulp either side (its lower bound is a float sum, which rounds far out), Manhattan reaches up to 4 and negative ones, boxes up to 9 blocks across with their corners either way round, columns, every pair of directions for `spiralAround`, boxes walked along movements with zero, -0.0 and NaN components, and draws from small boxes, some empty. A Manhattan search with a negative reach and a large depth finds no block and runs until the depth wraps, so those inputs need every reach non-negative or a depth up to 64.

`AABB`'s boxes are whole blocks, blocks' shapes (`Block.box`'s sixteenths) at blocks, entities' boxes (the player standing, crouching and swimming, items, arrows, minecarts, with `EntityDimensions.makeBoundingBox`'s float half width) around the walk scenario's spawn, standing on a block or anywhere, boxes between any two `Vec3`s, and any doubles. Edges add the player at the spawn, the empty box an item model without extents gets, and flat, endless, subnormal and NaN (both signs) boxes. Its extra inputs go where answers flip:
- `equals`: each box against a copy, and against a copy with one side an ulp away or a zero or NaN of the other sign;
- `intersects`, `intersect`, `minmax` and `distanceToSqr(AABB)`: an entity's box against a block or another box, moved so their sides meet, overlap by an ulp or are an ulp apart, along one axis or two;
- `contains` and `distanceToSqr(Vec3)`: points on a box's sides, an ulp either side, inside and outside;
- `clip` (all three) and `Mth.rayIntersectsAABB`: rays like the game's picks from near a block along a look vector, aimed at a box's center, a point inside it, a corner, an edge or a side; at a corner along a diagonal from a whole number of blocks away, where two sides are hit at the same scale; along an axis passing the other sides at `clipPoint`'s 1.0E-7 margin, give or take two ulps (the order the margin is added in decides those); starting inside a box or on a side, ending on a side, moving about 1.0E-7 along some axes (the threshold for moving along an axis), and of length 0. The boxes are a block's shapes at the block, which `clip(Iterable, …)` gets relative to the block, so the shapes' boxes tie too;
- `collidedAlongVector`: entities walking, falling, stepping like a projectile or heading for the box, past a fluid's box (the only list the game passes) or a block's shapes.

An `Identifier` is `[namespace, path]`. Identifiers are the game's (blocks, models, textures, a tag's, the scenario's marker, the realms namespace), ones with every character a part allows, empty parts and `..` as a path, and random ones, mostly in the default namespace. Their extra inputs pair namespaces and paths that break each rule (empty, `..`, upper case, a space, non-ASCII, a slash in a namespace, a second separator in a path) for the factories and `isValid*`, split those joined strings with separators the game uses and others (`é`, and both halves of a supplementary character, which Java's `indexOf(char)` finds inside one), add every path as a new path, prefix and suffix, compare identifiers with parts in common for `equals` and `compareTo`, and try every char up to U+017F and the surrogates for `isAllowedInIdentifier` and `validPathChar`.

Netty's `ByteBuf` is `[array, readerIndex, writerIndex, markedReaderIndex, markedWriterIndex]`: its whole backing array as hex, whose length is the capacity, then its indexes (the marks read by reflection). The array past the writer index is part of it, since `writerIndex(int)` can move over it and `clear()` leaves bytes there. Netty runs without `sun.misc.Unsafe` on JDK 25, so a heap buffer's new array is a zeroed `new byte[]`, like the port's, and never Netty's uninitialized one. A `FriendlyByteBuf` is the buffer it wraps. Each call gets a fresh heap buffer like `Unpooled.buffer`'s with the same array and indexes. Buffers hold fields the way packets write them: VarInts and VarLongs of every length, their largest values, `MIN_VALUE` and -1, a last byte whose high bits don't fit, overlong ones, ones a byte too long and ones cut short; strings with their length, valid or malformed UTF-8 (a lone continuation, an overlong NUL, an encoded surrogate, a sequence cut short, a code point past U+10FFFF, a byte UTF-8 never uses), a length past the end or negative, and `readUtf`'s longest length and one more; fixed-size fields (a long, the offline player's UUID, NaNs, the walk scenario's ground block, a `Vector3f` and a `Quaternionf`); and a handshake packet with its id read. Random buffers string up to four such fields, with a length prefix that's right, a little off or anything, read from the start, the end of the first field or anywhere, with no spare capacity, a little, or the game's default 256 bytes, and marks a quarter of the time. Edges add an empty buffer of no capacity and the default one, full buffers (so writes grow them), buffers read to the end, and one cleared after marking.

`ByteBuf`'s suite covers the methods the client calls on a buffer, `FriendlyByteBuf`'s every method it adds (`withoutOverridesOf(ByteBuf.class)` leaves out its overrides of `ByteBuf`'s, which only forward to the buffer it wraps), and `VarInt`, `VarLong` and `Utf8String` are static suites. Their extra inputs go where answers change:
- indexes around a buffer's for the index setters, `isReadable(int)`, `skipBytes`, `readBytes(int)` and `ensureWritable`: negative, zero, the reader and writer indexes, the capacity, the readable bytes, one past each, and `MAX_VALUE`; ranges for `toString` (all the readable bytes, all of the capacity, empty at the end, past either end, negative), for `slice` (the same, the readable bytes and one more, what's past the writer index, and an end past `MAX_VALUE`; a slice is a buffer like any other, so its bytes and indexes are checked, but not its maximum capacity), and for `readBytes` and `writeBytes` of arrays and other buffers;
- NaNs with other payloads for `writeFloat` and `writeDouble`, which write their raw bits;
- every value whose VarInt or VarLong is a byte longer than the one before's, its neighbours and its negation, written to the default buffer and to a full one; and VarInts and VarLongs of every length up to one past the longest, with any data bits, overlong now and then, and another field after them;
- strings whose UTF-16 length and UTF-8 size differ, and malformed UTF-8, read and written with maximums around each limit (the length, the size over 3, and ones whose triple wraps: `1 << 30`, 715827883), and strings of 32767 and 32768 units for `readUtf()` and `writeUtf(String)`, in characters of one, two and three bytes;
- identifiers valid and not for `readIdentifier`, and arrays of bytes, VarInts and longs with their length, one more than there are, or negative, read with maximums around the length.

Two filters keep vanilla from allocating gigabytes: `ensureWritable` and `writeBytes` with a range only get lengths up to 2^16, or ones that overflow the writer index (which throw before growing), since vanilla grows the buffer before it finds the source's range wrong; and `readByteArray(int)` and `readVarIntArray(int)` drop buffers whose length prefix is over 2^16 but within the maximum, which vanilla allocates before it finds the buffer shorter. The port allocates the same way, and the smaller lengths still check it. `tools/golden.py` turns Netty's leak detector off: the cases never release the buffers `readBytes(int)` hands back.

Stream codecs and `IntFunction`s are objects rather than methods, so they get cases of their own (`Codecs`). A codec named N gets `N.decode` cases, which read the buffer in `args[0]` (the result is the value, and `after[0]` the buffer afterwards), and `N.encode` cases, which write `args[1]` into the buffer in `args[0]` (the result is null, and `after[0]` the buffer afterwards). An `IntFunction` named N gets `N.apply` cases, from an id to a value. The port checks them with `golden.check_codec` and `golden.check_function`, which make the codec or function inside each checked call, so a panic making it counts as the case's. A codec or function a factory makes from arguments that have generators (`ByteBufCodecs.stringUtf8`'s maximum) takes them first (`check_codec_from`, `check_function_from`), and a case throws when the factory does. Decoding reads every buffer edge, random buffers, and the codec's own encodings of the first 200 values (the value edges first): whole, cut short by a byte, cut anywhere, and with another field after them. Encoding writes each value edge into a random buffer and a random value into each buffer edge, then random values into random buffers. The values are the generators' for the codec's value type: a codec's or function's type arguments pick them, and the buffer has to be a `ByteBuf` or a `FriendlyByteBuf` and the values a class's, since a generic one's generator wouldn't know its type arguments. A parameterized value type gets its raw class's generator unless its arguments pick one (`ResourceKey.REGISTRY_STREAM_CODEC`'s `ResourceKey<? extends Registry<?>>`, whose argument only says what it's a key of), and is encoded as its raw class. Boxed numbers have their primitives' generators, and an `OptionalInt` is its int or null, either way round (`of(-1)` writes empty's 0).

Static fields get these cases wherever a suite writes fields: `Vec3i`'s, `BlockPos`'s, `Direction`'s, `Vec3`'s (and `LP_STREAM_CODEC`), `BlockHitResult`'s, `Identifier`'s and `Rotation`'s `STREAM_CODEC`, and `Direction`'s and `Rotation`'s `BY_ID`. A field whose buffer or values have no generator is skipped, naming the type. `CodecSuite` covers a class whose members hand out codecs and functions (`ByteBufCodecs`, `StreamCodec`, `ByIdMap`): its fields like that, its static methods making codecs or functions from generated arguments, its other static methods like a `StaticSuite`'s (`readCount`, `writeCount`), and, for methods taking codecs or functions, the instances the suite lists, each named by the method's descriptor and a label for what it was given: `optional(Lnet/minecraft/network/codec/StreamCodec;)Lnet/minecraft/network/codec/StreamCodec;[VAR_INT]`. The port builds the same instance under the same name. The instances are the game's kinds of codecs and functions:
- `ByteBufCodecs`: `optional` of `VAR_INT` and `STRING_UTF8`; `collection` and its operations with `ArrayList::new` and `VAR_INT` or `STRING_UTF8`, and generated maximums; `list` of `Direction.STREAM_CODEC`, and `list(int)` of `STRING_UTF8`; `fixedSizeCollection` and `fixedSizeList` of `VAR_INT`, `FLOAT` and `BOOL`, with sizes mostly a random list's (0 to 6) and `-1`, `140` and `65536`, since a larger one can't be read from a random buffer and `ArrayList`'s constructor rejects a negative one; and `idMapper(Direction::from3DDataValue, Direction::get3DDataValue)`. Their values are lists of up to 6 elements mostly, up to 140 now and then (whose count takes a second byte), and optionals empty a quarter of the time. `byteArray(int)`'s decoding drops buffers whose length prefix is over 2^16 but within the maximum, like `readByteArray(int)`'s.
- `StreamCodec`: `of(FriendlyByteBuf::writeUUID, FriendlyByteBuf::readUUID)`, `ofMember` writing and reading an `Identifier` on a `FriendlyByteBuf`, `unit(Direction.NORTH)` (which only writes `NORTH`), `VAR_INT.apply(ByteBufCodecs::optional)`, `BYTE.map(Mth::unpackDegrees, Mth::packDegrees)`, `VAR_INT.cast()` on a `FriendlyByteBuf`, and every `composite`, of 1 to 14 fields of `VAR_INT`, `STRING_UTF8`, `BOOL` and `FLOAT` in turn. A composite's value is the list of its fields, which the getters read and the constructor (a `FunctionN` made with `java.lang.reflect.Proxy`) makes, so it's an array like a tuple.
- `ByIdMap`: `continuous` of the directions by their 3D data value with each strategy, and two it refuses to make (by 2D data value, which has gaps, and of no values); `sparse` of the horizontal directions by 2D data value with `UP` for the rest, and one it refuses (two directions share 2D data value -1). Ids are the int edges, -16 to 16, and random ints.

`FriendlyByteBuf`'s readers and writers that take a decoder, an encoder or a function get the same treatment from its `InstanceSuite`: cases for the instances the suite lists with `given`, each named by the method's descriptor and a label (`readOptional(…)Ljava/util/Optional;[VAR_INT]`). Their `args` are the receiver and the generated arguments, without the instance, and a result declared as an `Object` (`readNullable`'s, `readById`'s) is encoded by its own class. The instances are the game's kinds:
- `readOptional` and `writeOptional` of `VAR_INT`, and of `ClientboundDamageEventPacket`'s source position (a `Vec3` as three doubles);
- `readNullable` and `writeNullable` of `readIdentifier` and `writeIdentifier`, and of `readUtf` and `writeUtf`; the static ones of the signature in `GAME_PROFILE_PROPERTIES` (`Utf8String` of at most 1024 units);
- `readById` of `Direction.BY_ID` and `Rotation.BY_ID`, and `writeById` of `Direction::get3DDataValue` and `get2DDataValue` (-1 for up and down);
- `readWithCount`, which nothing in the client calls, of `readVarInt` and `readUtf`.

Values a method lets be null are null a quarter of the time, like an empty optional. Besides the buffer edges and random buffers, each reader reads what its writer writes of 100 values (the edges first): whole, with a field after, cut short by a byte, and cut anywhere. The signatures include strings around 1024 units, written without the limit so the reader sees too long ones.

The Netty handlers that frame packets get a `HandlerSuite`. Their `decode` and `encode` are protected and take a context neither uses, so subclasses call them with null, on a fresh handler per case:
- `Varint21FrameDecoder.decode` reads the buffer in `args[0]` the way Netty's `ByteToMessageDecoder` asks, again while bytes are left and the last call took a frame out, and its result is the frames it found (an array of buffers). Its buffers are the edges, random ones, frames with lengths of one to three bytes (whole, with more after them, cut short, after bytes already read), runs of up to eight frames, the handshake, and lengths of zero (an overlong zero too), cut short, and wider than 21 bits. Its `[in chunks]` cases take the rest of a run of frames in `args[1]`, an array of byte arrays, each written to the buffer before the same decoder is asked again. Half the cuts are one byte into a frame, so lengths arrive split, and the decoder has to start each one afresh.
- `Varint21LengthFieldPrepender.encode` writes the message in `args[0]` into the buffer in `args[1]`: bodies at each header length's bounds, up to 2^21 - 1 and 2^21 (which throws), all readable or after bytes already read, into the game's default buffer and a full one.

Protocols and packets have encodings of their own (`PacketValues`):
- A `PacketFlow`, `ConnectionProtocol` or `ClientIntent` is its constant's name, and a `PacketType` `[flow, id]`, like any record. Types are the ones the ported protocols register, each also with the other flow, and random flows and identifiers.
- A packet is its fields: a record's components, or the fields another class's public constructor sets, in that order (read by reflection), so a `ClientboundHelloPacket` is `[serverId, publicKey, challenge, shouldAuthenticate]` and a `ServerboundLoginAcknowledgedPacket` `[]`. A value declared as a `Packet`, which a protocol's codec reads and writes, is `[type, fields]`, since it can be any of the protocol's. A `ServerboundKeyPacket` is `[keybytes, encryptedChallenge]`, made by reading them from a buffer, since its public constructor encrypts with `Crypt`.
- The custom queries' payloads are records too, `DiscardedQueryAnswerPayload` `[]` and `DiscardedQueryPayload` `[id]`, and one declared as its interface (a packet's component) is encoded by its own class. A `CustomQueryAnswerPayload` argument is null a quarter of the time, since a packet's may be.
- Each argument is its own copy of a packet or payload, made of copies of its fields, so no two arguments share an array: JSON can't say two values are the same object, and a record compares an array component by reference. So a `ServerboundCookieResponsePacket` equals another only when their keys are equal and neither has a payload, and a `ClientboundStoreCookiePacket` never does.
- A protocol's template (a `SimpleUnboundProtocol`) is its details, `[id, flow, [[type, networkId], …]]`, and a bound protocol (a `ProtocolInfo`) `[id, flow]`.
- A packet listener argument records the calls on it: it's `[]` in `args`, and its `after` slot is the calls, each `[method, argument…]`, so `handle` cases show which handler a packet calls with what. The port's `Recorder` (in `packet_listener.rs`'s tests) implements every listener trait the same way.

Each packet class gets `InstanceSuite.every`, whose `STREAM_CODEC` gets codec cases like any codec constant. Its values put each field's edges among the others' first: protocol versions (the release's, a snapshot's), addresses and port numbers past an unsigned short, player names, server ids and strings around each reader's limit (`readUtf(255)`, `16` and `20`, in characters of one, two and four bytes), byte arrays (and a public key's and a challenge's length), compression thresholds and transaction ids (any ints), identifiers, and cookies (byte arrays, and ones of 5120 and 5121 bytes). A codec constant `N` can get more buffers to decode with `extraInputs("N.decode", …)`, for fields its writer refuses but its reader doesn't see otherwise: `ServerboundHelloPacket`'s names over 16 characters and the cookie packets' payloads over 5120 bytes, written without the limit, and the custom query packets' payloads (everything after the header, which their readers skip) of 1 MiB and a byte more. A record whose components include an enum hashes the constant's identity hash, which changes from run to run, so `InstanceSuite.exclude` writes its `hashCode` as skipped (`PacketType`, `ClientIntentionPacket`), and the port marks it pending. So does a record holding an array, whose `hashCode` and `toString` hash and print the array's identity hash (the cookie packets').

A login's last packet carries the player's profile, from Mojang's authlib (`ProfileValues`). A `Property` is a record, `[name, value, signature]`, and so is a `GameProfile`, `[id, name, properties]`. A `PropertyMap`, and the Guava `Multimap` it's made from, is its `asMap()`'s entries in order, `[[key, [property, …]], …]`. The multimaps are built the way the game builds them, with `ImmutableMultimap.builder()`, which groups the values by key in the order each key first came. Names are the skin's `textures`, a few names the random ones share (so keys repeat), and strings around `GAME_PROFILE_PROPERTIES`' limit of 64; values a skin's textures (base64 JSON) and strings around 32767; signatures none a quarter of the time, a 4096-bit key's base64 signature, and strings around 1024. The multimaps' edges add the empty one, each property alone, two properties under one name either way round, names that interleave either way round, a property twice, a key that isn't its property's name, and 16 and 17 properties (the codec's limit). Profiles are the player names (around 16), any `UUID`s and those maps, the offline player's profile and a signed skin's. `PropertyMap`'s suite adds the `Multimap` methods it forwards (`values`, `size`, `isEmpty`, `equals`, `hashCode`, `toString`) with `inherited`, and `equals` gets every pair of edges, so maps with the same keys in another order compare equal. `ByteBufCodecs`' `GAME_PROFILE_PROPERTIES` and `GAME_PROFILE` also decode what's written without the codec's limits (on the count, the strings and the name), and counts of 0, -1, `MIN_VALUE`, 16, 17 and `MAX_VALUE` with nothing after them: a `CodecSuite` takes extra buffers for a codec constant like an `InstanceSuite` does, with `extraInputs("N.decode", …)`. `UUIDUtil` is a static suite, whose offline UUIDs also get the player names, and `java.util.UUID`'s suite adds `nameUUIDFromBytes`, with `OfflinePlayer:` and each player name among its byte arrays.

The configuration protocol's serverbound packets come next (`PacketValues`). A `ClientInformation` is a record, `[language, viewDistance, chatVisibility, chatColors, modelCustomisation, mainHand, textFilteringEnabled, allowsListing, particleStatus]`, with languages around `readUtf(16)`'s limit, view distances and skin parts past a byte (`writeByte` keeps the low 8 bits, and the reader reads the distance signed and the parts unsigned), and every constant of `ChatVisiblity`, `HumanoidArm` and `ParticleStatus`. Its constructor reading a `FriendlyByteBuf` also reads what `write` writes, which doesn't stop the language at 16 characters. A `KnownPack` is `[namespace, id, version]`, with the vanilla pack's parts and strings around `STRING_UTF8`'s 32767, and a `ServerboundSelectKnownPacks`' packs are lists of them (a `List<KnownPack>` argument gets them, like `List<AABB>`), with the 64 its codec takes and 65. A custom packet payload is a record too, `BrandPayload` `[brand]` and `DiscardedPayload` `[id]`, but one declared as `CustomPacketPayload` (a packet's component, a dispatch codec's value) is `[class, fields]` by the class's simple name, `["BrandPayload", ["vanilla"]]`, since a `DiscardedPayload` can have the brand's identifier. Brands are around `readUtf()`'s 32767, and payload identifiers are the scenario's marker, the brand's, `minecraft:register` and any. `CustomPacketPayload`'s `CodecSuite` checks `codec(StreamMemberEncoder, StreamDecoder)` with a brand's `writeUtf` and `readUtf`, and `codec(FallbackProvider, List)` as `ServerboundCustomPayloadPacket` makes it (a `DiscardedPayload` of up to 32767 bytes for any identifier but the brand's) and with no types and a maximum of 0. `ServerboundCustomPayloadPacket` also decodes discarded payloads of 32767 and 32768 bytes and brands past 32767, written without the limit. An `InstanceSuite` gives a static method making a stream codec from generated arguments codec cases like `CodecSuite`'s (`DiscardedPayload.codec(Identifier, int)`, whose buffer is a type variable, read as its bound, `FriendlyByteBuf`), and that one also decodes buffers as long as maximums of 0, 1, 255 and 32767, and a byte either side. `FriendlyByteBuf.readEnum` and `writeEnum` are given `ServerboundResourcePackPacket.Action` (cases `readEnum(Ljava/lang/Class;)Ljava/lang/Enum;[ServerboundResourcePackPacket.Action]`), and `readEnum` reads VarInts from -16 to 16; a result declared as an `Enum` is encoded by its own class, like an `Object`. The port checks a codec made from two arguments with `golden.check_codec_from2`.

NBT (`NbtValues`, `NbtSuites`) encodes every tag as `[id, payload]`, whatever it's declared as: an `EndTag` `[0, null]`, the numbers `[1, byte]` to `[6, double]`, the arrays `[7, [byte, …]]`, `[11, [int, …]]` and `[12, [long, …]]`, a string `[8, value]`, a list `[9, [tag, …]]`, and a compound `[10, [capacity, [[key, tag], …]]]`: its `HashMap`'s table length (0 before it's made, read by reflection, which `tools/golden.py` opens `java.util` to) and its tags in the map's order, which is the order it writes them in. A `TagType` is its name (`"BYTE"`, `"INVALID[13]"`), an `NbtAccounter` `[quota, usage, maxDepth, depth]`, a `Number` (`box()`) is encoded by its own class, and a `Map.Entry` (`entrySet()`) is `[key, value]`. A `DataInput` or `DataOutput` is Netty's `ByteBufInputStream` or `ByteBufOutputStream` over a buffer, as `FriendlyByteBuf.readNbt` and `writeNbt` make them, encoded as the buffer; the port's checks make the stream over the buffer inside the call (`check_mut` with a `&mut ByteBuf`).
- Tags are the game's kinds: items' and block entities' compounds, lists of one kind and of several (which a list writes as compounds that wrap them under the empty key), lists holding compounds that look like those, nested up to 17 deep, numbers at `ShortTag`'s and `IntTag`'s cache bounds, -0.0 floats and doubles (which only the constructor makes), and compounds whose tables are bigger than they need (after removals) or as small as can be (copied like `shallowCopy`), keys whose hashCodes are equal, and 12, 13, 24 and 25 tags, where tables grow. Each argument is its own copy, each compound's map made with the same table length and order (an empty one with a table gets a key put and taken out). A deeper tag would pass serde_json's recursion limit in the port's test, so the default accounter's depth of 512 is checked through accounters of 0 to 3 and 16 deep, the same check. Strings around `writeUTF`'s 65535 bytes (in characters of one to three bytes, U+0000's two, and supplementary characters' six) are too big for every member's edges, so the writers, `skipString` and the string type's `load` get them as extra inputs.
- A member taking a compound's key also gets the receiver's own keys, and one taking a list's or array's index the indexes from -1 to one past the end. `TagType.load` and `skip` read what tags of the type write, one or several in a row; `NbtIo`'s readers read what its writers write, and root tags with names; `FriendlyByteBuf.readNbt` reads what `writeNbt` writes. Accounters are the game's (the default 2 MiB, the trusted unlimited ones, the click action's 32 KiB and 16 deep), small quotas and depths, ones at their quota or depth, a usage whose next sum overflows, and a negative quota.
- A read with an accounter whose quota is bigger than the default one (a trusted codec's, or a usage whose sum overflows) is dropped unless the same read with the default quota doesn't run out of it (`NbtValues.readsLittle`): a count read from random bytes can be in the billions, and a list or array is allocated after it's accounted for, so vanilla would allocate gigabytes. Reading NBT wraps an `IOException` in a crash report, whose system details probe the hardware with OSHI (files under `/proc` and `/sys`, and `lshw`, `dmidecode`, `lspci` and `cpuid` as processes) for over 20 ms a report, so `tools/golden.py` runs the generator without OSHI's jar. `SystemReport` catches the `NoClassDefFoundError` like any detail it can't get, and only the exception's class goes into a golden, so the files come out the same. The generator sets `SystemReport`'s logger to `ERROR`, since it warns with a stack trace about each detail it can't get, the game's version included.
- Modified UTF-8 can decode to a lone surrogate, which the golden files' UTF-8 can't hold, so buffers a `DataInput` reads never hold an encoded surrogate that isn't followed by its pair (`NbtValues.noLoneSurrogates`). `ByteBufInputStream`'s suite reads modified UTF-8 that's valid, overlong, malformed in each place, cut short and past the end; `ByteBufOutputStream`'s writes strings around the 65535-byte limit.
- `java.util.HashMap` has a program suite (`HashMapSuite`): `put`, `remove`, `get`, `containsKey` and `copy` (`new HashMap<>(map)`) on a map of strings, each step `[output, [capacity, [[key, value], …]]]`. Keys come from small pools, from a family whose hashCodes are all equal ("Aa" and "BB" blocks) and from one whose spread hashes agree in their low six bits, so bins grow past 8, which makes a table under 64 grow. A program whose map makes a tree bin (a bin of 9 in a table of 64 or more) is written under `treeified programs`, which the port marks pending. `sized programs` run the same kinds of programs on a map made with `new HashMap<>(initialCapacity)`, `[initialCapacity, program]`, the way codecs make their maps and sets: 6 programs for each capacity around the powers of two and the thresholds (0 to 33, 63 to 65, 100, 128, 140, 65535 and 65536), negative ones (which throw), and 120 random capacities up to 300. Their tree bins go under `treeified sized programs`, also pending.
- `ByteBufCodecs`' `TAG`, `TRUSTED_TAG`, `COMPOUND_TAG`, `TRUSTED_COMPOUND_TAG` and `OPTIONAL_COMPOUND_TAG` get codec cases (a codec of `Optional<X>` gets X's values or empty, a quarter of the time), and `tagCodec` and `optionalTagCodec` are given the click action's accounter, `compoundTagCodec` the trusted one. A codec constant's decode inputs can be dropped like a method's (`whereDecode("N.decode", …)`).

SNBT has a suite of its own (`SnbtSuites`, `net.minecraft.nbt.TagParser`: 16,884 cases), over `NbtOps`. A parse's result is `["tag", tag]` or `["error", message]`, the `CommandSyntaxException`'s message with its context, worded through `en_us`; a reader's cases add its cursor after. `parseFully(String)` gets 5,287 inputs: hand-written SNBT of every kind (each number form at its edges: suffixes, signedness, hex and binary, underscores, exponents, leading zeros, ranges; every string form and escape, and a surrogate pair made of two escapes; lists and arrays with their element types; compounds with repeated keys and keys of one hash; the operations; whitespace of every kind and some Java doesn't skip), hand-written input hitting each error, 1,500 random documents in the forms SNBT can be written in, what 400 random tags print as SNBT, and 3,000 mutations of all of those (one to three characters inserted, deleted or replaced). `parseFully(StringReader)` gets 1,790 of them after a prefix, `parseAsArgument` 2,414, most with text after a value, `parseCompoundFully` 2,139 and `parseCompoundAsArgument` 1,024. `FLATTENED_CODEC` and `LENIENT_CODEC` (whose alternative is `CompoundTag.CODEC`) decode 1,789 and 1,825 tags (the inputs as strings, compounds and any tags) and encode 315 and 301 compounds onto the empty prefix and others, results as `DfuCodecSuite`'s. `\N{name}` escapes need Unicode's table of character names, which isn't ported, so no input holds one; nor does a case whose input, result or message would hold a lone surrogate, or a compound of more than eight keys of one hash, whose bin Java's `HashMap` makes a tree of.

The click action's tag comes behind a length prefix (`ByteBufCodecs.lengthPrefixed`), which reads its value from a slice of the buffer. `lengthPrefixed(int)` is given the click action's `optionalTagCodec`, and `lengthPrefixed(int, BiFunction)` a discarded payload's codec in a `FriendlyByteBuf` (`(parent, child) -> new FriendlyByteBuf(child)`), which skips every byte its slice has. Their maximums are the click action's 65536 half the time and small ones otherwise, with edges at 0 to 4, 16, 32767, 32768 and the int limits. A listed instance gets more buffers to decode like a codec constant, under `extraInputs("descriptor[label].decode", …)`, each its leading arguments and the buffer: tags (none, an empty compound, a byte, a string, a compound of two) and payloads (none, one byte, five) behind a prefix that's right, a byte short, a byte long, zero, negative or an int's limit, with maximums of the payload's length, a byte less and 65536, no spare capacity or 4 bytes (so a prefix a byte long is past the writer index but inside the array), and a byte after or none, read after a byte already read (so a mark set on the buffer would show); and discarded payloads of 32767 and 32768 bytes. The tags' values also hold a string too long for `writeUTF`, whose writer throws after writing the tag's id, so encoding it shows that nothing reaches the buffer.

`ServerboundCustomClickActionPacket` is a record, `[id, payload]`, whose payload is a tag or none (an `Optional<Tag>` argument gets them: a parameterized type picks its generator, like `List<AABB>`). An `EndTag`'s `hashCode` is `Object`'s, an identity hash, so `hashCode` is given no packet holding one (`where`). Its codec also decodes tags behind prefixes of 65536 bytes (the limit, zeros after the tag) and 65537, byte arrays of 32744 and 32745 bytes (an array accounts 24 bytes and one a byte, so the click action's 32 KiB takes the first and refuses the second) and of 40000, and compounds nested 16 and 17 deep (it reads 16).

The configuration protocol's clientbound packets that need neither text components nor the registries come next (`PacketValues`). The unit ones (`ClientboundFinishConfigurationPacket`, `ClientboundResetChatPacket`, `ClientboundClearDialogPacket`) are `[]`, and `ClientboundKeepAlivePacket` and `ClientboundPingPacket` `[id]`, any long or int. `ClientboundSelectKnownPacks` gets the serverbound one's lists of packs, which its codec takes without a limit. `ClientboundResourcePackPopPacket`'s `Optional<UUID>` and `ClientboundPostEffectsPacket`'s `List<Identifier>` get generators of their own (any UUID or none, lists of identifiers), like `List<KnownPack>`. A `ClientboundTransferPacket`'s host is an address or a string around `readUtf()`'s 32767 (in characters of one and four bytes) and its port any int (a VarInt), and a `ClientboundCodeOfConductPacket`'s text is around `STRING_UTF8`'s 32767; both codecs also decode what's written without the limit. `ClientboundCustomPayloadPacket`'s `CONFIG_STREAM_CODEC` gets the serverbound packet's payloads, and also decodes a discarded payload of the most it takes (1 MiB) and a byte more, and brands past 32767; `GAMEPLAY_STREAM_CODEC` reads a `RegistryFriendlyByteBuf`, so it's skipped.

A `ResourceKey` is `[registry, identifier]`. Keys are interned, so each argument is the key itself, like the game's. They're the keys of registries the server synchronizes (biomes, dimension types, chat types, damage types, enchantments, wolf and painting variants, dialogs) and of the dimensions, which it doesn't, the root registry's own, keys of elements (the overworld, plains), keys with the odd identifiers (empty parts, `..`) and one in a registry named like the scenario's marker, and random ones: a registry's key half the time, and otherwise an element's in one of those registries or any. `Registries` is a static suite: every registry's key as a field, and its static methods on the keys above. A `RegistrySynchronization.PackedRegistryEntry` is a record, `[id, data]`, whose data is any tag or none, and a `ClientboundRegistryDataPacket` `[registry, entries]`, with lists of those entries (a `List<PackedRegistryEntry>` argument gets them). `ResourceKey` doesn't override `hashCode`, so the packet's record `hashCode` hashes the key's identity hash and is written as skipped, and the entry's `hashCode` is given no entry holding an `EndTag`. The packet's `equals` also compares packets of every pair of the keys' edges with no entries, among which are keys with the same identifier in different registries, and the entry's codec also decodes data at the default quota and past it: lists of 40329 empty compounds (2097144 bytes accounted: 36 for the list, and 4 and 48 for each compound) and 40330, a byte each to read. With these, `PacketType`'s generator has 34 types and their other flows, 68 edges, whose pairs are past `MAX_EDGE_PRODUCT` (2048), so its `equals` gets every pair of edges as extra inputs, like it got them as its edge cases before.

A `java.util.HashSet` is `[capacity, [element, …]]` and a `java.util.HashMap` `[capacity, [[key, value], …]]`, whatever they're declared as (a record's `Set` or `Map`, a codec's value): like a compound's map, the table's length and what it holds in its order, read by reflection (`HashMapSuite.encode`), since the table decides the order an encoder writes it in. Other maps have no encoding yet. Each argument is a copy with the same table length and order (`HashMapSuite.copy`, made with the capacity and filled in order). `Codecs.hashSetOf` and `hashMapOf` make them like `listOf`: edges add the empty one without a table and with one, each element (or key, or value) edge alone, all of them, all of them as a codec makes them (`new HashSet<>(count)`), and the game's; random ones have a random list's sizes and are made with `new HashSet<>()`, as a codec makes them, or with more put and taken out again, so the table is bigger than they need. `ClientboundUpdateEnabledFeaturesPacket`'s features are sets of identifiers: the server's (`FeatureFlags.REGISTRY.toNames`, a `HashSet`), every flag's, each flag's and none, six identifiers whose hashCodes are equal (paths of "ak" and "c-" blocks, which share a bin) added either way round, so equal sets write them in other orders, 12, 13, 24 and 25, where the table grows, and 13 with 10 taken out. Its codec also decodes counts with nothing after them (negative ones throw making the set), identifiers twice (the set keeps one) and one that isn't an identifier. `ClientboundCustomReportDetailsPacket`'s details are maps of names around `stringUtf8(128)`'s limit and short values; values around 4096 (in characters of one and four bytes), 13, 32 and 33 details, colliding names (`"Aa"` and `"BB"` blocks) put either way round, and 13 with 10 taken out are among the maps' edges, not the values' own, so random maps don't draw 4 KiB strings. Its codec also decodes what's written without the limits, counts around 32, negative and with nothing after them, and a name twice (the map keeps the second value where the first was). `ByteBufCodecs.map` is given `HashMap::new` with `STRING_UTF8` and `VAR_INT` (maps of strings to ints), and with the report details' codecs and a generated maximum.

The game protocol's packets whose codecs read the registries come next (`RegistryValues`). A `RegistryFriendlyByteBuf` is a `FriendlyByteBuf`'s buffer (the same edges and random buffers, encoded the same) with the registries a client has once it has joined a vanilla server: the static ones (`BuiltInRegistries`, `ClientRegistryLayer.STATIC`) and the synchronized ones in the order vanilla's server sends them, which the generator loads the way the server does (`WorldLoader`: the vanilla data pack from `client.jar`, the static registries' tags, then `RegistryDataLoader.WORLD_REGISTRIES`), each registry's elements sorted by identifier. The status protocol, the server list's ping, comes next (`PacketValues`): `StatusPacketTypes` is a static suite, `StatusProtocols` a `ProtocolSuite`, `ServerboundStatusRequestPacket` is `[]`, and `ServerboundPingRequestPacket` and `ClientboundPongResponsePacket` (which play shares) `[time]`, any long. `ClientboundStatusResponsePacket`'s status is read from JSON with DataFixerUpper's codecs and holds text components, so it has no generator yet and `StatusProtocols.CLIENTBOUND.codec()` is skipped; a test reads the status response vanilla's server sent and writes it back byte for byte. The block state registry has hand-written suites (`BlockSuites`), which encode a property as the name of its field in `BlockStateProperties` (every block's properties are among them, each in one field), a value as a boolean, an int or its constant's name, a block as its registered name (`minecraft:stone`) and a state as its id in `Block.BLOCK_STATE_REGISTRY`:

Chunk data has hand-written suites too (`ChunkSuites`). Programs run ops on one object and record each op's output; the first op that throws ends the program as `{"throws": …}`. Bytes are hex strings, and a block state is its id.
- `SimpleBitStorage` for every bits per entry from 1 to 32 (and bits it refuses): `<init>(II)V` → `[bits, size, raw]`; `<init>(II[J)V` from random longs → every `get(i)`, which runs the divide-by-magic-number cell index for every index, at sizes of 4096 (a section), 64 (a section's biomes), 0, 1, around the values per long, and random ones, and longs a cell short or long, which throw; `<init>(II[I)V` from random values (any int now and then, which the mask cuts) → the longs, and too few values; `unpack`, `getAll` and `fill` (which also writes the bits past a long's last whole value) → the ints or longs; and `programs`, `[bits, size, longs, ops]` → `[outputs, longs after]`, of `get`, `set`, `getAndSet`, `fill` and `copy` with indexes and values out of range now and then.

Where a key lands goes by its identity hash, which changes from run to run, so no output may depend on it: a key is never added twice, and `addMapping` only gets ids no key has (a shadow map runs the ops as they're made), or ones past what the table grows to, which throw after the key is in. A `java.util.BitSet` is its words in use (`toLongArray`). Its generator makes the light packets' masks (bits of the overworld's 26 light sections, all of them, alternating), single bits around the words' bounds and random words, none past bit 255. `java.util.BitSet`'s `InstanceSuite` covers what the codecs and the client's light code call; `set(I)` gets indexes up to 1024, since a bigger one makes it allocate. With it, `ByteBufCodecs.BIT_SET` and `FriendlyByteBuf`'s bit set readers and writers get cases. A fixed-size bit set's reader allocates its size over 8 bytes before it reads, so `fixedBitSet(I)` is a listed instance with sizes up to 2^16 (around the bytes' bounds, 26, and random ones), and `readFixedBitSet` and `writeFixedBitSet` drop larger sizes (`where`).

An entity's movement has pure parts that get goldens too, private or protected statics called by reflection: `Entity`'s `collideWithShapes` (6,000 cases: the player's boxes, standing, crouching and swimming, around the walk scenario's ground, moving like a walk, a fall, a jump or a step, or by the margins, through up to six blocks' shapes, full blocks and the base shapes, around the block under it) and `collectCandidateStepUpHeights` (6,000: the same shapes, step heights of 0.6, 1.0 and any, and heights to skip of 0.0, -0.0, the walk's fall and the ground's), `getInputVector` (4,000: inputs as `modifyInput` makes them, sneaking and diagonal ones among them, the speeds the player moves at, on the ground and in the air, sprinting or not, and turns around the compass), and `LivingEntity.computeModifiedFriction` (549: the blocks' frictions and modifiers, and any). `PlayerSuites` has `AttributeInstance` programs (1,500), `[attribute, ops]` on one of the attributes movement reads, each step `[output, value]`: `setBaseValue` (in and past the attribute's range, NaN and infinities), `addTransientModifier` of each operation (throwing for an id that's on), `removeModifier`, `removeModifiers` and `getValue`. Each operation's modifiers have one id, so an instance never holds two of one operation, whose order is a fastutil open hash map's.

Scenarios are replayed offline by tests (`rustcraft::oracle::client::replay`, "Offline replays" below), which reproduce vanilla's trace and its serverbound packets from the scenario-start marker on.

`BlockPos`'s `AABB` overloads get boxes up to 5 blocks across whose sides are on blocks' faces, 1.0E-7 or an ulp inside or outside them, or anywhere in a block, and `betweenCornersInDirection` also `cornerWalks`' directions. `AABB.Builder`s have included up to 8 points (and the edges none, one with -0.0 or NaN, or infinities).

`FrustumIntersection.intersectAab` and `testPoint` also get boxes and points like the game's (chunk sections, entities and the camera's cube, relative to the camera), boxes and points on a plane to rounding (on the frustum's face, where the order the plane's terms are added in decides which side they land on), and every float edge in each coordinate of a box in front of every edge frustum.

- **Pending ledger.** Each ported file ends with a test that checks every method and constant in its golden file, or marks it pending with a reason. Anything neither checked nor pending fails the test, so a class is either fully verified or says what's left.
- **Methods that hang.** Some vanilla methods never return on extreme inputs. A watchdog names the call, and the suite keeps the inputs in range with `where()`.

### Pipelines and shaders

`RenderSuites` records the renderer's pipelines and the shaders vanilla's OpenGL backend compiles for them, from vanilla's own classes:
- `DefaultVertexFormat`, `BindGroupLayouts` and `RenderPipelines` are their public constants. A vertex format is `[stepRate, vertexSize, [[name, offset, format], …]]`, a bind group layout `[[name, type, gpuFormat], …]`, and a pipeline `[location, shaders, defines, bindGroupLayouts, colorTargetStates, depthStencilState, polygonMode, cull, vertexFormats, primitiveTopology, pushConstantSize, sortKey]`: shaders `[[stage, id], …]`, defines `[[[key, value], …], [flag, …]]` in the order they were defined, color targets `[blendFunction, format, writeMask]` (a blend function `[[src, dst, op], [src, dst, op]]` for color and alpha), depth `[test, write, biasScale, biasConstant]`, and the 16 vertex buffer slots. A pipeline's layouts are a hash set whose order changes from run to run, so they're sorted by their uniforms' names. An OIT set is its three pipelines, a snippet its builder's fields. `requiredPipelines()` and `optionalPipelines()` are the locations `ShaderManager` compiles, in their `HashMap`'s order.
- The four steps of compiling each of those pipelines, as `PipelineBuilder.compilePipeline` runs them, with the shaders `ShaderManager.loadConfigs` loads from the client jar (through a `ResourceManager` that lists the jar's assets):
  - `GlslCompiler.compileToSpv`: `[flags, name, stage, defines]` → the SPIR-V's bytes as hex, each shader once;
  - `SPIRVModule.reflect`: the same arguments → `[inputs, outputs, descriptors, pushConstants]`, an interface variable `[name, location, flat, component, type]`, a descriptor `[name, resourceType, set, binding, type]`, a type `[baseType, dimensions, vectorSize, [arrayLength, …]]`;
  - `PipelineBuilder.generateBackendCreateInfo` (private, by reflection): `[flags, location]` → the create info, its shaders' SPIR-V after the bindings are renumbered, and each uniform's binding;
  - `GlPipelineRecompiler.decompileShaders`: `[flags, location]` → each shader's GLSL 330, the text `glShaderSource` gets.
- `flags` are the device's `[isZZeroToOne, shaderDrawParameters, isExplicitDepthRequired]`, the three answers that change the text, from a stand-in device like `ProjectionSuite`'s. Mesa's llvmpipe under Xvfb, where the oracle client renders, is `[true, true, false]`: its log lists `GL_ARB_clip_control` and `GL_ARB_shader_draw_parameters` among the extensions vanilla turned on, and it isn't an Apple GPU. Every pipeline gets that; five that read the flags (terrain, multidraw terrain, clouds, an OIT pass, the GUI) also get the other seven combinations. No vanilla shader reads `RENDERPEARL_INSTANCE_INDEX_INCLUDES_BASE_INSTANCE`, so `shaderDrawParameters` only changes SPIRV-Cross's output.
- `RenderPipelines`' sort keys are the order the pipelines are built in, which is its static initialiser's: nothing in the generator builds a pipeline before it, and in the game only post chains do, after it.

The port compiles through the same native libraries (PORTING.md), so its SPIR-V and GLSL are compared byte for byte.

### Textures and the block atlas

`TextureSuites` reads the vanilla pack the way the client does: `ClientPackSource.createVanillaPackSource`'s pack (the jar's resources, then a layer for the launcher's asset index, whose directory isn't on the machine, as it holds only sounds and translations) opened into a `MultiPackResourceManager`, after `ClientBootstrap.bootstrap()` (which registers the atlases' sprite sources). An image is `[width, height, md5]`, the MD5 of its RGBA bytes as they lie in memory, so a mismatch is a pixel that differs.
- `MultiPackResourceManager`: `getNamespaces`, what `listResources` lists under `textures`, `textures/block`, `atlases`, `models/block` and `blockstates`, in its `TreeMap`'s order, and each atlas definition's resource stack.
- `NativeImage.read` of every PNG under `textures/` (3,964): the RGBA stb decodes.

- `SpriteLoader` (the block atlas's CPU half, as `loadAndStitch` runs it with the oracle client's options: mipmap levels 4, filtering that isn't anisotropic, and llvmpipe's 16384 as the largest texture): the sprites `atlases/blocks.json`'s sources list, loaded by `SpriteResourceLoader`, then `stitch`, `[atlas, maxMipmapLevels]` → `[width, height, mipLevel, [[name, x, y, width, height, padding], …]]` in the order `gatherSprites` hands them out, and `increaseMipLevel` of each sprite, `[name, mipLevel]` → `[animated, [image, …]]`, every mip level as `[width, height, md5]`. `SpriteLoader.stitch` reads the options from `Minecraft.getInstance()`, which the generator has none of, so the suite runs its steps with those values.

The port reads the pack from `vanilla/<version>/resources/` (the client jar unpacked) and decodes with LWJGL's own `liblwjgl_stb.so`, so both sides run the same decoder.

The atlas's GPU half, drawing each sprite into each mip level, is a frame test (`tests/opengl_frame.rs`, below).

### Block models

`ModelSuites` covers block models, from the math that turns them to every block state's baked quads:
- `SymmetricGroup3`, `OctahedralGroup`, `Quadrant` (with `parseJson` of every multiple of 45 degrees from -720 to 720 and the int limits) and `FrontAndTop` are `InstanceSuite.every`s, their constants every receiver and argument. `BlockMath` is a static suite whose `getFaceTransformation` also gets the 48 rotations' transformations, made the way `BlockModelRotation` makes them, with each side. JOML's `Matrix3f.set(int, int, float)` writes with `Unsafe` without checking the column and row, so random ones crashed the JVM: its cases keep to the nine elements, each set to 1, -0.0 and NaN in an identity and a rotation.
- `BlockModelRotation`: each of the 48, its `toString`, transformation and face matrices, and its uv-locked state's. `FaceBakery` asks `isIdentity` about an inverse face matrix before anything else reads it, which adds properties to the shared matrix, so they're recorded as `FaceBakery` reads them, after that check (PORTING.md, "Block models"). The suite runs before the bake.
- `LazilyParsedNumber`: every number in the vanilla pack's models and block states (286 different texts), as Gson reads it: `floatValue()` and `intValue()`.
- `ModelBakery`: `ModelManager`'s reload, as far as block states go. The block and item atlases are stitched like `TextureSuites`' (a quad's UVs are its sprite's place in the atlas; `MaterialBaker` looks a material up in the item atlas first), every model file is read with `CuboidModel.fromStream`, the block states' definitions with `BlockStateModelLoader`, their models found and resolved by `ModelDiscovery` (item models aren't discovered: no block state's model needs one), and `ModelBakery.bakeModels` bakes them with a `MaterialBaker` over the two atlases. A model is `[kind, particle, materialFlags, contents]`: a single variant's part, a weighted list's `[weight, model]` entries, or a multipart's models the state selects. A part is `[useAmbientOcclusion, particle, materialFlags, quads]`, its quads unculled, then culled toward each direction in `Direction`'s order, and a quad `[positions, packedUVs, direction, [atlas, sprite, layer, tintIndex, shadeDirectionOverride, lightEmission]]`, a material `[atlas, sprite, forceTranslucent]`. `bake` is the MD5 of each block state's encoding (as Gson writes it, which is serde_json's text), for all 35,723, `bake[full]` the encoding itself for each block's default state, and `missingModels.block` the missing model's. The file is 6.8 MB. The quads' item render types aren't recorded: they come with item rendering.
- `ModelBlockRenderer`: sections meshed the way `SectionCompiler.compile` meshes one, each non-air block of the section in `BlockPos.betweenClosed`'s order whose render shape is a model, at its place in the section and with its state's seed, its quads into a `BufferBuilder` for their layer (`putBlockBakedQuad`), flat and with ambient occlusion. The level (`MeshLevel`, the same in the port's test) is a pattern of 24 blocks' states (air two times in five) by a hash of the position and a seed, crossing the section's sides: whole blocks whose shapes and rendering the port has, opaque, cut out, translucent, glowing, emissive, rotated, invisible, and with unculled faces inside (slime, beacon, vault, mangrove roots). Sky light is `floorMod(3x + 5y + 7z + seed, 16)` and block light `floorMod(7x + 11y + 13z, 16)`, the cardinal lighting the default, and `BlockColors` empty: the biomes' tints come with `BiomeColors`. Each of 12 seeds, flat and smooth, gives each started layer's `[layer, vertexCount, md5]` of its vertex bytes. `LightCoordsUtil` is a static suite (its `getLightCoords` take a level, so they're checked through the meshes).
- `SectionCompiler`: `compile` over `RenderSectionRegion`s made the way `RenderRegionCache` makes them, the section and its 26 neighbours copied (`SectionCopy`, none for a section of only air, past the level's height or of a chunk the level doesn't have). "walk" compiles every section with blocks of the walk capture's chunks, the camera at the walk's eye, as `[x, sectionY, z, ambientOcclusion]`; "pattern" compiles the middle of 27 sections of `MeshLevel`'s blocks (its waterlogged states left out: fluids come with `FluidRenderer`), as `[seed, ambientOcclusion, cameraX, cameraY, cameraZ]`, the camera deciding the translucent layer's order. A region is made without its constructor, which asks a `ClientLevel` for its lighting, and answers the level's questions itself: `MeshLevel`'s light (seed 0 for the walk), the default cardinal lighting, white tints. A result is `[layers, visibility]`: each rendered layer's `[layer, vertexCount, indexCount, md5 of the vertices, md5 of the sorted indices or null]`, and the `VisibilitySet` as a long, bit `from + 6 * to` for each pair of faces it connects. The port's test puts the chunk packet goldens' chunks in a `ClientLevel` and reads them through `RenderRegionCache` (`create_region_over`, the light and tints the test's). A region of the level itself copies its light, biomes and cached tints for the worker thread that compiles it (PORTING.md, "Meshing"): `render_section_region::tests` checks that copy against the level, every block's light of both layers and raw brightness in the 27 sections and every resolver's tint in the section and the layer below, for regions in the middle, at the edge and at the top and bottom of the walk's chunks, lit from their packets and with a layout of `ClientLevel`'s golden biomes, then again over the level's cache with the first region's tints given back.

### The font

`FontSuites` loads the vanilla pack's fonts the way `FontManager` does: its private `prepare` (each `font/*.json`'s providers loaded and the references resolved) run on the calling thread, then each font made a `FontSet` with no font options as `apply` makes it (`apply` itself reads `Minecraft.getInstance()`). ## 2. Scenarios and tick traces

A scenario, `oracle/scenarios/<name>.json`, is the input both clients replay:

```json
{
  "world": { "seed": 0, "preset": "flat", "time": 6000, "game_mode": "survival" },
  "player": { "pos": [0.5, -60.0, 0.5], "y_rot": 0.0, "x_rot": 0.0 },
  "options": { "window": [854, 480], "fov": 70, "gui_scale": 2, "render_distance": 4, "hide_gui": false },
  "steps": [
    { "ticks": 20, "keys": ["forward"] },
    { "ticks": 1, "keys": ["forward", "jump"] },
    { "ticks": 10, "keys": [], "look": [90.0, 10.0] },
    { "screenshot": "after-walk" }
  ]
}
```

- `keys` are held for every tick of the step: `forward`, `back`, `left`, `right`, `jump`, `sneak`, `sprint`, `attack`, `use`. A key held while a screen is up goes to the screen, as a person's would, so it holds nothing down.
- `look` sets `[y_rot, x_rot]` in degrees at the start of every tick of the step.
- `screenshot` captures the current frame as `<name>.png` without advancing the game. With `"blink_on": true` it's taken just after the focused edit box's cursor has come on: the cursor blinks by the wall clock, 300 ms on and 300 off from when the box got the focus (`EditBox.focusedTime`, `TextCursorUtils.isCursorVisible`), so both clients wait until the blink is in the first 100 ms of a shown half (the oracle client reads `focusedTime` by reflection), and the frame comes well before it turns off. Without it, a screenshot of a screen with a focused edit box shows the cursor or not by chance. A scenario that opens a screen screenshots it while it's open.
- Input between two ticks, which the game handles as it comes, without a tick (Fabric's `TestInput.pressKey` would wait for one, which the trace doesn't have):
  - `{"key": "escape"}` presses and releases a key (`holdKey` then `releaseKey`: `KeyboardHandler.keyPress` with its SDL scancode and SDL's keycode for it): `escape`, `enter`, `t`, `slash`, `tab`, `backspace`;
  - `{"type": "/list"}` types characters (`typeChars`: `KeyboardHandler.charTyped` with each UTF-16 unit);
  - `{"cursor": [x, y]}` moves the mouse to a place in the window's pixels (`setCursorPos`: `MouseHandler.onMove`). Opening a screen releases the mouse, which Java puts where the X server's pointer is (`resyncMousePosition`), so a scenario puts it somewhere after a screen opens before a screenshot shows the screen;
  - `{"click": "left"}` presses and releases a mouse button where the cursor is (`holdMouse` then `releaseMouse`: `MouseHandler.onButton` with SDL's button number, 1 for the left);
  - `{"scroll": 1.0}` turns the mouse wheel where the cursor is (`scroll`: `MouseHandler.onScroll`, up for positive);
  - `{"command": "tellraw @s …"}` sends a command, without its slash, like the setup's (`connection.sendCommand`).

  An input step's `wait_for` waits for its answer right after it: the client not ticking, the network running, until each type has been queued more often than before the input; then the client handles what it has queued, before the next tick. A chat line's age, and so how faded it is at a tick, is then the same every run.
- `screenshots_every`, optional on a step with ticks, captures a frame after every so many of the step's ticks, counted from its first, each named by the tick it comes after, its trace line's `tick` in four digits (`tick-0007.png`): a video of the step, for checking that frames are identical over time, mid-motion, and not only in stills. A frame comes after its tick's trace line and the step's `wait_for`, before the screenshot steps that follow. `walk-video` is the walk with turns, jumps, a sprint and a sneak, a frame every 1 to 5 ticks (36 in its 159 ticks; "Frames over time" below).
- `hide_gui`, optional, is vanilla's F1 (`Hud.toggle`) for the whole run: no HUD, hand or crosshair, so the screenshots are the level alone. Both clients set it before joining (`walk-no-gui` is the walk with it).
- `hide_splash`, optional in `options`, is the accessibility option `hideSplashTexts`: the title screen's splash is a random line (or the date's), pulsing by the wall clock, so a scenario that shows the title screen hides it. The port has no splash yet.
- `title`, optional, lists steps on the title screen before the client joins, once the server is ready: `{"ticks": N}` waits N ticks (the client ticking without a level, Fabric's `waitTicks`), and screenshots and input steps as above. The title screen fades in over two seconds of the wall clock after the game loads, so a scenario waits that long before its first screenshot. Fabric's client game tests hold the panorama still (their `ScreenMixin` calls `holdSpin` as `Screen.extractPanorama` begins), and the port's scenario driver does the same, so the panorama is at its start in every screenshot. The title screen's panorama, `textures/gui/title/background/panorama_*.png`, comes from the launcher's asset index (the jar has 1-pixel placeholders), which the oracle client reads from Loom's cache and the port from `vanilla/<version>/assets/` (`tools/setup_vanilla.py`).
- `wait_for`, optional, lists clientbound packet types (`"minecraft:set_health"`) the server sends in answer to the step's last tick, like the damage of a landing that tick. After that tick and its trace line, the client doesn't tick until each type has been queued for its game thread more often than when the step began; then it handles everything queued, which it would have at its next frame anyway, and goes on. Below, "The server's answers".
- `tick_rate`, optional in `world`, paces the run on a server: the server is slowed down to that many ticks a second (`tick rate`), and both clients tick in step with it, one tick between each two of the server's. Below, "Paced scenarios".
- `setup`, optional, is a list of commands (without their slash) that build the scenario's course on the flat world, like `"fill -2 -60 8 2 -60 8 minecraft:oak_stairs[facing=south,half=bottom,shape=straight,waterlogged=false] strict"`. Physics scenarios use `fill` and `setblock` in their `strict` mode, which places each state as written, without shape updates from or to its neighbours (a fence's connections, a stair's corners), so the course is exactly what the commands say.

Before tick 0, both modes put the world in the scenario's state with the same commands, the scenario's `setup` before the player is put in place. A port joining a server must send the same ones:

```
gamerule advance_time false
gamerule advance_weather false
gamerule random_tick_speed 0
gamerule spawn_mobs false
difficulty normal
time set <time>
weather clear
gamemode <game_mode> @s
tp @e[type=!minecraft:player] 0 -1000 0
<setup…>
tp @s <x> <y> <z> <y_rot> <x_rot>
```

On a server, the client first waits until every chunk within its render distance is in the level. The server sends a chunk's light changes (`light_update`) only to a client for which the chunk is at the edge of what it has, a neighbour still to be sent making an edge (`ChunkHolder.broadcastChanges`, `ChunkMap.isChunkOnTrackedBorder`), and a chunk sent after the setup comes with the setup's blocks and with its light as the server's light engine has it then. The port used to start the setup once the first chunk batch had come (its stand-in for the loading screen), and its runs of `block-steps`, `water-current`, `slabs-and-fences` and `falls` got light updates and chunks vanilla's didn't; vanilla's own runs already had every chunk before the setup.

A paced scenario then sends `tick rate <tick_rate>` (Java's `Float.toString`, `tick rate 2.0`) and finds the server's ticks (below) before the rest. A command that places blocks (`fill`, `setblock`) waits, the client ticking, until the server has sent it at least one more block change (`block_update` or `section_blocks_update`, counted like `wait_for`'s packets) before the next command goes: the server sends a tick's block changes at its end, so each command's come in a tick of their own and are grouped the same way every run. Then the client waits for chunks to render (`areChunksRendered`, `are_chunks_rendered`): every chunk within the render distance in the level, and every chunk the server sends a player at that distance too (`ChunkTrackingView.isWithinDistance` with the neighbours it includes: 117 chunks at a render distance of 4), which a section at the render distance's edge waits for before it compiles (`LevelExtractor`'s `hasAllNeighbors`); the level's light caught up (no light update queued, of which a client runs some each frame, and no work left for its light engine), since a chunk's sections only become dirty once its light is in; and every visible section compiled (`hasRenderedAllSections`, which only counts the queued ones). Then at least 20 ticks, until the player is on the ground and the camera is at rest (`isCameraAtRest`, `is_camera_at_rest`; "Screenshots" below). The player is the offline player `rustcraft`. A course keeps clear of the spawn point (0.5, -60, 0.5), where the player is when the setup runs: a block filled there hurts it (`inWall`) if a server tick falls before the `tp`.

Right before tick 0 both clients start every texture atlas's animations over, each at its first frame, drawn into the atlas (the oracle client's `restartTextureAnimations`, the port's `restart_texture_animations`): the animations advance a tick at a time from the client's start, and how many ticks the join took varies, so a screenshot of water, lava or fire would otherwise show another frame each run. From then on both advance them once a frame with a tick, which is once a tick: Fabric's client game tests run at most one tick a frame (its `MinecraftMixin.captureTicksPerFrame`), and so does the port with a scenario's driver.

On a server, the client then sends a marker right before tick 0: a serverbound `minecraft:custom_payload` with the identifier `rustcraft:scenario_start` and no data (payload `18` followed by the identifier's ASCII). A vanilla server ignores it. Packet diffs use it to tell the join phase from the scenario, so a port joining a server must send it at the same point.

A run writes `<out>/<scenario>/trace.jsonl`, one line per client tick, as the tick ends (before the packets the client handles before its next tick):

```json
{"tick":0,"pos":["…","…","…"],"delta":["…","…","…"],"y_rot":"…","x_rot":"…","on_ground":true,"horizontal_collision":false,"vertical_collision":true,"sprinting":false,"crouching":false,"pose":"STANDING"}
```

`pos` and `delta` (`getDeltaMovement`) are doubles, and the rotations are floats. Where the client has other entities, the line ends with them, in the order it added them (`entitiesForRendering`), each its type and position after the tick: `"entities":[{"type":"minecraft:pig","pos":["…","…","…"]}]`; a line without other entities has no such field, so the scenarios recorded before it have the lines they had. Screenshots go to `<out>/<scenario>/screenshots/<name>.png`.

A scenario should move the player from tick 0: the client sends its position when it moved, or every 20 ticks without (`positionReminder`), and how many ticks the join took before the marker varies from run to run, so a scenario that starts standing still could send a reminder at a different tick each run.

### The server's answers

What the server sends back that changes the player arrives between client ticks, and when depends on the network and the server's clock: the client is stepped one tick at a time, much faster than the server's 20 a second, which runs in real time. A clientbound play packet is decoded on the Netty thread and queued for the game thread (`PacketUtils.ensureRunningOnSameThread`, `PacketProcessor.scheduleIfPossible`), and the game thread handles the queue at the start of every frame (`Minecraft.runTick`: `processQueuedPackets`, then `runAllTasks`, then `tick`), never inside a tick. Fabric's client game test parks the client right after `runAllTasks` of a frame that ticks (`MinecraftMixin`'s `postRunTasks`), and `runOnClient` runs its task right there, not through the game's queues.

So the oracle client used to write a tick's line from the next frame's pause, after that frame's packets: whatever had come in meanwhile was in it, or not. Landing from five blocks shows it: the server answers the move that lands (`ServerGamePacketListenerImpl.handleMovePlayer`, `doCheckFallDamage`, `Block.fallOn`, `causeFallDamage`) with `damage_event` at once, and at the end of the same server tick `set_entity_data` (the health), `set_entity_motion` (fall damage marks the player hurt, `markHurt`) and `set_health`, all to the player itself; the first recording of a five-block fall had that motion in the landing's next line. Two things make it deterministic, and both clients do them:

- the trace line is written as the tick ends: the oracle client's `MinecraftTickMixin` writes it at `Minecraft.tick`'s return (`TickTrace`), and the port's `OracleGameTest` after its `Minecraft::tick`. Re-recorded with it, the scenarios recorded before had the same traces, digest for digest (PROGRESS.md, 2026-10-23);
- a step that ends on such a tick waits for the answer (`wait_for`), so it's handled before the next tick, not at whichever tick it happens to come. The oracle client counts the packets queued by type (`PacketProcessorMixin`, `PacketArrivals`), sleeps while the client is parked, then has the client handle its queue (`client.packetProcessor().processQueuedPackets()`); the port counts in its `PacketProcessor` (`arrivals`) and runs the network without ticking.

What the answer holds isn't the client's, though. Players move on both sides (`MoveSimulationType.AUTHORITATIVE_SIDE_AND_SERVER`): every server tick, `ServerPlayer.doTick` runs the player's travel with gravity, then puts it back where the client last said it was (`absSnapTo`). So the motion the server sends (its player's `getDeltaMovement`) and the fall distance its damage comes from depend on how many of the server's ticks fell while the client was in the air: two recordings of the same five-block fall got a motion of (0, -0.0784, 0) and (0, -0.2305, 0), and 2 and 3 damage. A scenario takes care that this doesn't reach the trace: the answer is handled after the landing's line, and on the ground the next tick's collision ends whatever vertical motion it had; its horizontal motion (zero, the server's player has no input) is the same every run. Unpaced, the answer's packets themselves differ from run to run, so `oracle-diff`'s clientbound multiset can't match on a scenario with damage; paced (below), the server ticks once between each two client ticks, and they're the same every run.

`set_health` also comes on the server's own clock while the player regenerates (natural regeneration, every 10 ticks or so with a full food bar), so a scenario that waits for it turns regeneration off in its `setup` (`gamerule natural_health_regeneration false`).

The offline replay has the server's answers from a capture: at a step's `wait_for`, it takes the capture's clientbound packets after the marker in the order they came, up to the waited-for ones, and applies those that change the player (`set_entity_motion`, `set_health`, `damage_event`), after the tick's line like the live clients. A scenario that waits is only replayed where a capture is, so CI records `falls` with the port's own client, like the walk.

The server's own packets differed from run to run where a scenario's course was built, before the setup waited for each command's blocks: the server sends a section's block changes once a tick (`section_blocks_update`, or `block_update` for one), so how the setup's commands fell into its ticks decided how they were grouped. A scenario that ends just after the player crosses into a new chunk may or may not catch the server's `set_chunk_cache_center` and the new chunks before the client leaves (the server sends them a batch a tick, as many as the client's acknowledgements ask for), so a scenario ends well inside a chunk (`slabs-and-fences` was moved 4 blocks back into the spawn chunk for it). Both show in `oracle-diff`'s clientbound multiset, not in what the client sends or its trace. So do the light updates of a setup started before every chunk had come (above), and what the server works out on its own clock, which a paced scenario pins (below).

A summoned entity gets a random UUID, which its `add_entity` and the summon's chat feedback (its hover text) carry, so a scenario summons with one (`UUID:[I;0,0,1,1]`). A mob plays its ambient sound at random (`Mob.baseTick`, even with `NoAI`), each `sound` packet with a random seed, so a scenario's mobs are `Silent:1b`. A piston's sounds can't be silenced: the server plays them with a pitch and a seed from its level's random (`PistonBaseBlock.triggerEvent`), so `piston-push`'s clientbound multiset differs in those two `sound` packets from run to run (the port's first live run against vanilla's: only those two, their pitch and seed), while its trace and its packets from the marker are compared as any scenario's.

### Paced scenarios

The server ticks on its own clock, at fixed times: `MinecraftServer.runServer` adds a tick's nanoseconds to the next tick's time, and between ticks it handles the packets that came, so each tick sees the client's moves that came before it. The client ticks on its own clock too, so its ticks fall anywhere between the server's, and now and then two of them fall between two of the server's, or none. The server sees that, in what it works out from the player it simulates (above):
- the air under water. Every server tick its player's eyes are in water (`LivingEntity.baseTick`, in `ServerPlayer.doTick`), the server takes one from its air and sends it (`set_entity_data`), and adds four a tick once they're out. In one live run of `water` the port's player's eyes went under for one dip in three server ticks and vanilla's in two, from the same trace, and a flag the client's moves change (swimming) came with a different air value. In that run the port's ticks came 45 to 50 ms after the server's packets, just before its next tick, where a millisecond either way moves a tick to the other side; vanilla's came 0 to 47 ms after, with 22 to 170 ms between its ticks;
- the damage of a fall: the fall distance grows by the client's moves and by the server's own simulated move every server tick (above);
- an entity's position sync every 60 of its tracker's ticks (`ServerEntity.sendChanges`, a `move_entity_pos` of nothing), which comes in a run or not depending on how many server ticks passed from the summon to the client leaving.

A scenario with a `tick_rate` (2) pins them, and both clients do the same (`ServerTicks`, Java and Rust):
- once every chunk is in, the client sends `tick rate <tick_rate>`, waits for the client to have it (`ticking_state`), then for the server's next `set_time`: the server synchronizes the time every 20 ticks as a tick ends (`MinecraftServer.tickChildren`, flushed with the rest of the tick's packets at its end), and no command has made it send one out of turn since. Its arrival is when that tick ended;
- from then on until the client leaves, every client tick is released at a slot: that arrival plus half a server tick, plus whole ticks, so its packets come to the server halfway between two of its ticks, with 250 ms either way at 2 ticks a second. At its slot the client first handles what it has queued, so everything the server sent before it is handled before the tick, then the test acts (the setup's commands, the marker, the keys) and the tick runs. Each check a stage waits on (the commands' blocks, the position, the settling) is made at a slot, like Java's `waitFor` checks before each tick. The client leaves at the slot after its last tick, once the server has answered it;
- a tick that gets to its slot, or ends, more than a third of a server tick after the slot may have come to the server after its next tick. The run says so (`… ms after its slot`), and one of the scenario's ticks that does fails the run (`fell behind the server's ticks`), since the server's answers then aren't the scenario's: a client that gets to its slot that late waits for the next one, and the server ticks without it. `oracle_client.py capture` and `port_client.py capture` run a paced scenario that failed so up to three times in all;
- the oracle client's own tick timer keeps 20 ticks a second (`MinecraftTickTargetMixin`; vanilla's follows the server's rate, `Minecraft.getTickTargetMillis`), and it draws at most 10 frames a second (`maxFps`). At the server's rate its timer had it ready for a tick only on its own grid of the server's tick, and a slow frame put it behind the slots for good (560 ms, in one run); at 20 it's parked well before each slot. Neither changes what a tick computes: the rate only times the frames, and the frames llvmpipe draws at up to 120 a second took the CPU the server and the client need to keep to the slots. The port's timer keeps 20, it draws at most 10 frames a second too (its `framerate_limit`, the same frames llvmpipe draws taking the same CPU), and it ticks at most once a frame like Fabric's (`captureTicksPerFrame`), its driver called where Fabric parks the client (`TestDriver::before_tick`).

The server's rate doesn't change what a tick computes: the server's and the client's ticks run the same code at any rate. At 5 ticks a second, two vanilla runs of `water` had the same air tick for tick, and the port's run matched them, and so did two runs each of `falls` (the damage) and `entities`; but on this shared machine, at a load of 15 to 22, the oracle client's ticks came to the server up to 140 ms after their slots now and then, past the 100 ms that rate leaves, so the scenarios run at 2.

One difference between two vanilla runs is left that neither client makes: the join's first chunk, (0, 0), sometimes comes with a sky light layer for the section below the world where other runs have it empty (`emptySkyYMask`), the server's light engine having got further or not when it wrote the chunk (2 of 6 runs of `water`, no other run). It shows in the clientbound multiset, and such a run is run again.

### Offline replays

`rustcraft::oracle::client::replay` replays a scenario on the port's `LocalPlayer` without a server: the player put at the scenario's position and settled like the oracle client settles it (20 ticks, then until it's on the ground), then each tick what `Minecraft.tick` does for it (`commonTick`, the player's `tick`, `sendChanges`, then `client_tick_end`), with each step's keys held and its look set before the tick. It gives the trace, and the serverbound packets from the marker on (the marker, then each tick's), written by the game protocol, each `name payload` like the capture's. A test per scenario compares both with vanilla's run, strictly, line by line where vanilla's `vanilla/<version>/oracle/<scenario>/` is, and by MD5s of vanilla's trace and of its packets from the marker on (without what `oracle-diff` ignores by default), committed, everywhere: oracle-diff's strict phase, offline.

The level is replayed two ways:
- the flat preset (bedrock, two dirt, grass at -61) with the blocks the scenario's `setup` places and the entities it summons (`summon <type> <x> <y> <z> {…}`: where it says, in that order, which is where and in the order the server adds and sends them), which needs no capture and is what CI runs;
- where a capture of the scenario is (vanilla's, or the port's own in `target/oracle/<scenario>/`, which CI records for the walk), a `ClientLevel` filled from it the way the client's listener fills it: the configuration's registries, the login's level, and every chunk, forgotten chunk, block update, change of view and added or removed entity before the marker, in order. Its blocks below y = -32 must be the flat level's, block for block, so a course is what its commands say.

Where the port's own run on a server (`tools/port_client.py capture <scenario>`) wrote its `trace.jsonl`, its trace and its packets from the marker on are checked against the same digests. CI records the walk's, so CI checks the live client's walk too.

A new scenario is drafted on the port before vanilla records it: `SCENARIO=<name> cargo test --lib replays_a_draft -- --ignored` replays it on the flat level into `target/oracle/<name>-draft/` (checking nothing), which shows where the player lands and when, to put a `wait_for` on the right tick.

## 3. Packet captures

`packet-proxy` sits between a client and a vanilla server in offline mode. It writes `capture.jsonl`, one line per packet after framing and decompression:

```json
{"seq":0,"connection":0,"ms":0,"direction":"serverbound","state":"handshake","id":0,"name":"minecraft:intention","payload":"…hex…"}
```

`state` follows the protocol (`handshake`, `status`, `login`, `configuration`, `play`). Names come from `vanilla/<version>/generated/reports/packets.json`. `connection` counts connections in the order they were accepted. `ms` is for humans; diffs ignore it.

`tools/vanilla_server.py` gives every run a fresh world with fixed settings:
- offline mode, no compression, no whitelist;
- flat world with the scenario's seed, no structures, peaceful;
- `respawn_radius 0`, otherwise the spawn point is random;
- no time, weather or mob cycles;
- `rustcraft` as an operator, written to `ops.json` with its offline UUID.

`oracle-diff packets` compares the two directions differently, because the vanilla server can't produce byte-identical output twice:

- **Client → server packets** (the client's behaviour) are compared in two parts, split at the scenario-start marker:
  - *From the marker on*, they must match strictly: same order, same bytes.
  - *Before it* is the join and setup. The server runs in real time while the client is stepped one tick at a time, so how many ticks pass before the world is loaded varies. Per-tick packets (`client_tick_end`, `move_player_*`, `player_input`) are dropped, and the rest are compared as a multiset with exact payloads. A missing or changed `chat_command`, `client_information` or `accept_teleportation` still shows up.
  - A marker in only one capture is a difference. With no marker in either capture, the whole stream is strict.
- **Server → client packets** are compared as a multiset. Payloads are compared regardless of order, because the server writes tags, recipes, commands and chunk heightmaps in Java `HashMap` order, which changes from run to run. `--ordered` makes the comparison strict.
- **`--join`** compares only the join phase, gate 1's definition: on a connection whose captures both have the marker, the serverbound packets before it (as above) and the clientbound packets that came before the client sent it. A connection with no marker on either side is still compared whole, and a marker on one side only still differs.
- **Ignored by default** (`--no-default-ignore` turns this off) are packets that differ in every run:
  - `keep_alive`, `ping`/`pong`, `ping_request`/`pong_response`: random ids and clocks;
  - `login_finished`: a random session id;
  - `set_time`: sent on a timer;
  - `update_advancements`: timestamps;
  - `chunk_batch_*`: pacing based on the client's clock.

The port's runs come from `tools/port_client.py capture <scenario>`, the counterpart of `oracle_client.py capture`: a fresh `vanilla_server.py` (`--compression-threshold` turns compression on), `packet-proxy` in front of it, and the port (`target/release/rustcraft --quickPlayMultiplayer … --username rustcraft --headless --oracleScenario … --oracleOut target/oracle`) joining as `rustcraft`. The port's `OracleGameTest` (`src/rustcraft/oracle/client/`) does what the oracle client's `runMultiplayer` does: waits for the level to load, sends the same setup commands, waits for the scenario's position and every chunk within the render distance to be in the level (Java then waits for the renderer's sections, which come with the render track), settles 20 ticks and until the player is on the ground (and, with a renderer, the camera at rest), sends the marker, replays the scenario's ticks (each step's keys held and its look set before each tick) and disconnects. It writes `target/oracle/<scenario>/trace.jsonl`, `capture.jsonl` and `client.log`; screenshots come with the renderer.

`port_client.py check-join <scenario>` is gate 1 end to end: it captures the port's run and runs `oracle-diff packets --join` against vanilla's capture, exiting 0 when the join phases match. With `--compression-threshold N`, both runs have the server compress: the captures show packets inflated, so they only differ by the server's `login_compression`, and the port's run is compared with vanilla's run at the same threshold, `vanilla/<version>/oracle-compressed-<N>/<scenario>/`, which `check-join` records with `oracle_client.py capture … --compression-threshold N` when it isn't there.

The oracle client is vanilla under Fabric Loader and Fabric API (the client game test API needs it), which would send two serverbound packets an unmodded client doesn't: Fabric Loader patches `ClientBrandRetriever.getClientModName` to brand the client `fabric`, and Fabric API's networking registers the channels it receives with a `minecraft:register` custom payload once the game protocol starts. Those are Fabric's, not vanilla's, so the reference would be wrong, and the oracle mod undoes them with two mixins (`oracle/client/src/main/java/rustcraft/oracle/client/mixin/`): `getClientModName` returns `vanilla`, and Fabric's client-side network addons announce no channels (`createRegistrationPayload` returns null, which every registration they send goes through). Nothing else about the client changes: re-recorded with them, the walk scenario's trace and screenshots came out identical, and its packets differed only in those two (PROGRESS.md, 2026-10-22). Fabric's development launch also loads the game's classes from a remapped jar without signatures, so `Minecraft.checkModStatus` finds the client "very likely" modified and the title screen shows its version as "Minecraft 26.3 (Modded)"; a third mixin (`MinecraftModStatusMixin`) returns what the signed jar with vanilla's brand finds, "probably not", which changes nothing else a scenario shows (crash reports and F3's text read it too).

`oracle_client.py capture` starts the client first. `OracleGameTest` waits on the title screen until a file the runner creates once the server is ready, then joins, so the server has ticked about as long when the client joins as when the port joins its server, a second or two, however long the client took to start. Before, the server started first and ticked through the client's 25 s or so of startup, and timers on the server's tick count fell into a capture or not depending on that: the players' latency, a `player_info_update` every 601 ticks, came 5 s into the walk scenario in one reference capture and before the join in a re-recording.

## 4. Screenshots

The oracle client renders with OpenGL on Mesa's llvmpipe under Xvfb, so its output doesn't depend on the GPU. It turns off the vignette, view bobbing, vsync and clouds, sets particles to minimal, and uses Fabric's test defaults (no chunk fade, no music, no tutorial). The port must render with the same settings for screenshots to be comparable. `oracle-diff image` reports how many pixels differ and the largest channel difference, and can write a heatmap.

The rest of its options come from `oracle/client/options.txt`, which `oracle_client.py` copies into the client's run directory before every run. The game reads `options.txt` from there and writes it back on exit, and Fabric's test defaults keep whatever it read for every option they don't set, so a run used to depend on what earlier runs in the same checkout had left: a first run applies the default `fancy` graphics preset at startup (`Minecraft`'s constructor), which sets the anisotropic filtering among others, and a later one reads `custom` back and applies nothing. The walk reference was recorded on a later run, and a fresh checkout's first run differed from it in 14% of each screenshot's pixels, the grass towards the horizon. The pinned file is the options that reference was recorded with: the `custom` preset, `maxAnisotropyBit` 2, RGSS texture filtering and 4 mipmap levels. Fabric's own default asks for no anisotropic filtering with `maxAnisotropyBit` 0, which 26.3's range (1 to 3) refuses, logging "Illegal option value 0 for Anisotropic Filtering" and keeping 2.

The port renders the same way: `tests/opengl_frame.rs` runs `rustcraft` under `xvfb-run -a` with the oracle client's environment (`LIBGL_ALWAYS_SOFTWARE=1`, `GALLIUM_DRIVER=llvmpipe`, `SDL_VIDEO_DRIVER=x11`), and skips without `xvfb-run`. Xvfb's GLX visuals come from Mesa's dril, which asks the GPU's DRM node for its configs through GBM; on a machine without one (CI's runners, a container) dril falls back to a fixed list with no sRGB-capable visual, the framebuffer vanilla asks for, and SDL finds no GLX visual. So CI sets `SDL_VIDEO_FORCE_EGL=1`, which the runs inherit: SDL's EGL path on the same Xvfb and llvmpipe, which renders the same pixels (the frames render into the main target's textures, not the window's framebuffer). The oracle machine has a DRM node, and its Xvfb takes GLX, like vanilla. It checks:
- the device: `--device-info` prints the three lines vanilla logs about it (`Minecraft.java`'s "Using graphics backend…", "Using graphics device…" and "Using graphics device extensions…", the extensions in their `HashSet`'s order), whose flags follow from the extensions, and which equal the oracle client's log when this machine has one, with the shader goldens' flags;
- frames read back like `Screenshot.takeScreenshot`: `--screenshot` clears the main render target like `GameRenderer.render` (to `GuiRenderState.clearColorOverride`'s transparent black, or the loading overlay's brand background), and every pixel of the PNG is that color with its alpha made opaque, RGBA at the target's size like vanilla's; and a render pass clearing GL's lower left quarter shows up at the image's lower left.
- every pipeline `ShaderManager.reload` compiles (the 190 required and 2 optional ones) compiles and links on the driver from the GLSL vanilla hands it (`--compile-pipelines`);
- the block atlas: `--dump-atlas` loads it like the client and uploads it like `TextureAtlas.upload` (each sprite drawn into each mip level by `pipeline/animate_sprite_blit`, animated ones from their first frame's texture), then writes it like `dumpContents` (`<id>_<level>.png` and `<id>.txt`). Its pixels are known from the goldens: the layout and the sprites' mip levels are vanilla's, and with nearest filtering and clamped edges the pixel `k` into a sprite's padded place at level `L` is the sprite's texel `k - p_L` clamped into it, each texture coordinate on a texel's center since every size and padding is a multiple of `2^L`; llvmpipe zeroes new textures, so the rest is transparent black. All five levels match those pixels exactly;
- draws: `--fill` draws `GuiGraphicsExtractor.fill`s through `pipeline/gui` the way `GuiRenderer` does (a `BufferBuilder` mesh of `ColoredRectangleRenderState`'s vertices, the shared quad indices, the GUI's orthographic projection and model view in their uniform blocks), and the test knows every pixel: the fills' corners are whole pixels at the GUI scale, so no pixel's center lies on an edge, an opaque color blends to itself, a fill with alpha 0 is discarded, and later fills cover earlier ones.
- a resize: `--render-scenario … --start-size 427x241` renders the walk's spawn view's first frame at 427 by 241, then the window resized to the scenario's 854 by 480 (`GameRenderer.resize`: the main target made again, the visible sections worked out again, the projection and the GUI's scale following the framebuffer's size); the screenshot is vanilla's spawn view, by its digest, on the oracle's driver.

The port's screenshots come from its runs on a server: a scenario with screenshot steps makes the port render (offscreen when it's `--headless`), and `OracleGameTest` renders a frame at a partial tick of 1 and reads it back at each step, like `OracleScreenshot.take`, after waiting, like the oracle client, for every visible section to compile (`hasRenderedAllSections`) and for the camera to come to rest. So the settling also waits until both are the same as the tick before. The oracle's client was at rest by then anyway, and its screenshots didn't change with the waits (`walk-no-gui`, `walk`, `sky-sunset`, `sky-night` and `sky-sunrise` recorded again: the same digests). `tools/port_client.py` runs such a scenario's port under `xvfb-run -a` with the oracle client's environment (CI adds `SDL_VIDEO_FORCE_EGL=1`, see above). The port renders with the oracle's `options.txt` where it differs from the defaults: no chunk fade, cloud range 64, RGSS texture filtering. `rustcraft --render-scenario SCENARIO --capture CAPTURE --screenshot out.png` renders a scenario's first view offscreen without a server, from the level a capture's packets fill (`CapturedLevel::from_capture_with_light`: the chunks' and the light updates' light run like the client's listener runs it, all of it before each block change, since the setup's blocks come ticks after the chunks), its clocks set by the capture's `set_time`s, the player settled where the scenario puts it: the same pixels as the live run's. ### Frames over time

A step's `screenshots_every` takes a frame every so many ticks, so a scenario can be compared as a video: `walk-video` walks, sprints, sprint-jumps, stops, turns on the spot, walks back with a jump, looks up, jumps on the spot, looks down at the ground and strafes sneaking, with the HUD and the hand, 36 frames in 125 ticks, after 34 ticks of looking around without frames (below). Mid-motion frames check what stills can't: the camera's position between ticks (`Mth.lerp` at the frame's partial tick), the field of view easing in and out with the sprint (`Camera.tick`'s modifier), the eye height easing with the sneak, the hand's sway behind a turn (`xBob` and `yBob`), the sky and terrain from a moving camera.

Where in the frame the screenshot is taken has to be the same in both clients. Fabric parks the client in a frame that ticks right after `runAllTasks` (`MinecraftMixin.postRunTasks`), so after the frame that drew the last tick and the next frame's packets and tasks, but before that frame's `textureManager.tick()` and its tick; `OracleScreenshot.take` renders there with `DeltaTracker.ONE`, a partial tick of 1 for the level, the entities and the GUI alike. The port's driver is called at the same point (`TestDriver::before_tick`, before the textures' tick) and runs the steps between ticks there, the screenshots at a partial tick of 1 and the input steps, before a paced tick's slot, like Java's `replay` before `ServerTicks.tick`. It used to take them as the tick ended, before the texture animations' next tick, and its animations started over a tick later than vanilla's (the oracle client starts them over while parked, before the frame's texture tick): a screenshot of water or lava came a tick behind.

What a frame shows mustn't depend on the frames drawn between ticks, whose partial ticks and number follow the clock. Four things in vanilla carry over from those frames, and a scenario keeps clear of them:
- the block the player looks at: `Minecraft.renderFrame` picks it at the frame's partial tick (`pick(worldPartialTicks)`), and the screenshot's frame doesn't pick, so its outline is that of the block picked last. While the player moves, `walk-video` looks no lower than 10 degrees, where nothing within reach is hit; it looks at the ground only standing still, where every partial tick picks the same block. (The port picks at the screenshot's partial tick, which is the same block there.)
- the sections' occlusion graph: a camera moving into another 8-block cell (`SectionOcclusionGraph.invalidateIfNeeded`, `floor(pos / 8)` on each axis) starts a full update on a background thread, whose result a frame may or may not have. `walk-video` keeps the camera within x and z 0 to 8 and y -64 to -56.
- the frustum's culling, applied again when the camera's rotation crosses 2 degrees (`LevelExtractor.extract`, `floor(rot / 2)`), at the camera's position in the first frame after: `walk-video` turns only standing still, so every frame's camera is in the same place.
- the sections compiled: a client compiles only the sections in view (`LevelExtractor.extract` queues the visible dirty ones), and the occlusion graph only goes on through a compiled section, so turning to look somewhere new for the first time shows the far sections a ring a frame as they compile and the graph reaches past them. How far that got by a frame depends on the frames drawn since the turn, and on when vanilla's worker threads finished compiling (the port compiles a frame's sections at its end): a first run of `walk-video` without the look-around had 5 of its frames, 0 to 2 ticks after a turn, short of sections along the horizon in vanilla's (4,717 pixels at most) and not in the port's. `walk-video` looks all four ways first, 8 ticks each standing still, so every section around is compiled before the frames.

The server can answer differently too. A client that says it's on the ground when the server's player didn't land on anything in its own move gets the blocks under it sent again (`ServerGamePacketListenerImpl.forceSendPlayerSupportBlocks`, "standing on air", once every 200 ticks at most): in that first run vanilla's landing from the jump on the spot got one `block_update` and the port's didn't, from the same packets, as the server's ticks fell. `walk-video` is paced (`tick_rate` 2, "Paced scenarios" above), which pins the server's ticks between the client's.

The view's rotation and the hand's sway come from the tick (`look` sets the rotation before it, `baseTick` makes it the old rotation too), so frames between ticks don't rotate.

`cargo run -p oracle-diff -- video target/oracle/walk-video --out walk-video.gif --scale 2` plays a run's frames as a GIF in game time; with two runs, side by side with the heatmap of where they differ.

## GL profiles: a Mac's OpenGL on llvmpipe

A Mac's OpenGL isn't llvmpipe's: Apple's stops at 4.1 core, without most of the extensions vanilla's `GlDevice` and `GlHeuristics` look for, so every fallback they have runs there, and nowhere here. A GL profile runs both clients on llvmpipe restricted to a platform's OpenGL through Mesa's overrides, into references of its own; the default references stay as they are. `oracle/gl-profiles.json` holds each profile's environment, which `oracle_client.py` and `port_client.py` (`--gl-profile`) and `tests/opengl_frame.rs` read.

`macos` is Apple's OpenGL 4.1: `MESA_GL_VERSION_OVERRIDE=4.1FC` (a forward-compatible 4.1 core context, what a Mac gives for the 3.3 core context vanilla asks for), `MESA_GLSL_VERSION_OVERRIDE=410`, and `MESA_EXTENSION_OVERRIDE` taking away each extension vanilla or the port looks for that a Mac lacks: `GL_ARB_buffer_storage`, `GL_ARB_clip_control`, `GL_ARB_multi_draw_indirect`, `GL_ARB_base_instance`, `GL_ARB_shader_draw_parameters`, `GL_KHR_debug`, `GL_ARB_debug_output`, `GL_ARB_direct_state_access` and `GL_ARB_vertex_attrib_binding`. The list is those checks against Apple's OpenGL capability tables: of what they look for, a Mac has `GL_EXT_texture_filter_anisotropic`, `GL_ARB_draw_indirect` and `GL_EXT_debug_label`. Two of Mesa's limits make the profile a little stricter than a Mac:
- Mesa can't take away its always-on extensions one at a time (`KHR_debug`, `ARB_debug_output`, `ARB_direct_state_access`, `ARB_vertex_attrib_binding` and 40 more: "cannot be disabled"), and asking for one takes them all out of the list, `GL_EXT_debug_label` with them. Vanilla only labels with the debug options' labels on, which neither client turns on.
- `GL_ARB_multi_draw_indirect` and `GL_ARB_draw_indirect` share one flag in Mesa, so `GL_ARB_draw_indirect` goes too: the device's indirect draw count is 0 where a Mac's is 1. Neither client draws indirectly without base instances (`LevelRenderer.multiDrawIndirectAvailable`), so the terrain draws one section at a time either way.

Both clients then log `4.1 (Core Profile) Mesa 26.0.8-1ubuntu0.3` and `GL_EXT_texture_filter_anisotropic` alone, depth runs from -1 to 1 (`isZZeroToOne` false: no `glClipControl`, the projections' other depth range, the shaders without `RENDERPEARL_DEPTH_IS_ZERO_TO_ONE`), and the paths a Mac takes run: buffers made with `glBufferData`, vertex arrays set up with `glVertexAttribPointer` on each bind, the terrain through `DrawSeparate` (each layer's non-multidraw pipeline, a draw per section with its section's uniform block), no shader draw parameters, no debug output. What only a Mac shows: `isExplicitDepthRequired` (Apple's renderer name, which only the order-independent transparency's shaders read), the error `GlStateManager` drops after clears on macOS, and Apple's own rasterization, which no screenshot here predicts.

Vanilla's runs under the profile are in `vanilla/26.3/oracle-gl41/`, recorded with `oracle_client.py capture <scenario> --accept-eula --gl-profile macos --out vanilla/26.3/oracle-gl41` (`walk-no-gui` and `walk`), and the port's in `target/oracle-gl41/` (`port_client.py capture <scenario> --accept-eula --gl-profile macos --out target/oracle-gl41`), compared with `oracle-diff dir --strict`. Vanilla's screenshots under the profile are its default ones, bit for bit: neither the depth range nor drawing the terrain a section at a time moves a pixel of these views. `tests/opengl_frame.rs` checks the device's lines on the profile, the walk's spawn view rendered offline under it, and the port's runs' screenshots, by vanilla's digests under the profile (`VANILLA_SCREENSHOTS_GL41`); CI's `frames` job records the port's two runs under it.

## Backends: vanilla's Vulkan on lavapipe

Vanilla 26.3 has a Vulkan backend of its own (`com/mojang/renderpearl/backend/vulkan/`), which `--graphicsBackend vulkan` picks (it falls back to OpenGL when Vulkan fails, so a run checks its log says `Using graphics backend Vulkan`). Both clients run it on Mesa's lavapipe under Xvfb, the Vulkan side of the same Mesa (`mesa-vulkan-drivers` 26.0.8-1ubuntu0.3, the loader `libvulkan1` 1.4.341), through SDL's `VK_KHR_xlib_surface`: `oracle_client.py --backend vulkan` passes the oracle client `-Poracle.backend=vulkan` (`oracle/client/build.gradle`), and `port_client.py --backend vulkan` the port `--graphicsBackend vulkan`, each with `VK_DRIVER_FILES` set to lavapipe's ICD. Vanilla's runs are in `vanilla/26.3/oracle-vulkan/` (`walk-no-gui`, `walk`), the port's in `target/oracle-vulkan/`, compared with `oracle-diff dir --strict`; the default references stay as they are.

Vanilla's Vulkan frames are their own reference: they differ from its GL frames by the two drivers' rasterizers (`walk-no-gui`'s spawn in 5,441 pixels, by at most 2). On Vulkan a copy's callback isn't a fenced task but runs when the encoder's destruction queue comes round to the copy's submit again, two submits on, so the oracle client's screenshot submits (nothing) while it waits for the readback there (`OracleScreenshot`); its GL path is unchanged. Two vanilla runs of `walk-no-gui` on Vulkan (`check-determinism --capture --backend vulkan`) match; a first one differed from them by a `player_info_update`, the server's 601-tick latency update coming before the end of a run that took longer, so the reference is the first of the two (`oracle-determinism/a`).

`tests/opengl_frame.rs` runs its checks on the Vulkan backend too (skipping where lavapipe isn't installed): the device's lines against vanilla's Vulkan log (`ORACLE_DEVICE_VULKAN` with `RUSTCRAFT_ORACLE_DRIVER=1`), every pipeline compiled from vanilla's SPIR-V, the cleared frames, the readback's orientation, the GUI fills, the walk's spawn view rendered offline, and the port's live runs' screenshots, by vanilla's Vulkan digests (`VANILLA_SCREENSHOTS_VULKAN`). CI's `frames` job installs lavapipe at the snapshot's version and records the port's two runs on it. `VulkanConst`'s tables have goldens (`VulkanSuites`: every enum constant, usage and write mask, 2,992 cases).

## Soak: the live client on a generated world

The scenarios' worlds are flat, with few kinds of blocks. `port_client.py soak` joins the port's live client (headless, straight to the server, no proxy) to a fresh `vanilla_server.py` world of a preset (`--preset normal`, seed 0 unless `--seed`, structures on), and takes the player around it: the spawn, plains, a forest, a desert and the caves under it, an ocean, a village and the caves under the spawn, `--seconds-per-stop` at each (20 by default). Each place comes from the server's `locate`, and its chunks are force-loaded until generated before the player goes there, so every block state, block entity and biome the server sends there reaches the client's chunk handling, light, collisions and tints. It exits 1 if the client exits early, leaves the server (a panic while handling a packet disconnects), or logs a panic or code that isn't ported, printing those lines with their counts and the end of the log (`target/soak/client.log`), and 0 otherwise, with each stop and where the server has the player at its end. At the end it stops the server first, so the client is disconnected and exits on its own, printing the packets it skipped as `Unported` by type, which the report lists, the most first: what to port next.

`--render` runs the client in a window under `xvfb-run` instead of headless, so it renders a frame each time round its loop like vanilla, and the tour goes through the renderer too: every visible section of each stop compiled, the sky, the fog, fluids.

The soak is about the world, not the player's physics, so it keeps the player clear of what the player's port doesn't do yet: the server's ticks are frozen (`tick freeze`, so no fluid flows into what the soak builds), and at each stop the player stands on a 3 by 3 platform the soak builds at a chunk's middle, in a chunk section emptied of fluids (on the surface, the first section above the ground; underground, deepslate around a small room at -47). The spawn stop is built before the client joins, and the world spawn moved onto it. CI runs it with 5 seconds a stop.

## Stalls: the connection's own thread

`port_client.py stall` joins the port's live client (headless, no proxy) to a fresh flat `vanilla_server.py` world with `rustcraft --stall 40` (`src/rustcraft/stall_test.rs`): once the level is ready, the game thread sleeps 40 seconds in one tick, the way one long frame on a slow machine stalls it, then the client goes on for 20 seconds, still connected, and disconnects. The server sends a keep-alive every 15 seconds and drops a client that hasn't answered the last one when the next is due, so a client whose game thread reads the connection is gone by then (`lost connection: Timed out`); vanilla answers keep-alives on Netty's thread, and so does the port (PORTING.md, "The connection's threads"). It exits 0 when the client exited 0 after the stall and the server logged no timeout. CI runs it.

`RUSTCRAFT_BINARY=path` makes `port_client.py` run that build instead of building the tree's, so a long live check can run on a frozen build while the tree changes.

## Benchmark: the same scene in both clients

Gate 5's numbers come from `tools/bench.py`, which runs vanilla and the port on the same world with the same settings and measures the same points of both. A bench, `oracle/bench/<name>.json`, is a world (seed and level type), the clients' options (window, field of view, GUI scale, render distance 12, `maxFps` 260, which is unlimited), a warm-up at the world's spawn, a path of teleports 48 blocks apart along +x that loads chunks while the player moves, and a view held at a spot far from the path, whose chunks none of the path's are. `terrain` is the normal preset of seed 0, 160 blocks up looking 25° down over the land; `flat` the flat preset, standing on the grass.

```sh
flock /tmp/rustcraft-oracle.lock python3 tools/bench.py terrain --runs 3 --perf --accept-eula     # both clients, 3 runs each
flock /tmp/rustcraft-oracle.lock python3 tools/bench.py flat --runs 3 --clients port --accept-eula
flock /tmp/rustcraft-oracle.lock python3 tools/bench.py terrain --runs 0 --capture --accept-eula  # the offline benchmark's capture
target/release/rustcraft --benchLevel target/bench/terrain/capture.jsonl                            # the offline benchmark
```

One vanilla server serves a session: it generates the bench's chunks first (force loaded, then released), with its ticks frozen, its entities killed (the port draws none yet) and a barrier under each spot. Each client then joins it in turn, alternating which goes first, windowed under its own Xvfb on llvmpipe like the oracle's runs, and the server's console takes the player along: the spawn for `warmup_seconds`, each spot of the path for its `seconds`, then the hold's spot, which settles for `settle_seconds` and is held for `seconds`. The player's saved data is deleted between runs, so every run joins at the spawn: the server logs the player leaving before it saves them, so `bench.py` deletes what comes until nothing has for a second (a session once stopped on a file the server renamed as it was deleted). The server runs with `vanilla_server.py --no-watchdog` (`max-tick-time -1`): generating a force-loaded block of chunks is one server tick, which took over the watchdog's minute once at a load of 42.

**Vanilla is the unmodified client jar**, launched like the launcher launches it: the launcher's default JVM flags for a new installation (`-Xmx2G -XX:+UnlockExperimentalVMOptions -XX:+UseG1GC -XX:G1NewSizePercent=20 -XX:G1ReservePercent=20 -XX:MaxGCPauseMillis=50 -XX:G1HeapRegionSize=32M`), the version's JVM arguments for Linux from `version.json`, the launcher's asset index, and JDK 25 (the version's `javaVersion`). Its game directory is its own, with the oracle client's `options.txt` and the bench's options on top, no inactivity frame limit, no sound and no Realms notifications. It's measured by JFR's method tracing (`jdk.MethodTrace`, JDK 25), which only times: started once the player has joined (`jcmd JFR.start`), so it doesn't slow the startup, with no other JFR event, and turned into the port's events by `tools/JfrEvents.java`. The warm-up gives its JIT the spawn's chunks and frames before anything is timed.

**The port** is the release build, run with `--bench BENCH.json`, which sets the same options, and `--benchOut FILE`, which records the same points (`src/rustcraft/bench.rs`) from a thread of its own. A client `port@BINARY` runs another build, to compare two builds on one world.

The points, the same methods in both:

| Event | Vanilla (traced) | Port (recorded) |
| --- | --- | --- |
| `frame` | `Minecraft.runTick` | `Minecraft::run`'s turn |
| `submit` | `GlCommandEncoder.submit`, after the blit to the window | right before `present`, after the blit |
| `tick` | `Minecraft.tick` | `Minecraft::tick` |
| `compile` | `SectionCompiler.compile` (worker threads) | `SectionCompiler::compile` (worker threads, the render thread for a section the player changed) |
| `light` | `ClientLevel.update` (the queued light updates, then the engine's) | `ClientLevel::update` |
| `chunk` | `ClientPacketListener.handleLevelChunkWithLight` on the render thread | the game thread's half of the same handler |

What a run reports (`summary.json` has every run's, the table the median and range of the runs):
- **startup**: the process's start (`/proc`) to the server's "joined the game", which includes reaching the server: both clients connect at once (`--quickPlayMultiplayer`).
- **held view**: frames a second (frame events in the 30 seconds held), a frame's time (one frame's start to the next), the time from a frame's start to its submit, and the CPU time of the render thread and of the whole process (`/proc/<pid>/task/<tid>/stat`) divided by the frames. With `--perf`, 10 more seconds of the render thread sampled by `perf record` (sudo) split into the client's own code, the driver's (Mesa's libraries, X11's, and code without a symbol, which is llvmpipe's JIT-compiled shaders; vanilla's JIT-compiled Java is named by the JVM's perf map, `jcmd Compiler.perfmap`) and the kernel's. The client's share is "CPU per frame outside the driver".
- **loading**: while the path's chunks come, frames a second and frame times, section compiles a second and each compile's time (wall time: vanilla's run on worker threads beside llvmpipe's), each chunk's handling on the game thread, and the light updates' time per chunk.
- **settle**: the hold's teleport to the end of the last section compile before the hold: how long everything visible takes to compile from nothing, the server's sending included (the same server for both).
- **ticks** and **resident memory** (VmRSS at the end of the hold, VmHWM).

Neither client is limited to a frame rate, so on this machine's llvmpipe a frame's time is mostly the driver's rasterizing, on llvmpipe's threads; the render thread's CPU and its share outside the driver are what say something about the clients themselves.

Vanilla does work the port doesn't do yet, and the numbers include it: entities and block entities (none in the bench's view but the player), particles (minimal), sound, `animateTick`, chat. Both compile sections on worker threads, with the oracle's `prioritizeChunkUpdates:1` (those the player changed on the render thread).

**The offline benchmark**, `rustcraft --benchLevel CAPTURE`, needs no server or window: it puts the chunks of a capture of a bench's join (`bench.py --capture`: the port's join through packet-proxy, the warm-up long) in a level the way the listener puts them, works out their light, then compiles every section of each chunk whose neighbours are there, timing each part in the thread's CPU time, which other processes on the machine don't add to. It prints the times and an MD5 of every mesh's vertex and index bytes and every visibility set, in a fixed order: an optimization of meshing, light or chunk handling must leave the digest as it was. `perf stat -e instructions:u` of it is a measure a busy machine doesn't move. Where outputs go: `target/bench/<bench>/`.
