# Testing against vanilla

The real game is the source of truth. Every check runs vanilla and the port on the same input and compares the outputs, from most precise to least:

| Layer | Vanilla side | Compared by |
| --- | --- | --- |
| 1. Function goldens | `oracle/golden/` calls real methods from `client.jar` | `cargo test` |
| 2. Tick traces | `oracle/client/` (a Fabric mod) records the player every tick of a scenario | `oracle-diff trace` |
| 3. Packets | `packet-proxy` records client ↔ vanilla server traffic | `oracle-diff packets` |
| 4. Screenshots | `oracle/client/` takes screenshots at scenario checkpoints | `oracle-diff image` |

Draw-call streams from the renderer (renderpearl) will become layer 5 once the port renders.

Everything vanilla produces lands in `vanilla/<version>/`, which is gitignored. `MINECRAFT_VERSION` pins the version.

## Commands

```sh
python3 tools/setup_vanilla.py                                    # once per version
python3 tools/golden.py && cargo test                             # layer 1
python3 tools/golden.py com.mojang.blaze3d.platform.NativeImage   # only these suites, keeping the other files
python3 tools/oracle_client.py run walk                           # layers 2 and 4, singleplayer
python3 tools/oracle_client.py capture walk --accept-eula         # layers 2–4 on a fresh vanilla server
python3 tools/oracle_client.py check-determinism walk --capture --accept-eula
python3 tools/port_client.py capture walk --accept-eula          # layer 3, the port on a fresh vanilla server
cargo run -p oracle-diff -- packets --join vanilla/26.3/oracle/walk/capture.jsonl target/oracle/walk/capture.jsonl
python3 tools/port_client.py check-join walk --accept-eula       # gate 1: the two lines above
python3 tools/port_client.py check-join walk --accept-eula --compression-threshold 256
python3 tools/oracle_client.py capture walk --accept-eula --ping  # the server list's ping, vanilla's
python3 tools/port_client.py capture walk --accept-eula --ping    # and the port's (rustcraft --ping)
cargo run -p oracle-diff -- packets vanilla/26.3/oracle/walk-ping/capture.jsonl target/oracle/walk-ping/capture.jsonl
cargo run -p oracle-diff -- dir vanilla/26.3/oracle/walk target/oracle/walk
```

Wrap the ones that start a server, a client or the proxy in `flock /tmp/rustcraft-oracle.lock`: they use fixed ports, and the machine is shared.

`--accept-eula` accepts Mojang's EULA (https://aka.ms/MinecraftEULA) for the local server. Running a server requires it.

## Encoding rules

Shared by every file below:

- Floats are the lowercase hex of their raw IEEE 754 bits, as JSON strings: 8 digits for `float`/`f32`, 16 for `double`/`f64` (`1.0f` → `"3f800000"`). Comparisons are bit-exact, so `-0.0 != 0.0`. The one exception is that any NaN matches any NaN: NaN bits even differ between two runs of the golden generator, since the same operation can give NaNs of either sign depending on when HotSpot's JIT compiles it, which varies from run to run.
- `int`, `long`, `short` and `byte` are JSON numbers. A `char` is a number (its UTF-16 code unit). A `boolean` is a JSON bool.
- A `String` is a JSON string. Arrays and Java records are JSON arrays (records in component order). A `UUID` is `[most, least]`.
- Files are JSON Lines: one object per line.

## 1. Function goldens

`python3 tools/golden.py` compiles `oracle/golden/` against the client jar and writes one file per class to `vanilla/<version>/golden/<binary class name>.jsonl`, e.g. `net.minecraft.util.Mth.jsonl`.

The generator bootstraps the game first, like the game's own tests (`SharedConstants.tryDetectVersion()`, then `Bootstrap.bootStrap()`): some classes only load once the registries exist (`ConfigurationProtocols`, whose clientbound template holds the dialog packet), and some members need the game's version (`KnownPack.vanilla`). Bootstrapping changed no golden case, and it sends `System.out` to the log, so the generator prints its progress to the stream from before.

Static methods are covered by reflection. Every public static method whose parameter and return types have a generator (or that returns `void`) gets:
- edge cases (zeros, signed zeros, NaN, infinities, MIN/MAX, angles, powers of two, non-ASCII strings);
- 500 seeded random inputs;
- for `Mth.sin`/`cos`, every entry of their lookup table;
- for `Math.sin`/`cos`/`tan`/`log`/`pow`, which HotSpot computes with its own assembly, 20,000 more inputs each, spread over every path through it, since last-bit differences between libms are rare;
- for `Mth.atan2`, angles that read every entry of its tables;
- for `Math.hypot`, 6,000 more spread over every path through fdlibm's code, with its thresholds and the point where it switches formulas;
- for `MatrixUtil.eigenvalueJacobi` and `svdDecompose`, matrices like the ones `Transformation` decomposes, and ones where `approxGivensQuat` switches to a quarter turn. `eigenvalueJacobi` takes at most 1,024 steps (`where()`): billions would take minutes, and the game takes 5;
- for `Mth.rayIntersectsAABB`, the rays `AABB.clip` gets (below), as a start and a direction.

A random value is one of its generator's edges one time in eight, so edges also meet random partners, and otherwise a fresh one. The exception is an edge whose encoding is longer than 16,384 characters (`Values.MAX_DRAWN_EDGE`), which gets a fresh value instead. Those edges hold a string at a codec's limit of 32767 units, like a `KnownPack`'s parts, a brand or a property's value. The edges already cover each of them, and drawn at random they came back in most random lists and pairs: `ServerboundSelectKnownPacks`' file was 1.4 GB of them.

Arrays (`byte[]`, `int[]`, `long[]`) are JSON arrays of numbers, and each call gets its own copy, so `after` shows what a method wrote into one (`readBytes`, `readFixedSizeLongArray`). A `CharSequence` is a string, and a `Charset` is UTF-8, the only one the game's packets use, written as its name.

A `RandomSource` argument is a `LegacyRandomSource` seeded with the argument. Its next `nextLong()` after the call is recorded in `after` (one slot per argument), so how many values a method draws must match too. A static method taking it first is checked with `golden.check_random`; anything else (`Vec3.offsetRandom`) with `golden.check_mut`, to which `golden.rs` passes a `LegacyRandomSource` decoded from the seed and encoded as its next `nextLong()`. Any other argument a method wrote to gets its state afterwards in its slot (`MatrixUtil.checkProperty` adds to its matrix's properties). An empty slot means the argument didn't change, or is the returned object, which `result` already shows; the port's argument must then equal what it was or the result. A `void` method's result is null, so `after` is all it shows (`svdDecompose` writes its matrix's parts into four arguments). The port checks those with `golden.check_mut`, whose function takes every argument as `&mut`.

`java.lang.Float.toString` and `Double.toString` (the JDK's `FloatToDecimal` and `DoubleToDecimal`, which every `toString` printing a float goes through) get the edges and random values, and where their digits and format change: every exponent's smallest, middle and largest significands of either sign, each power of ten and an ulp either side, the plain and scientific forms' thresholds (1.0E-3, 1.0E7), the smallest subnormals, whole numbers, and 30,000 random values, half of them any bits and half in the game's magnitudes.

DataFixerUpper's `DataResult` has a program suite (`DataResultSuite`): 2,000 programs on results of ints, each made one of the six ways (`success` with or without a lifecycle, `error` with or without a partial value and a lifecycle) and run through ops (`map`, `flatMap`, `ap`, `apply2`, `apply2stable`, `apply3` with results made the same ways, `setPartial` both ways, `mapError`, `setLifecycle`, `addLifecycle`, `promotePartial`, `resultOrPartial`, `getOrThrow`, `getPartialOrThrow`, `mapOrElse`, `hasResultOrPartial`, `isSuccess`, `toString`), each step the op's output and the result afterwards, `["success", value, lifecycle]` or `["error", message, partial, lifecycle]`, a lifecycle `"Stable"`, `"Experimental"` or `["Deprecated", since]`. The functions are fixed ones of ints (`x * 2 + 1`, `a * 3 + b`…), whose overflow wraps.

`NbtOps.INSTANCE` has a suite of its own (`NbtOpsSuite`): every method on `NbtValues`' tags (each kind's edges and 300 random ones), with results as `DfuValues` encodes them (`["success", value, lifecycle]` or `["error", message, [partial] or [], lifecycle]`, a number `[box, value]`); merging into lists and arrays with tags of their elements' kind half the time, so arrays stay arrays or become lists; merging into compounds, ends and other tags with string keys and others, from a `LinkedHashMap` and from `getMap` of a compound; `getMap`'s `MapLike` (its `toString`, entries and lookups by string and by tag); `convertTo` itself; and 300 programs each of the list and record builders' ops (`add` of tags, results and keys that aren't strings, `withErrorsFrom`, `setLifecycle`, `mapError`), then two builds, the second of what the first left.

DataFixerUpper's codecs have a suite on NBT (`DfuCodecSuite`, `com.mojang.serialization.Codec`): the primitive codecs and codecs made with each combinator the text components reach (`listOf` with and without sizes, `either`, `xmap`, `comapFlatMap`, `flatComapMap`, `flatXmap` and `validate` with errors and partial values, `withAlternative` both ways, `fieldOf`, `optionalFieldOf` and its lenient and defaulted forms, records of 1 to 5, 11 and 16 fields, a map codec's `stable`, `xmap` and `flatXmap`, `dispatch` and `partialDispatch` with types that fail both ways, and `recursive`), each named by how it's made. A codec named N gets `N.encode` cases (a value onto a prefix: the end mostly, compounds and any tags) and `N.decode` cases (the result a `DataResult` of `[value, rest]`): its own encodings of 150 random values, each with one tag inside replaced, removed or added, and any tags. Values are by shape: numbers by class, lists as arrays, an `Optional` as its value or null, an `Either` as `["left", v]` or `["right", v]`, a record as its fields.

`java.lang.String`'s suite is hand-written: `hashCode` of every edge and random string, `compareTo` of every pair of edges, random pairs, and strings against their prefixes and one-character extensions, and decoding UTF-8 (`<init>([BLjava/nio/charset/Charset;)V`, the charset always UTF-8): every byte and every pair of bytes, every 3-byte lead with every second byte and a third either side of the continuation range, every 4-byte lead (and the leads past U+10FFFF) with every second byte, cut short after the third or not, then 2,000 random byte strings that are mostly UTF-8's lead and continuation bytes, and the edge and random strings encoded.

Stateful classes get hand-written suites, which run seeded random programs of ops and record a step per op. A program ends at the first op that throws, recorded as `{"throws": …}`:
- `RandomSourceSuite`: each op's output, for every `RandomSource` implementation.
- `PoseStackSuite`: `[output, pose, normal, trustedNormals]`, the op's output and the top pose afterwards (`trustedNormals` is read by reflection). One program in four draws any float, NaN included. The last 256 programs also multiply by transformations, whose output is the transformation afterwards: `mulPose` adds to its matrix's properties.
- `Matrix4fStackSuite`: the current matrix after each op, for stack sizes from 1 to 20 and a few the constructor rejects.
- `Matrix3x2fStackSuite`: the same for the GUI's pose stack, with the ops the client calls on it (push, pop, translate, scale, rotate).
- `ProjectionSuite`: `[output, zNear, zFar, fov, width, height, invertY, matrixVersion]`. `getMatrix` needs `RenderSystem`'s device, so the suite installs a stand-in (a `GpuDevice` proxy that only answers `getDeviceInfo`) whose `isZZeroToOne` is the case's `args[0]`.

Value types (JOML's, and the game's below) get an `InstanceSuite`, which covers the constructors and instance methods it lists the same way. A case calls one method on a fresh receiver, which is `args[0]`, and `after[0]` is the receiver's state afterwards. Any other argument the method wrote to gets its state in `after` too, unless it's the returned object, which `result` already shows. A constructor is an `<init>` case whose result is the new object, and a static method listed with them (a record's factories) gets cases without a receiver. `equals(Object)` takes another object of the same class. The port checks them with `golden.check_method`, which fails a case when vanilla recorded an `after` slot the check can't see, or `golden.check_mut` when the method also writes to another argument. A suite can add cases for a member (`extraInputs`, each a receiver followed by the arguments), and write the class's public constants like a static suite (`withFields`).

JOML objects are encoded as their fields in declaration order: a `Vector2f` is `[x, y]`, a `Vector3f` `[x, y, z]`, a `Vector4f` and a `Quaternionf` `[x, y, z, w]`, a `Matrix3x2f` (or `Matrix3x2fStack`) `[m00, m01, m10, m11, m20, m21]`, a `Matrix3f` `[m00, m01, …, m22]`, a `Matrix4f` (or `Matrix4fStack`) `[m00, m01, …, m33, properties]`, and a `FrustumIntersection` its 24 private plane components `[nxX, nxY, nxZ, nxW, pxX, …, pzW]` followed by its `planes`, an array of six `Vector4f` (read by reflection). An `Axis` is the name of its constant (`"XP"`). A `GivensParameters` is `[sinHalf, cosHalf]`, like any record. A `Transformation` is `[matrix, decomposed, translation, leftRotation, scale, rightRotation, identity]`: its fields (read by reflection), the four parts null until it's decomposed, then whether it's the `IDENTITY` constant, which the game compares with by reference. An `Optional` (only `Transformation.compose` takes one) is its value or null, and so is an argument a method lets be null (a `Transformation`'s missing part). Transformations are made the ways the game makes them (block entities' parts, block model rotations, entities' parts, and matrices of those parts), from any JOML matrix, or decomposed already. The receivers and arguments come from JOML itself (identities, translations, rotations, scales, the camera's projections, products of those, and matrices built from components, NaN and infinities included), so their properties are ones the game's matrices can have. 2D poses are the GUI's (pixel translations, GUI scales, a map decoration's rotation), and frustums are mostly the camera's culling frustums (`Camera.createProjectionMatrixForCulling` times the view rotation) looking anywhere.

The game's own value types get `InstanceSuite.every`, which covers every public constructor, method and constant the class declares, like a static suite does: a member whose arguments have no generator, or whose result has no encoder, is written as skipped, so the port has to mark it pending (the codecs, and `Direction.orderedByNearest`, which takes an `Entity`). An inherited method whose answer depends on the receiver's class is added with `inherited` (`Vec3i.toString` prints `BlockPos{…}` for a `BlockPos`), and so is one a class forwards to an object it holds (`PropertyMap`'s `Multimap` methods), and `where` drops inputs like a static suite's. A `Vec3i` is `[x, y, z]` (ints), and so are a `BlockPos` and a `MutableBlockPos`; a `Vec3` is `[x, y, z]` (doubles), a `Vec2` `[x, y]` (floats), and a JOML `Vector3i` `[x, y, z]` (ints). An enum constant is its name (`"NORTH"`), an `EnumSet` (`Vec3.align`'s axes) the names of its constants in order, and a collection, stream, iterator or iterable the array of its elements, each encoded by its own class as it comes (the first 512). `BlockPos`'s iterables hand out one `MutableBlockPos` they move, so each element is encoded before the next is asked for. When working out an element throws (`randomBetweenClosed` drawing from an empty box), the call counts as throwing, so the port collects the elements inside the checked call. A `Position` argument is a `Vec3`, and an argument a method lets be null (`Direction.getNearest`'s fallback) gets null among its extra inputs. When every argument is an enum, the edges are every combination already, so there are no random cases.

An `AABB` is `[minX, minY, minZ, maxX, maxY, maxZ]` (doubles), an `AABB.Builder` its private fields `[minX, minY, minZ, maxX, maxY, maxZ, defined]` (floats and a boolean), and a `BlockHitResult` `[location, direction, blockPos, miss, inside, worldBorderHit]`, `HitResult`'s field first. A `BlockHitResult` is also the receiver of `HitResult`'s methods, since entities aren't ported. An `Optional` result is its value, encoded by its own class, or null. A parameter's generic type can pick its generator where the raw class can't: a `List<AABB>` or `Iterable<AABB>` is a list of boxes (an array), like a block's shape from `VoxelShape.toAabbs`.

Their values are like the game's: blocks around the walk scenario's spawn at any height, steps and offsets, blocks anywhere inside the world border, and any ints; the walk scenario's spawn and its deltas, entities' deltas, look vectors, block corners and centers, and any doubles; rotations. Edges include NaNs of both signs: x86's own NaN (`0.0 / 0.0`) is negative, unlike Java's canonical one, and `hashCode` has to make them the same. The extra inputs go where results flip: points exactly as far apart as the distance a strict `<` checks them against (and an ulp either side), vectors whose length is `normalize`'s threshold (along an axis, where the length comes out exact), ties for `getNearest` and `axisStepOrder`, subnormal dot products for `getApproximateNearest`, `fromYRot`'s multiples of 45 degrees, every degree of `isFacingAngle`, and `BlockModelRotation`'s 48 matrices for `Direction.rotate`. `Float.floatToIntBits` and `Double.doubleToLongBits` get NaNs with other payloads.

`BlockPos`'s blocks also include the largest and smallest coordinates `asLong` packs (26 bits for x and z, 12 for y) and one past them, and its extra inputs go where its answers change: every block at those limits for `asLong`, blocks packed into longs for `of`, `getX(J)` and the rest, points on `clampLocationWithin`'s bounds and an ulp either side (its lower bound is a float sum, which rounds far out), Manhattan reaches up to 4 and negative ones, boxes up to 9 blocks across with their corners either way round, columns, every pair of directions for `spiralAround`, boxes walked along movements with zero, -0.0 and NaN components, and draws from small boxes, some empty. A Manhattan search with a negative reach and a large depth finds no block and runs until the depth wraps, so those inputs need every reach non-negative or a depth up to 64.

`AABB`'s boxes are whole blocks, blocks' shapes (`Block.box`'s sixteenths) at blocks, entities' boxes (the player standing, crouching and swimming, items, arrows, minecarts, with `EntityDimensions.makeBoundingBox`'s float half width) around the walk scenario's spawn, standing on a block or anywhere, boxes between any two `Vec3`s, and any doubles. Edges add the player at the spawn, the empty box an item model without extents gets, and flat, endless, subnormal and NaN (both signs) boxes. Its extra inputs go where answers flip:
- `equals`: each box against a copy, and against a copy with one side an ulp away or a zero or NaN of the other sign;
- `intersects`, `intersect`, `minmax` and `distanceToSqr(AABB)`: an entity's box against a block or another box, moved so their sides meet, overlap by an ulp or are an ulp apart, along one axis or two;
- `contains` and `distanceToSqr(Vec3)`: points on a box's sides, an ulp either side, inside and outside;
- `clip` (all three) and `Mth.rayIntersectsAABB`: rays like the game's picks from near a block along a look vector, aimed at a box's center, a point inside it, a corner, an edge or a side; at a corner along a diagonal from a whole number of blocks away, where two sides are hit at the same scale; along an axis passing the other sides at `clipPoint`'s 1.0E-7 margin, give or take two ulps (the order the margin is added in decides those); starting inside a box or on a side, ending on a side, moving about 1.0E-7 along some axes (the threshold for moving along an axis), and of length 0. The boxes are a block's shapes at the block, which `clip(Iterable, …)` gets relative to the block, so the shapes' boxes tie too;
- `collidedAlongVector`: entities walking, falling, stepping like a projectile or heading for the box, past a fluid's box (the only list the game passes) or a block's shapes.

An `Identifier` is `[namespace, path]`. Identifiers are the game's (blocks, models, textures, a tag's, the scenario's marker, the realms namespace), ones with every character a part allows, empty parts and `..` as a path, and random ones, mostly in the default namespace. Their extra inputs pair namespaces and paths that break each rule (empty, `..`, upper case, a space, non-ASCII, a slash in a namespace, a second separator in a path) for the factories and `isValid*`, split those joined strings with separators the game uses and others (`é`, and both halves of a supplementary character, which Java's `indexOf(char)` finds inside one), add every path as a new path, prefix and suffix, compare identifiers with parts in common for `equals` and `compareTo`, and try every char up to U+017F and the surrogates for `isAllowedInIdentifier` and `validPathChar`.

Netty's `ByteBuf` is `[array, readerIndex, writerIndex, markedReaderIndex, markedWriterIndex]`: its whole backing array as hex, whose length is the capacity, then its indexes (the marks read by reflection). The array past the writer index is part of it, since `writerIndex(int)` can move over it and `clear()` leaves bytes there. Netty runs without `sun.misc.Unsafe` on JDK 25, so a heap buffer's new array is a zeroed `new byte[]`, like the port's, and never Netty's uninitialized one. A `FriendlyByteBuf` is the buffer it wraps. Each call gets a fresh heap buffer like `Unpooled.buffer`'s with the same array and indexes. Buffers hold fields the way packets write them: VarInts and VarLongs of every length, their largest values, `MIN_VALUE` and -1, a last byte whose high bits don't fit, overlong ones, ones a byte too long and ones cut short; strings with their length, valid or malformed UTF-8 (a lone continuation, an overlong NUL, an encoded surrogate, a sequence cut short, a code point past U+10FFFF, a byte UTF-8 never uses), a length past the end or negative, and `readUtf`'s longest length and one more; fixed-size fields (a long, the offline player's UUID, NaNs, the walk scenario's ground block, a `Vector3f` and a `Quaternionf`); and a handshake packet with its id read. Random buffers string up to four such fields, with a length prefix that's right, a little off or anything, read from the start, the end of the first field or anywhere, with no spare capacity, a little, or the game's default 256 bytes, and marks a quarter of the time. Edges add an empty buffer of no capacity and the default one, full buffers (so writes grow them), buffers read to the end, and one cleared after marking.

`ByteBuf`'s suite covers the methods the client calls on a buffer, `FriendlyByteBuf`'s every method it adds (`withoutOverridesOf(ByteBuf.class)` leaves out its overrides of `ByteBuf`'s, which only forward to the buffer it wraps), and `VarInt`, `VarLong` and `Utf8String` are static suites. Their extra inputs go where answers change:
- indexes around a buffer's for the index setters, `isReadable(int)`, `skipBytes`, `readBytes(int)` and `ensureWritable`: negative, zero, the reader and writer indexes, the capacity, the readable bytes, one past each, and `MAX_VALUE`; ranges for `toString` (all the readable bytes, all of the capacity, empty at the end, past either end, negative), for `slice` (the same, the readable bytes and one more, what's past the writer index, and an end past `MAX_VALUE`; a slice is a buffer like any other, so its bytes and indexes are checked, but not its maximum capacity), and for `readBytes` and `writeBytes` of arrays and other buffers;
- NaNs with other payloads for `writeFloat` and `writeDouble`, which write their raw bits;
- every value whose VarInt or VarLong is a byte longer than the one before's, its neighbours and its negation, written to the default buffer and to a full one; and VarInts and VarLongs of every length up to one past the longest, with any data bits, overlong now and then, and another field after them;
- strings whose UTF-16 length and UTF-8 size differ, and malformed UTF-8, read and written with maximums around each limit (the length, the size over 3, and ones whose triple wraps: `1 << 30`, 715827883), and strings of 32767 and 32768 units for `readUtf()` and `writeUtf(String)`, in characters of one, two and three bytes;
- identifiers valid and not for `readIdentifier`, and arrays of bytes, VarInts and longs with their length, one more than there are, or negative, read with maximums around the length.

Two filters keep vanilla from allocating gigabytes: `ensureWritable` and `writeBytes` with a range only get lengths up to 2^16, or ones that overflow the writer index (which throw before growing), since vanilla grows the buffer before it finds the source's range wrong; and `readByteArray(int)` and `readVarIntArray(int)` drop buffers whose length prefix is over 2^16 but within the maximum, which vanilla allocates before it finds the buffer shorter. The port allocates the same way, and the smaller lengths still check it. `tools/golden.py` turns Netty's leak detector off: the cases never release the buffers `readBytes(int)` hands back.

Stream codecs and `IntFunction`s are objects rather than methods, so they get cases of their own (`Codecs`). A codec named N gets `N.decode` cases, which read the buffer in `args[0]` (the result is the value, and `after[0]` the buffer afterwards), and `N.encode` cases, which write `args[1]` into the buffer in `args[0]` (the result is null, and `after[0]` the buffer afterwards). An `IntFunction` named N gets `N.apply` cases, from an id to a value. The port checks them with `golden.check_codec` and `golden.check_function`, which make the codec or function inside each checked call, so a panic making it counts as the case's. A codec or function a factory makes from arguments that have generators (`ByteBufCodecs.stringUtf8`'s maximum) takes them first (`check_codec_from`, `check_function_from`), and a case throws when the factory does. Decoding reads every buffer edge, random buffers, and the codec's own encodings of the first 200 values (the value edges first): whole, cut short by a byte, cut anywhere, and with another field after them. Encoding writes each value edge into a random buffer and a random value into each buffer edge, then random values into random buffers. The values are the generators' for the codec's value type: a codec's or function's type arguments pick them, and the buffer has to be a `ByteBuf` or a `FriendlyByteBuf` and the values a class's, since a generic one's generator wouldn't know its type arguments. A parameterized value type gets its raw class's generator unless its arguments pick one (`ResourceKey.REGISTRY_STREAM_CODEC`'s `ResourceKey<? extends Registry<?>>`, whose argument only says what it's a key of), and is encoded as its raw class. Boxed numbers have their primitives' generators, and an `OptionalInt` is its int or null, either way round (`of(-1)` writes empty's 0).

Static fields get these cases wherever a suite writes fields: `Vec3i`'s, `BlockPos`'s, `Direction`'s, `Vec3`'s (and `LP_STREAM_CODEC`), `BlockHitResult`'s, `Identifier`'s and `Rotation`'s `STREAM_CODEC`, and `Direction`'s and `Rotation`'s `BY_ID`. A field whose buffer or values have no generator is skipped, naming the type. `CodecSuite` covers a class whose members hand out codecs and functions (`ByteBufCodecs`, `StreamCodec`, `ByIdMap`): its fields like that, its static methods making codecs or functions from generated arguments, its other static methods like a `StaticSuite`'s (`readCount`, `writeCount`), and, for methods taking codecs or functions, the instances the suite lists, each named by the method's descriptor and a label for what it was given: `optional(Lnet/minecraft/network/codec/StreamCodec;)Lnet/minecraft/network/codec/StreamCodec;[VAR_INT]`. The port builds the same instance under the same name. The instances are the game's kinds of codecs and functions:
- `ByteBufCodecs`: `optional` of `VAR_INT` and `STRING_UTF8`; `collection` and its operations with `ArrayList::new` and `VAR_INT` or `STRING_UTF8`, and generated maximums; `list` of `Direction.STREAM_CODEC`, and `list(int)` of `STRING_UTF8`; `fixedSizeCollection` and `fixedSizeList` of `VAR_INT`, `FLOAT` and `BOOL`, with sizes mostly a random list's (0 to 6) and `-1`, `140` and `65536`, since a larger one can't be read from a random buffer and `ArrayList`'s constructor rejects a negative one; and `idMapper(Direction::from3DDataValue, Direction::get3DDataValue)`. Their values are lists of up to 6 elements mostly, up to 140 now and then (whose count takes a second byte), and optionals empty a quarter of the time. `byteArray(int)`'s decoding drops buffers whose length prefix is over 2^16 but within the maximum, like `readByteArray(int)`'s.
- `StreamCodec`: `of(FriendlyByteBuf::writeUUID, FriendlyByteBuf::readUUID)`, `ofMember` writing and reading an `Identifier` on a `FriendlyByteBuf`, `unit(Direction.NORTH)` (which only writes `NORTH`), `VAR_INT.apply(ByteBufCodecs::optional)`, `BYTE.map(Mth::unpackDegrees, Mth::packDegrees)`, `VAR_INT.cast()` on a `FriendlyByteBuf`, and every `composite`, of 1 to 14 fields of `VAR_INT`, `STRING_UTF8`, `BOOL` and `FLOAT` in turn. A composite's value is the list of its fields, which the getters read and the constructor (a `FunctionN` made with `java.lang.reflect.Proxy`) makes, so it's an array like a tuple.
- `ByIdMap`: `continuous` of the directions by their 3D data value with each strategy, and two it refuses to make (by 2D data value, which has gaps, and of no values); `sparse` of the horizontal directions by 2D data value with `UP` for the rest, and one it refuses (two directions share 2D data value -1). Ids are the int edges, -16 to 16, and random ints.

`FriendlyByteBuf`'s readers and writers that take a decoder, an encoder or a function get the same treatment from its `InstanceSuite`: cases for the instances the suite lists with `given`, each named by the method's descriptor and a label (`readOptional(…)Ljava/util/Optional;[VAR_INT]`). Their `args` are the receiver and the generated arguments, without the instance, and a result declared as an `Object` (`readNullable`'s, `readById`'s) is encoded by its own class. The instances are the game's kinds:
- `readOptional` and `writeOptional` of `VAR_INT`, and of `ClientboundDamageEventPacket`'s source position (a `Vec3` as three doubles);
- `readNullable` and `writeNullable` of `readIdentifier` and `writeIdentifier`, and of `readUtf` and `writeUtf`; the static ones of the signature in `GAME_PROFILE_PROPERTIES` (`Utf8String` of at most 1024 units);
- `readById` of `Direction.BY_ID` and `Rotation.BY_ID`, and `writeById` of `Direction::get3DDataValue` and `get2DDataValue` (-1 for up and down);
- `readWithCount`, which nothing in the client calls, of `readVarInt` and `readUtf`.

Values a method lets be null are null a quarter of the time, like an empty optional. Besides the buffer edges and random buffers, each reader reads what its writer writes of 100 values (the edges first): whole, with a field after, cut short by a byte, and cut anywhere. The signatures include strings around 1024 units, written without the limit so the reader sees too long ones.

The Netty handlers that frame packets get a `HandlerSuite`. Their `decode` and `encode` are protected and take a context neither uses, so subclasses call them with null, on a fresh handler per case:
- `Varint21FrameDecoder.decode` reads the buffer in `args[0]` the way Netty's `ByteToMessageDecoder` asks, again while bytes are left and the last call took a frame out, and its result is the frames it found (an array of buffers). Its buffers are the edges, random ones, frames with lengths of one to three bytes (whole, with more after them, cut short, after bytes already read), runs of up to eight frames, the handshake, and lengths of zero (an overlong zero too), cut short, and wider than 21 bits. Its `[in chunks]` cases take the rest of a run of frames in `args[1]`, an array of byte arrays, each written to the buffer before the same decoder is asked again. Half the cuts are one byte into a frame, so lengths arrive split, and the decoder has to start each one afresh.
- `Varint21LengthFieldPrepender.encode` writes the message in `args[0]` into the buffer in `args[1]`: bodies at each header length's bounds, up to 2^21 - 1 and 2^21 (which throws), all readable or after bytes already read, into the game's default buffer and a full one.

Protocols and packets have encodings of their own (`PacketValues`):
- A `PacketFlow`, `ConnectionProtocol` or `ClientIntent` is its constant's name, and a `PacketType` `[flow, id]`, like any record. Types are the ones the ported protocols register, each also with the other flow, and random flows and identifiers.
- A packet is its fields: a record's components, or the fields another class's public constructor sets, in that order (read by reflection), so a `ClientboundHelloPacket` is `[serverId, publicKey, challenge, shouldAuthenticate]` and a `ServerboundLoginAcknowledgedPacket` `[]`. A value declared as a `Packet`, which a protocol's codec reads and writes, is `[type, fields]`, since it can be any of the protocol's. A `ServerboundKeyPacket` is `[keybytes, encryptedChallenge]`, made by reading them from a buffer, since its public constructor encrypts with `Crypt`.
- The custom queries' payloads are records too, `DiscardedQueryAnswerPayload` `[]` and `DiscardedQueryPayload` `[id]`, and one declared as its interface (a packet's component) is encoded by its own class. A `CustomQueryAnswerPayload` argument is null a quarter of the time, since a packet's may be.
- Each argument is its own copy of a packet or payload, made of copies of its fields, so no two arguments share an array: JSON can't say two values are the same object, and a record compares an array component by reference. So a `ServerboundCookieResponsePacket` equals another only when their keys are equal and neither has a payload, and a `ClientboundStoreCookiePacket` never does.
- A protocol's template (a `SimpleUnboundProtocol`) is its details, `[id, flow, [[type, networkId], …]]`, and a bound protocol (a `ProtocolInfo`) `[id, flow]`.
- A packet listener argument records the calls on it: it's `[]` in `args`, and its `after` slot is the calls, each `[method, argument…]`, so `handle` cases show which handler a packet calls with what. The port's `Recorder` (in `packet_listener.rs`'s tests) implements every listener trait the same way.

Each packet class gets `InstanceSuite.every`, whose `STREAM_CODEC` gets codec cases like any codec constant. Its values put each field's edges among the others' first: protocol versions (the release's, a snapshot's), addresses and port numbers past an unsigned short, player names, server ids and strings around each reader's limit (`readUtf(255)`, `16` and `20`, in characters of one, two and four bytes), byte arrays (and a public key's and a challenge's length), compression thresholds and transaction ids (any ints), identifiers, and cookies (byte arrays, and ones of 5120 and 5121 bytes). A codec constant `N` can get more buffers to decode with `extraInputs("N.decode", …)`, for fields its writer refuses but its reader doesn't see otherwise: `ServerboundHelloPacket`'s names over 16 characters and the cookie packets' payloads over 5120 bytes, written without the limit, and the custom query packets' payloads (everything after the header, which their readers skip) of 1 MiB and a byte more. A record whose components include an enum hashes the constant's identity hash, which changes from run to run, so `InstanceSuite.exclude` writes its `hashCode` as skipped (`PacketType`, `ClientIntentionPacket`), and the port marks it pending. So does a record holding an array, whose `hashCode` and `toString` hash and print the array's identity hash (the cookie packets').

A login's last packet carries the player's profile, from Mojang's authlib (`ProfileValues`). A `Property` is a record, `[name, value, signature]`, and so is a `GameProfile`, `[id, name, properties]`. Names are the skin's `textures`, a few names the random ones share (so keys repeat), and strings around `GAME_PROFILE_PROPERTIES`' limit of 64; values a skin's textures (base64 JSON) and strings around 32767; signatures none a quarter of the time, a 4096-bit key's base64 signature, and strings around 1024. The multimaps' edges add the empty one, each property alone, two properties under one name either way round, names that interleave either way round, a property twice, a key that isn't its property's name, and 16 and 17 properties (the codec's limit). Profiles are the player names (around 16), any `UUID`s and those maps, the offline player's profile and a signed skin's. `PropertyMap`'s suite adds the `Multimap` methods it forwards (`values`, `size`, `isEmpty`, `equals`, `hashCode`, `toString`) with `inherited`, and `equals` gets every pair of edges, so maps with the same keys in another order compare equal. `ByteBufCodecs`' `GAME_PROFILE_PROPERTIES` and `GAME_PROFILE` also decode what's written without the codec's limits (on the count, the strings and the name), and counts of 0, -1, `MIN_VALUE`, 16, 17 and `MAX_VALUE` with nothing after them: a `CodecSuite` takes extra buffers for a codec constant like an `InstanceSuite` does, with `extraInputs("N.decode", …)`. `UUIDUtil` is a static suite, whose offline UUIDs also get the player names, and `java.util.UUID`'s suite adds `nameUUIDFromBytes`, with `OfflinePlayer:` and each player name among its byte arrays.

NBT (`NbtValues`, `NbtSuites`) encodes every tag as `[id, payload]`, whatever it's declared as: an `EndTag` `[0, null]`, the numbers `[1, byte]` to `[6, double]`, the arrays `[7, [byte, …]]`, `[11, [int, …]]` and `[12, [long, …]]`, a string `[8, value]`, a list `[9, [tag, …]]`, and a compound `[10, [capacity, [[key, tag], …]]]`: its `HashMap`'s table length (0 before it's made, read by reflection, which `tools/golden.py` opens `java.util` to) and its tags in the map's order, which is the order it writes them in. - A read with an accounter whose quota is bigger than the default one (a trusted codec's, or a usage whose sum overflows) is dropped unless the same read with the default quota doesn't run out of it (`NbtValues.readsLittle`): a count read from random bytes can be in the billions, and a list or array is allocated after it's accounted for, so vanilla would allocate gigabytes. Reading NBT wraps an `IOException` in a crash report, whose system details probe the hardware with OSHI (files under `/proc` and `/sys`, and `lshw`, `dmidecode`, `lspci` and `cpuid` as processes) for over 20 ms a report, so `tools/golden.py` runs the generator without OSHI's jar. `SystemReport` catches the `NoClassDefFoundError` like any detail it can't get, and only the exception's class goes into a golden, so the files come out the same. - `java.util.HashMap` has a program suite (`HashMapSuite`): `put`, `remove`, `get`, `containsKey` and `copy` (`new HashMap<>(map)`) on a map of strings, each step `[output, [capacity, [[key, value], …]]]`. Their tree bins go under `treeified sized programs`, also pending.
- `ByteBufCodecs`' `TAG`, `TRUSTED_TAG`, `COMPOUND_TAG`, `TRUSTED_COMPOUND_TAG` and `OPTIONAL_COMPOUND_TAG` get codec cases (a codec of `Optional<X>` gets X's values or empty, a quarter of the time), and `tagCodec` and `optionalTagCodec` are given the click action's accounter, `compoundTagCodec` the trusted one. A listed instance gets more buffers to decode like a codec constant, under `extraInputs("descriptor[label].decode", …)`, each its leading arguments and the buffer: tags (none, an empty compound, a byte, a string, a compound of two) and payloads (none, one byte, five) behind a prefix that's right, a byte short, a byte long, zero, negative or an int's limit, with maximums of the payload's length, a byte less and 65536, no spare capacity or 4 bytes (so a prefix a byte long is past the writer index but inside the array), and a byte after or none, read after a byte already read (so a mark set on the buffer would show); and discarded payloads of 32767 and 32768 bytes. The tags' values also hold a string too long for `writeUTF`, whose writer throws after writing the tag's id, so encoding it shows that nothing reaches the buffer.

Lists nest, so they're up to 6 long, with 128 modifiers (a count of two bytes) and 128 and 129 attributes (around the codec's limit) as edges; the codec also decodes the walk's three payloads. `Attributes` is a static suite, each field its holder.
- `set_default_spawn_position` is `[respawnData]`, a `LevelData.RespawnData` `[globalPos, yaw, pitch]` and a `GlobalPos` `[dimension, pos]` (the dimensions' keys and any in the dimension registry, every block edge), which also un-pends `FriendlyByteBuf.readGlobalPos` and `writeGlobalPos`.
- `set_entity_data` is `[id, packedItems]`, each `SynchedEntityData.DataValue` `[id, serializer, value]`: its id, its serializer's id in `EntityDataSerializers` and its value as the serializer's type is encoded, for the serializers the port has (the numbers, strings, booleans, `Rotations`, block positions, directions, block states, the parrots' optional ints, `Pose`, the twelve variants' holders, optional `GlobalPos`es, vectors, quaternions and arms). Its 564 value edges come in lists of 64, since a list's encoding stops at 512. A buffer whose reading reaches a value of another serializer (a component, an item stack, a particle…) isn't decoded (`RegistryValues.reachesUnported`); the codec also decodes the walk's player data (health and skin, flags, crouching and standing). The record's `hashCode` and `toString` hash and print the serializer, a lambda, by identity, so they're written as skipped.

`recipe_book_settings` is `[bookSettings]`, a `RecipeBookSettings` its four books' `TypeSettings` `[crafting, furnace, blastFurnace, smoker]` (read by reflection, made with its private constructor), each `[open, filtering]`, any booleans; `RecipeBookType` is its constants. `RecipeBookSettings` overrides none of `equals`, `hashCode` and `toString`, so the packet's record compares, hashes and prints it by identity, and those three are written as skipped. A class a packet holds that isn't a record is encoded by its fields, like a packet.

The status protocol, the server list's ping, comes next (`PacketValues`): `StatusPacketTypes` is a static suite, `StatusProtocols` a `ProtocolSuite`, `ServerboundStatusRequestPacket` is `[]`, and `ServerboundPingRequestPacket` and `ClientboundPongResponsePacket` (which play shares) `[time]`, any long. `ClientboundStatusResponsePacket`'s status is read from JSON with DataFixerUpper's codecs and holds text components, so it has no generator yet and `StatusProtocols.CLIENTBOUND.codec()` is skipped; a test reads the status response vanilla's server sent and writes it back byte for byte. The pinging itself is checked by captures: `oracle_client.py capture walk --ping` has the oracle client ping the scenario's server the way the server list does (`ServerStatusPinger`, ticked like `JoinMultiplayerScreen` ticks it) into `vanilla/<version>/oracle/walk-ping/`, `port_client.py capture walk --ping` has the port do the same (`rustcraft --ping`) into `target/oracle/walk-ping/`, and `oracle-diff packets` compares them: with no marker, the whole serverbound stream is strict, and the ping's time is the client's clock, which the default ignore list leaves out with the rest of the pings.

`ProtocolSuite` covers a class of protocols (`HandshakeProtocols`, `LoginProtocols`, `ConfigurationProtocols`): its constants as above, and each bound protocol's codec, whose cases are named `FIELD.codec()` and whose values are any of the packets its template lists. A protocol whose packets don't all have generators yet is skipped, naming the first that hasn't (login's clientbound one, at `login_disconnect`, and configuration's, at `disconnect`). `java.util.UUID`'s `hashCode` and `toString`, which a `ServerboundHelloPacket`'s use, have a suite of their own, and `StreamCodec.mapStream` is checked on `ClientIntentionPacket.STREAM_CODEC` wrapped with `FriendlyByteBuf::new`, the way the protocols put a packet's codec on a connection's `ByteBuf`.

`LpVec3` is a static suite whose `write` also gets movements around its limits (the smallest component it writes and an ulp either side, whole blocks around where the scale needs a VarInt, the largest it writes and past it, NaN and infinities, each sign along each axis with the other components zero, smaller or the same) into random buffers, `read` their encodings (whole, cut short, with a field after), and `hasContinuationBit` every byte. `Math.clamp(double, double, double)` is in `Math`'s suite.

The block state registry has hand-written suites (`BlockSuites`), which encode a property as the name of its field in `BlockStateProperties` (every block's properties are among them, each in one field), a value as a boolean, an int or its constant's name, a block as its registered name (`minecraft:stone`) and a state as its id in `Block.BLOCK_STATE_REGISTRY`:
- `BlockStateProperties`' fields, each property `[class, name, values]`, and `Property`'s methods on each of them (`args[0]` is the field): its name, values, value class and `toString`, `getName` of each value, `getInternalIndex` of each value, every other constant of an enum property's class and ints around an integer property's range (and the int limits), `getValue` of each value's name and of strings that look like other values or that `Integer.parseInt` takes or refuses (signs, leading zeros, any Unicode decimal digit, spaces, overflow), and `equals` of every pair; and the factories' checks, `IntegerProperty.create` on ranges it refuses and one whose `max + 1` wraps. `Integer.parseInt` and `Character.digit` (in radix 10, of every char) are static suites.
- `StateDefinition.Builder` on lists of properties: the definition is the properties sorted by name and the number of states, unless two share a name.
- `Blocks`' fields: a block, or a collection's blocks (`[weathering, waxed]` for copper's). `Block`'s suite has each block (`args[0]`): its registry id, class, `toString`, default state, its state definition's properties, states, first state, `toString` and `getProperty` of its properties' names and others, its description id and loot table, the getters of what `BlockBehaviour` copied, its `hasCollision` and `isRandomlyTicking` fields and `Properties`' `forceSolidOn` and `forceSolidOff` (read by reflection), and the kind of each of its `isRedstoneConductor`, `isSuffocating` and `isViewBlocking`: `default` when the lambda's class is a fresh `Properties`' (a lambda's class stands for where it's written), a `Blocks` field's name when it's that field's object, `custom` otherwise. And `stateById` around the ids, `getId(null)` and the registry's size.
- `BlockState`'s suite has every state (`args[0]`): its block, values and `toString`, what it took from its block's `Properties` (light, `isAir`, `liquid`, push reaction, destroy speed, map colour, `canOcclude`, `emissiveRendering`, `canBeReplaced`, the instrument…), whether it ticks randomly or has a block entity, and the functions taking a level asked at (1, 2, 3) of `EmptyBlockGetter` (`getPostProcessPos`, and the predicates of the `custom` kind and `NOT_EXTENDED_PISTON`, which answer from the state alone). Its lookups go by its block's definition, so `cycle` and `setValue` of each of a property's values (`[every value]`, a list) cover every state of a block with up to 64 and 64 spread over another's (its first, last and default among them); each block's default state is asked about 16 properties it may or may not have (`getValue`, `hasProperty`, `getOptionalValue`, `getValueOrElse`, `setValue`, `trySetValue`, `cycle`), and set to values its properties don't take (ints past their range and the int limits, constants an enum property leaves out). The port also checks every state's id, values and default against the data generator's `generated/reports/blocks.json`. Its `light` case is what `initCache` keeps for the light engine, `[useShapeForLightOcclusion, propagatesSkylightDown, getLightDampening, isSolidRender, occlusion shape, each direction's face of it]`, a shape as `BLOCK` or `EMPTY` (the shared constants, by reference) or `OTHER`, whose voxels only come with its class's shapes (`ShapeSuites` checks the shapes' mechanics). The port checks it for the states whose light it knows (`light_properties_ported`: their classes keep the whole block or no shape, or answer without one), and pins how many those are, so a state that stops being known fails too.

Chunk data has hand-written suites too (`ChunkSuites`). Programs run ops on one object and record each op's output; the first op that throws ends the program as `{"throws": …}`. Bytes are hex strings, and a block state is its id.
- `SimpleBitStorage` for every bits per entry from 1 to 32 (and bits it refuses): `<init>(II)V` → `[bits, size, raw]`; `<init>(II[J)V` from random longs → every `get(i)`, which runs the divide-by-magic-number cell index for every index, at sizes of 4096 (a section), 64 (a section's biomes), 0, 1, around the values per long, and random ones, and longs a cell short or long, which throw; `<init>(II[I)V` from random values (any int now and then, which the mask cuts) → the longs, and too few values; `unpack`, `getAll` and `fill` (which also writes the bits past a long's last whole value) → the ints or longs; and `programs`, `[bits, size, longs, ops]` → `[outputs, longs after]`, of `get`, `set`, `getAndSet`, `fill` and `copy` with indexes and values out of range now and then.
- `ZeroBitStorage`: `RAW`, and each method at sizes 0, 1, 64 and 4096 with indexes and values around them (`args[0]` is the size).
- `CrudeIncrementalIntIdentityHashBiMap`: `programs`, `[capacity, ops]` on a map made with `create(capacity)`, each step `[output, size]`: `add`, `addMapping`, `getId`, `byId`, `containsKey`, `containsId`, `size`, `clear`, `copy` and `iterator`, with capacities from 0 (whose first hash divides by zero) to 256. Where a key lands goes by its identity hash, which changes from run to run, so no output may depend on it: a key is never added twice, and `addMapping` only gets ids no key has (a shadow map runs the ops as they're made), or ones past what the table grows to, which throw after the key is in. A key mapped over another's id leaves both in the table, and which one `byId` keeps once the table grows goes by the hashes; the first version of the suite did that, and a fifth of its programs came out different in the port.
- `PalettedContainer`: `programs`, `[registry, initial, ops]` on `new PalettedContainer<>(initial, strategy)`, each step `[output, bitsPerEntry, getSerializedSize]`. The registry is `blocks` (`Strategy.createForBlockStates(Block.BLOCK_STATE_REGISTRY)`) or `biomes:N`, `Strategy.createForBiomes` over an `IdMapper` of N stand-ins (1 to 129, among them 65 and 67), since the bits a global palette takes follow from the registry's size. The ops set values from a pool of 1 to 700 (around each palette's resize: single value, linear, hash map, global), get them, `getAndSet`, `maybeHas` a value, `count` (sorted by id: Java's comes in an `Int2IntOpenHashMap`'s order, which its only caller, `recalcBlockCounts`, adds up), `getAll`, `forEachInPalette` (the first 512), `values` (every value in index order, as runs `[[id, count], …]`), `write` (the bytes), `copy`, `recreate`, `read` (of bytes; the output is what's left unread), `bitsPerEntry` and `getSerializedSize`, at positions out of range now and then. Every registry also reads, then writes, buffers made by hand for every bits per entry a byte can say (0 to 33, 64, 127, -1, -128): the palette its configuration reads and its storage's longs, with an id the registry doesn't have, a linear palette one longer than it holds, a hash map palette longer than its bits, entries past the palette, a byte short and a byte more (a global palette reads no palette, so it only gets the valid buffer and, near the global bits, entries past the registry, a byte short and a byte more); and what vanilla writes for each pool size. A hash map palette's entries never repeat, as above.

A `java.util.BitSet` is its words in use (`toLongArray`). Its generator makes the light packets' masks (bits of the overworld's 26 light sections, all of them, alternating), single bits around the words' bounds and random words, none past bit 255. `java.util.BitSet`'s `InstanceSuite` covers what the codecs and the client's light code call; `set(I)` gets indexes up to 1024, since a bigger one makes it allocate. With it, `ByteBufCodecs.BIT_SET` and `FriendlyByteBuf`'s bit set readers and writers get cases. A fixed-size bit set's reader allocates its size over 8 bytes before it reads, so `fixedBitSet(I)` is a listed instance with sizes up to 2^16 (around the bytes' bounds, 26, and random ones), and `readFixedBitSet` and `writeFixedBitSet` drop larger sizes (`where`).

An entity's movement has pure parts that get goldens too, private or protected statics called by reflection: `Entity`'s `collideWithShapes` (6,000 cases: the player's boxes, standing, crouching and swimming, around the walk scenario's ground, moving like a walk, a fall, a jump or a step, or by the margins, through up to six blocks' shapes, full blocks and the base shapes, around the block under it) and `collectCandidateStepUpHeights` (6,000: the same shapes, step heights of 0.6, 1.0 and any, and heights to skip of 0.0, -0.0, the walk's fall and the ground's), `getInputVector` (4,000: inputs as `modifyInput` makes them, sneaking and diagonal ones among them, the speeds the player moves at, on the ground and in the air, sprinting or not, and turns around the compass), and `LivingEntity.computeModifiedFriction` (549: the blocks' frictions and modifiers, and any). `PlayerSuites` has `AttributeInstance` programs (1,500), `[attribute, ops]` on one of the attributes movement reads, each step `[output, value]`: `setBaseValue` (in and past the attribute's range, NaN and infinities), `addTransientModifier` of each operation (throwing for an id that's on), `removeModifier`, `removeModifiers` and `getValue`. Each operation's modifiers have one id, so an instance never holds two of one operation, whose order is a fastutil open hash map's.

Scenarios are replayed offline by tests (`rustcraft::oracle::client::replay`, "Offline replays" below), which reproduce vanilla's trace and its serverbound packets from the scenario-start marker on.

`BlockPos`'s `AABB` overloads get boxes up to 5 blocks across whose sides are on blocks' faces, 1.0E-7 or an ulp inside or outside them, or anywhere in a block, and `betweenCornersInDirection` also `cornerWalks`' directions. `AABB.Builder`s have included up to 8 points (and the edges none, one with -0.0 or NaN, or infinities).

`FrustumIntersection.intersectAab` and `testPoint` also get boxes and points like the game's (chunk sections, entities and the camera's cube, relative to the camera), boxes and points on a plane to rounding (on the frustum's face, where the order the plane's terms are added in decides which side they land on), and every float edge in each coordinate of a box in front of every edge frustum.


`method` is the JVM name and descriptor, which keeps overloads apart. When vanilla throws, the port must panic.

- **Pending ledger.** Each ported file ends with a test that checks every method and constant in its golden file, or marks it pending with a reason. Anything neither checked nor pending fails the test, so a class is either fully verified or says what's left.
- **Methods that hang.** Some vanilla methods never return on extreme inputs. A watchdog names the call, and the suite keeps the inputs in range with `where()`.

### Pipelines and shaders

`RenderSuites` records the renderer's pipelines and the shaders vanilla's OpenGL backend compiles for them, from vanilla's own classes:
- `DefaultVertexFormat`, `BindGroupLayouts` and `RenderPipelines` are their public constants. A vertex format is `[stepRate, vertexSize, [[name, offset, format], …]]`, a bind group layout `[[name, type, gpuFormat], …]`, and a pipeline `[location, shaders, defines, bindGroupLayouts, colorTargetStates, depthStencilState, polygonMode, cull, vertexFormats, primitiveTopology, pushConstantSize, sortKey]`: shaders `[[stage, id], …]`, defines `[[[key, value], …], [flag, …]]` in the order they were defined, color targets `[blendFunction, format, writeMask]` (a blend function `[[src, dst, op], [src, dst, op]]` for color and alpha), depth `[test, write, biasScale, biasConstant]`, and the 16 vertex buffer slots. A pipeline's layouts are a hash set whose order changes from run to run, so they're sorted by their uniforms' names. An OIT set is its three pipelines, a snippet its builder's fields. `requiredPipelines()` and `optionalPipelines()` are the locations `ShaderManager` compiles, in their `HashMap`'s order.
- The four steps of compiling each of those pipelines, as `PipelineBuilder.compilePipeline` runs them, with the shaders `ShaderManager.loadConfigs` loads from the client jar (through a `ResourceManager` that lists the jar's assets):
  - `GlslCompiler.compileToSpv`: `[flags, name, stage, defines]` → the SPIR-V's bytes as hex, each shader once;
  - `SPIRVModule.reflect`: the same arguments → `[inputs, outputs, descriptors, pushConstants]`, an interface variable `[name, location, flat, component, type]`, a descriptor `[name, resourceType, set, binding, type]`, a type `[baseType, dimensions, vectorSize, [arrayLength, …]]`;
  - `PipelineBuilder.generateBackendCreateInfo` (private, by reflection): `[flags, location]` → the create info, its shaders' SPIR-V after the bindings are renumbered, and each uniform's binding;
  - `GlPipelineRecompiler.decompileShaders`: `[flags, location]` → each shader's GLSL 330, the text `glShaderSource` gets.
- `flags` are the device's `[isZZeroToOne, shaderDrawParameters, isExplicitDepthRequired]`, the three answers that change the text, from a stand-in device like `ProjectionSuite`'s. Mesa's llvmpipe under Xvfb, where the oracle client renders, is `[true, true, false]`: its log lists `GL_ARB_clip_control` and `GL_ARB_shader_draw_parameters` among the extensions vanilla turned on, and it isn't an Apple GPU. Every pipeline gets that; five that read the flags (terrain, multidraw terrain, clouds, an OIT pass, the GUI) also get the other seven combinations. No vanilla shader reads `RENDERPEARL_INSTANCE_INDEX_INCLUDES_BASE_INSTANCE`, so `shaderDrawParameters` only changes SPIRV-Cross's output.
- `RenderPipelines`' sort keys are the order the pipelines are built in, which is its static initialiser's: nothing in the generator builds a pipeline before it, and in the game only post chains do, after it.

The port compiles through the same native libraries (PORTING.md), so its SPIR-V and GLSL are compared byte for byte.

### Textures and the block atlas

`TextureSuites` reads the vanilla pack the way the client does: `ClientPackSource.createVanillaPackSource`'s pack (the jar's resources, then a layer for the launcher's asset index, whose directory isn't on the machine, as it holds only sounds and translations) opened into a `MultiPackResourceManager`, after `ClientBootstrap.bootstrap()` (which registers the atlases' sprite sources). An image is `[width, height, md5]`, the MD5 of its RGBA bytes as they lie in memory, so a mismatch is a pixel that differs.
- `MultiPackResourceManager`: `getNamespaces`, what `listResources` lists under `textures`, `textures/block`, `atlases`, `models/block` and `blockstates`, in its `TreeMap`'s order, and each atlas definition's resource stack.
- `NativeImage.read` of every PNG under `textures/` (3,964): the RGBA stb decodes.

- `SpriteLoader` (the block atlas's CPU half, as `loadAndStitch` runs it with the oracle client's options: mipmap levels 4, filtering that isn't anisotropic, and llvmpipe's 16384 as the largest texture): the sprites `atlases/blocks.json`'s sources list, loaded by `SpriteResourceLoader`, then `stitch`, `[atlas, maxMipmapLevels]` → `[width, height, mipLevel, [[name, x, y, width, height, padding], …]]` in the order `gatherSprites` hands them out, and `increaseMipLevel` of each sprite, `[name, mipLevel]` → `[animated, [image, …]]`, every mip level as `[width, height, md5]`. `SpriteLoader.stitch` reads the options from `Minecraft.getInstance()`, which the generator has none of, so the suite runs its steps with those values.

The port reads the pack from `vanilla/<version>/resources/` (the client jar unpacked) and decodes with LWJGL's own `liblwjgl_stb.so`, so both sides run the same decoder.

The atlas's GPU half, drawing each sprite into each mip level, is a frame test (`tests/opengl_frame.rs`, below).

### Block models

`ModelSuites` covers block models, from the math that turns them to every block state's baked quads:
- `SymmetricGroup3`, `OctahedralGroup`, `Quadrant` (with `parseJson` of every multiple of 45 degrees from -720 to 720 and the int limits) and `FrontAndTop` are `InstanceSuite.every`s, their constants every receiver and argument. `BlockMath` is a static suite whose `getFaceTransformation` also gets the 48 rotations' transformations, made the way `BlockModelRotation` makes them, with each side. JOML's `Matrix3f.set(int, int, float)` writes with `Unsafe` without checking the column and row, so random ones crashed the JVM: its cases keep to the nine elements, each set to 1, -0.0 and NaN in an identity and a rotation.
- `BlockModelRotation`: each of the 48, its `toString`, transformation and face matrices, and its uv-locked state's. `FaceBakery` asks `isIdentity` about an inverse face matrix before anything else reads it, which adds properties to the shared matrix, so they're recorded as `FaceBakery` reads them, after that check (PORTING.md, "Block models"). The suite runs before the bake.
- `LazilyParsedNumber`: every number in the vanilla pack's models and block states (286 different texts), as Gson reads it: `floatValue()` and `intValue()`.
- `ModelBakery`: `ModelManager`'s reload, as far as block states go. The block and item atlases are stitched like `TextureSuites`' (a quad's UVs are its sprite's place in the atlas; `MaterialBaker` looks a material up in the item atlas first), every model file is read with `CuboidModel.fromStream`, the block states' definitions with `BlockStateModelLoader`, their models found and resolved by `ModelDiscovery` (item models aren't discovered: no block state's model needs one), and `ModelBakery.bakeModels` bakes them with a `MaterialBaker` over the two atlases. A model is `[kind, particle, materialFlags, contents]`: a single variant's part, a weighted list's `[weight, model]` entries, or a multipart's models the state selects. A part is `[useAmbientOcclusion, particle, materialFlags, quads]`, its quads unculled, then culled toward each direction in `Direction`'s order, and a quad `[positions, packedUVs, direction, [atlas, sprite, layer, tintIndex, shadeDirectionOverride, lightEmission]]`, a material `[atlas, sprite, forceTranslucent]`. `bake` is the MD5 of each block state's encoding (as Gson writes it, which is serde_json's text), for all 35,723, `bake[full]` the encoding itself for each block's default state, and `missingModels.block` the missing model's. The file is 6.8 MB. The quads' item render types aren't recorded: they come with item rendering.
- `ModelBlockRenderer`: sections meshed the way `SectionCompiler.compile` meshes one, each non-air block of the section in `BlockPos.betweenClosed`'s order whose render shape is a model, at its place in the section and with its state's seed, its quads into a `BufferBuilder` for their layer (`putBlockBakedQuad`), flat and with ambient occlusion. The level (`MeshLevel`, the same in the port's test) is a pattern of 24 blocks' states (air two times in five) by a hash of the position and a seed, crossing the section's sides: whole blocks whose shapes and rendering the port has, opaque, cut out, translucent, glowing, emissive, rotated, invisible, and with unculled faces inside (slime, beacon, vault, mangrove roots). Sky light is `floorMod(3x + 5y + 7z + seed, 16)` and block light `floorMod(7x + 11y + 13z, 16)`, the cardinal lighting the default, and `BlockColors` empty: the biomes' tints come with `BiomeColors`. Each of 12 seeds, flat and smooth, gives each started layer's `[layer, vertexCount, md5]` of its vertex bytes. `LightCoordsUtil` is a static suite (its `getLightCoords` take a level, so they're checked through the meshes).
- `SectionCompiler`: `compile` over `RenderSectionRegion`s made the way `RenderRegionCache` makes them, the section and its 26 neighbours copied (`SectionCopy`, none for a section of only air, past the level's height or of a chunk the level doesn't have). "walk" compiles every section with blocks of the walk capture's chunks, the camera at the walk's eye, as `[x, sectionY, z, ambientOcclusion]`; "pattern" compiles the middle of 27 sections of `MeshLevel`'s blocks (its waterlogged states left out: fluids come with `FluidRenderer`), as `[seed, ambientOcclusion, cameraX, cameraY, cameraZ]`, the camera deciding the translucent layer's order. A region is made without its constructor, which asks a `ClientLevel` for its lighting, and answers the level's questions itself: `MeshLevel`'s light (seed 0 for the walk), the default cardinal lighting, white tints. A result is `[layers, visibility]`: each rendered layer's `[layer, vertexCount, indexCount, md5 of the vertices, md5 of the sorted indices or null]`, and the `VisibilitySet` as a long, bit `from + 6 * to` for each pair of faces it connects. The port's test puts the chunk packet goldens' chunks in a `ClientLevel` and reads them through `RenderRegionCache`.

### Environment attributes

`AttributeSuites` covers what the sky, fog and lightmap read: an `EnvironmentAttributeSystem` built the way `addDefaultLayers` builds a level's (the dimension type's constant layer and the biomes' positional ones through the system's private statics, the timelines of the dimension type's tag in its order, then the weather's where the level has weather), over the vanilla pack's dimension types, biomes and timelines decoded the way the client decodes its known pack's synchronized registries (the `NETWORK` codecs, which keep the syncable attributes). Tags aren't bound in the lookup the generator builds (`VanillaRegistries.createWorldLookup`, which the codecs resolve holders through), so the timelines tag is read from the pack's tag files in order, `#universal` first. A biome manager's source is one biome everywhere or "mixed", 14 biomes by a hash of the quart position; the clock and the weather are stubs set per case. The `ATTRIBUTES` field lists the attributes whose types the port has, in the registry's order, and a value is a boolean, a float's bits, a color's components or a moon phase's name.
- `EnvironmentAttributeSystem`: "getValue" is `[dimensionType, source, ticks, rain, thunder, x, y, z]` → `[plain, interpolated]`, each attribute's `getValue(attribute, pos, null)` and with a `SpatialAttributeInterpolator` filled the way the probe fills one, for the overworld, the nether and the end, each with its own biome and the mixed ones, at 29 times through the day and the moon's cycle (and before and long after), the overworld's with 4 kinds of weather, at 3 positions. The tick cache is invalidated before each case.
- `EnvironmentAttributeProbe`: 48 programs of `["tick", ticks, rain, thunder, x, y, z]` (the system's tick cache invalidated, then the probe ticked) and `["get", attribute, partialTicks]` on the overworld, the probe in a `ClientLevel` made without its constructor that has its attribute system and biome manager set, which is all `tick` reads. Reads skip attributes for a tick now and then, so their probes are dropped, and half the steps read the three angles, which blend between ticks the shorter way round.

### The frame

`CameraSuites` covers the camera's pure pieces, a `Camera` made with its constructor (it only keeps `Minecraft.getInstance()`, null in the generator) and `setRotation` (protected) called by reflection:
- `Camera`: "setRotation" is `[yRot, xRot]` → `[viewRotationMatrix, forwards, up, left]`, the matrix's 16 elements in column order and its properties, for the walk's rotations, right angles and their neighbours, and 400 random ones;
- `Frustum`: "cull" is `[x, y, z, yRot, xRot, fov, aspect, depthFar]` → `[cubes, boxes, offset]`: `Camera.update`'s culling frustum (the view rotation and `perspective(fov, aspect, 0.05, depthFar, true)`) prepared at the camera, its `cubeInFrustum` of the 9×5×9 sections around the camera's, `isVisible` of the same sections shifted a third of a block, and the camera after `offsetToFullyIncludeCameraCube(8)`, for 160 cameras (the walk's eye first).

The rest of the frame is checked by its screenshots: the level renderer's sections and draws, the fog, the sky and the lightmap only show in pixels.

## 2. Scenarios and tick traces

A scenario, `oracle/scenarios/<name>.json`, is the input both clients replay:

```json
{
  "world": { "seed": 0, "preset": "flat", "time": 6000, "game_mode": "survival" },
  "player": { "pos": [0.5, -60.0, 0.5], "y_rot": 0.0, "x_rot": 0.0 },
  "options": { "window": [854, 480], "fov": 70, "gui_scale": 2, "render_distance": 4, "hide_gui": false },
  "steps": [
    { "ticks": 20, "keys": ["forward"] },
    { "ticks": 1, "keys": ["forward", "jump"] },
    { "ticks": 10, "keys": [], "look": [90.0, 10.0] },
    { "screenshot": "after-walk" }
  ]
}
```

- `keys` are held for every tick of the step: `forward`, `back`, `left`, `right`, `jump`, `sneak`, `sprint`, `attack`, `use`.
- `look` sets `[y_rot, x_rot]` in degrees at the start of every tick of the step.
- `screenshot` captures the current frame as `<name>.png` without advancing the game.
- `hide_gui`, optional, is vanilla's F1 (`Hud.toggle`) for the whole run: no HUD, hand or crosshair, so the screenshots are the level alone. Both clients set it before joining (`walk-no-gui` is the walk with it).
- `setup`, optional, is a list of commands (without their slash) that build the scenario's course on the flat world, like `"fill -2 -60 8 2 -60 8 minecraft:oak_stairs[facing=south,half=bottom,shape=straight,waterlogged=false] strict"`. Physics scenarios use `fill` and `setblock` in their `strict` mode, which places each state as written, without shape updates from or to its neighbours (a fence's connections, a stair's corners), so the course is exactly what the commands say.

Before tick 0, both modes put the world in the scenario's state with the same commands, the scenario's `setup` before the player is put in place. A port joining a server must send the same ones:

```
gamerule advance_time false
gamerule advance_weather false
gamerule random_tick_speed 0
gamerule spawn_mobs false
difficulty normal
time set <time>
weather clear
gamemode <game_mode> @s
tp @e[type=!minecraft:player] 0 -1000 0
<setup…>
tp @s <x> <y> <z> <y_rot> <x_rot>
```

Then the client waits for chunks to render, plus at least 20 ticks until the player is on the ground. The player is the offline player `rustcraft`.

On a server, the client then sends a marker right before tick 0: a serverbound `minecraft:custom_payload` with the identifier `rustcraft:scenario_start` and no data (payload `18` followed by the identifier's ASCII). A vanilla server ignores it. Packet diffs use it to tell the join phase from the scenario, so a port joining a server must send it at the same point.

A run writes `<out>/<scenario>/trace.jsonl`, one line per client tick after the tick ran:

```json
{"tick":0,"pos":["…","…","…"],"delta":["…","…","…"],"y_rot":"…","x_rot":"…","on_ground":true,"horizontal_collision":false,"vertical_collision":true,"sprinting":false,"crouching":false,"pose":"STANDING"}
```

`pos` and `delta` (`getDeltaMovement`) are doubles, and the rotations are floats. Screenshots go to `<out>/<scenario>/screenshots/<name>.png`.

A scenario should move the player from tick 0: the client sends its position when it moved, or every 20 ticks without (`positionReminder`), and how many ticks the join took before the marker varies from run to run, so a scenario that starts standing still could send a reminder at a different tick each run.

A scenario also keeps clear of what the server answers by changing the player, like fall damage: landing from more than three blocks makes the server send the player's motion back (`set_entity_motion`, with `damage_event` and `set_health`), which the client applies between ticks, and the oracle client writes a tick's trace line from its own thread after the tick, once the client gets to it, so whether that line already has the server's motion depends on timing (it did in the first recording of a five-block fall, at the landing's next tick). Physics scenarios fall two blocks at most.

The server's own packets differ from run to run where a scenario's course is built: the server sends a section's block changes once a tick (`section_blocks_update`, or `block_update` for one), so how the setup's commands fall into its ticks decides how they're grouped, and a scenario that ends just after the player crosses into a new chunk may or may not catch the server's `set_chunk_cache_center` before the client leaves. Both show in `oracle-diff`'s clientbound multiset (the live `slabs-and-fences` run's did), not in what the client sends or its trace.

### Offline replays

`rustcraft::oracle::client::replay` replays a scenario on the port's `LocalPlayer` without a server: the player put at the scenario's position and settled like the oracle client settles it (20 ticks, then until it's on the ground), then each tick what `Minecraft.tick` does for it (`commonTick`, the player's `tick`, `sendChanges`, then `client_tick_end`), with each step's keys held and its look set before the tick. It gives the trace, and the serverbound packets from the marker on (the marker, then each tick's), written by the game protocol, each `name payload` like the capture's. A test per scenario compares both with vanilla's run, strictly, line by line where vanilla's `vanilla/<version>/oracle/<scenario>/` is, and by MD5s of vanilla's trace and of its packets from the marker on (without what `oracle-diff` ignores by default), committed, everywhere: oracle-diff's strict phase, offline.

The level is replayed two ways:
- the flat preset (bedrock, two dirt, grass at -61) with the blocks the scenario's `setup` places, which needs no capture and is what CI runs;
- where a capture of the scenario is (vanilla's, or the port's own in `target/oracle/<scenario>/`, which CI records for the walk), a `ClientLevel` filled from it the way the client's listener fills it: the configuration's registries, the login's level, and every chunk, forgotten chunk, block update and change of view before the marker, in order. Its blocks below y = -32 must be the flat level's, block for block, so a course is what its commands say.

Where the port's own run on a server (`tools/port_client.py capture <scenario>`) wrote its `trace.jsonl`, its trace and its packets from the marker on are checked against the same digests. CI records the walk's, so CI checks the live client's walk too.

## 3. Packet captures

`packet-proxy` sits between a client and a vanilla server in offline mode. It writes `capture.jsonl`, one line per packet after framing and decompression:

```json
{"seq":0,"connection":0,"ms":0,"direction":"serverbound","state":"handshake","id":0,"name":"minecraft:intention","payload":"…hex…"}
```

`state` follows the protocol (`handshake`, `status`, `login`, `configuration`, `play`). Names come from `vanilla/<version>/generated/reports/packets.json`. `connection` counts connections in the order they were accepted. `ms` is for humans; diffs ignore it.

`tools/vanilla_server.py` gives every run a fresh world with fixed settings:
- offline mode, no compression, no whitelist;
- flat world with the scenario's seed, no structures, peaceful;
- `respawn_radius 0`, otherwise the spawn point is random;
- no time, weather or mob cycles;
- `rustcraft` as an operator, written to `ops.json` with its offline UUID.

`oracle-diff packets` compares the two directions differently, because the vanilla server can't produce byte-identical output twice:

- **Client → server packets** (the client's behaviour) are compared in two parts, split at the scenario-start marker:
  - *From the marker on*, they must match strictly: same order, same bytes.
  - *Before it* is the join and setup. The server runs in real time while the client is stepped one tick at a time, so how many ticks pass before the world is loaded varies. Per-tick packets (`client_tick_end`, `move_player_*`, `player_input`) are dropped, and the rest are compared as a multiset with exact payloads. A missing or changed `chat_command`, `client_information` or `accept_teleportation` still shows up.
  - A marker in only one capture is a difference. With no marker in either capture, the whole stream is strict.
- **Server → client packets** are compared as a multiset. Payloads are compared regardless of order, because the server writes tags, recipes, commands and chunk heightmaps in Java `HashMap` order, which changes from run to run. `--ordered` makes the comparison strict.
- **`--join`** compares only the join phase, gate 1's definition: on a connection whose captures both have the marker, the serverbound packets before it (as above) and the clientbound packets that came before the client sent it. A connection with no marker on either side is still compared whole, and a marker on one side only still differs.
- **Ignored by default** (`--no-default-ignore` turns this off) are packets that differ in every run:
  - `keep_alive`, `ping`/`pong`, `ping_request`/`pong_response`: random ids and clocks;
  - `login_finished`: a random session id;
  - `set_time`: sent on a timer;
  - `update_advancements`: timestamps;
  - `chunk_batch_*`: pacing based on the client's clock.

The port's runs come from `tools/port_client.py capture <scenario>`, the counterpart of `oracle_client.py capture`: a fresh `vanilla_server.py` (`--compression-threshold` turns compression on), `packet-proxy` in front of it, and the port (`target/release/rustcraft --quickPlayMultiplayer … --username rustcraft --headless --oracleScenario … --oracleOut target/oracle`) joining as `rustcraft`. The port's `OracleGameTest` (`src/rustcraft/oracle/client/`) does what the oracle client's `runMultiplayer` does: waits for the level to load, sends the same setup commands, waits for the scenario's position and every chunk within the render distance to be in the level (Java then waits for the renderer's sections, which come with the render track), settles 20 ticks and until the player is on the ground, sends the marker, replays the scenario's ticks (each step's keys held and its look set before each tick) and disconnects. It writes `target/oracle/<scenario>/trace.jsonl`, `capture.jsonl` and `client.log`; screenshots come with the renderer.

`port_client.py check-join <scenario>` is gate 1 end to end: it captures the port's run and runs `oracle-diff packets --join` against vanilla's capture, exiting 0 when the join phases match. With `--compression-threshold N`, both runs have the server compress: the captures show packets inflated, so they only differ by the server's `login_compression`, and the port's run is compared with vanilla's run at the same threshold, `vanilla/<version>/oracle-compressed-<N>/<scenario>/`, which `check-join` records with `oracle_client.py capture … --compression-threshold N` when it isn't there.

The oracle client is vanilla under Fabric Loader and Fabric API (the client game test API needs it), which would send two serverbound packets an unmodded client doesn't: Fabric Loader patches `ClientBrandRetriever.getClientModName` to brand the client `fabric`, and Fabric API's networking registers the channels it receives with a `minecraft:register` custom payload once the game protocol starts. Those are Fabric's, not vanilla's, so the reference would be wrong, and the oracle mod undoes them with two mixins (`oracle/client/src/main/java/rustcraft/oracle/client/mixin/`): `getClientModName` returns `vanilla`, and Fabric's client-side network addons announce no channels (`createRegistrationPayload` returns null, which every registration they send goes through). Nothing else about the client changes: re-recorded with them, the walk scenario's trace and screenshots came out identical, and its packets differed only in those two (PROGRESS.md, 2026-10-22).

`oracle_client.py capture` starts the client first. `OracleGameTest` waits on the title screen until a file the runner creates once the server is ready, then joins, so the server has ticked about as long when the client joins as when the port joins its server, a second or two, however long the client took to start. Before, the server started first and ticked through the client's 25 s or so of startup, and timers on the server's tick count fell into a capture or not depending on that: the players' latency, a `player_info_update` every 601 ticks, came 5 s into the walk scenario in one reference capture and before the join in a re-recording.

## 4. Screenshots

The oracle client renders with OpenGL on Mesa's llvmpipe under Xvfb, so its output doesn't depend on the GPU. It turns off the vignette, view bobbing, vsync and clouds, sets particles to minimal, and uses Fabric's test defaults (no chunk fade, no music, no tutorial). The port must render with the same settings for screenshots to be comparable. `oracle-diff image` reports how many pixels differ and the largest channel difference, and can write a heatmap.

The rest of its options come from `oracle/client/options.txt`, which `oracle_client.py` copies into the client's run directory before every run. The game reads `options.txt` from there and writes it back on exit, and Fabric's test defaults keep whatever it read for every option they don't set, so a run used to depend on what earlier runs in the same checkout had left: a first run applies the default `fancy` graphics preset at startup (`Minecraft`'s constructor), which sets the anisotropic filtering among others, and a later one reads `custom` back and applies nothing. The walk reference was recorded on a later run, and a fresh checkout's first run differed from it in 14% of each screenshot's pixels, the grass towards the horizon. The pinned file is the options that reference was recorded with: the `custom` preset, `maxAnisotropyBit` 2, RGSS texture filtering and 4 mipmap levels. Fabric's own default asks for no anisotropic filtering with `maxAnisotropyBit` 0, which 26.3's range (1 to 3) refuses, logging "Illegal option value 0 for Anisotropic Filtering" and keeping 2.

The port renders the same way: `tests/opengl_frame.rs` runs `rustcraft` under `xvfb-run -a` with the oracle client's environment (`LIBGL_ALWAYS_SOFTWARE=1`, `GALLIUM_DRIVER=llvmpipe`, `SDL_VIDEO_DRIVER=x11`), and skips without `xvfb-run`. CI's runner has it, but on its Xvfb (xserver 21.1.12, Mesa 25.2) SDL finds no GLX visual for the attributes vanilla asks for (GLX itself works), so CI sets `SDL_VIDEO_FORCE_EGL=1`, which the runs inherit: SDL's EGL path on the same Xvfb and llvmpipe. This machine's Xvfb takes GLX, like vanilla. It checks:
- the device: `--device-info` prints the three lines vanilla logs about it (`Minecraft.java`'s "Using graphics backend…", "Using graphics device…" and "Using graphics device extensions…", the extensions in their `HashSet`'s order), whose flags follow from the extensions, and which equal the oracle client's log when this machine has one, with the shader goldens' flags;
- frames read back like `Screenshot.takeScreenshot`: `--screenshot` clears the main render target like `GameRenderer.render` (to `GuiRenderState.clearColorOverride`'s transparent black, or the loading overlay's brand background), and every pixel of the PNG is that color with its alpha made opaque, RGBA at the target's size like vanilla's; and a render pass clearing GL's lower left quarter shows up at the image's lower left.
- every pipeline `ShaderManager.reload` compiles (the 190 required and 2 optional ones) compiles and links on the driver from the GLSL vanilla hands it (`--compile-pipelines`);
- the block atlas: `--dump-atlas` loads it like the client and uploads it like `TextureAtlas.upload` (each sprite drawn into each mip level by `pipeline/animate_sprite_blit`, animated ones from their first frame's texture), then writes it like `dumpContents` (`<id>_<level>.png` and `<id>.txt`). Its pixels are known from the goldens: the layout and the sprites' mip levels are vanilla's, and with nearest filtering and clamped edges the pixel `k` into a sprite's padded place at level `L` is the sprite's texel `k - p_L` clamped into it, each texture coordinate on a texel's center since every size and padding is a multiple of `2^L`; llvmpipe zeroes new textures, so the rest is transparent black. All five levels match those pixels exactly;
- draws: `--fill` draws `GuiGraphicsExtractor.fill`s through `pipeline/gui` the way `GuiRenderer` does (a `BufferBuilder` mesh of `ColoredRectangleRenderState`'s vertices, the shared quad indices, the GUI's orthographic projection and model view in their uniform blocks), and the test knows every pixel: the fills' corners are whole pixels at the GUI scale, so no pixel's center lies on an edge, an opaque color blends to itself, a fill with alpha 0 is discarded, and later fills cover earlier ones.

The port's screenshots come from its runs on a server: a scenario with screenshot steps makes the port render (offscreen when it's `--headless`), and `OracleGameTest` renders a frame at a partial tick of 1 and reads it back at each step, like `OracleScreenshot.take`, after waiting, like the oracle client, for every visible section to compile (`hasRenderedAllSections`). `tools/port_client.py` runs such a scenario's port under `xvfb-run -a` with the oracle client's environment (CI adds `SDL_VIDEO_FORCE_EGL=1`). The port renders with the oracle's `options.txt` where it differs from the defaults: no chunk fade, cloud range 64, RGSS texture filtering. `rustcraft --render-scenario SCENARIO --capture CAPTURE --screenshot out.png` renders a scenario's first view offscreen without a server, from the level a capture's packets fill (`CapturedLevel`), its clocks set by the capture's `set_time`s, the player settled where the scenario puts it: the same pixels as the live run's. `tests/opengl_frame.rs` renders the GUI-free walk's spawn view that way from the walk's capture (CI's own) and checks it against the digest of vanilla's screenshot's RGBA bytes.

## Where outputs go

- Vanilla runs: `vanilla/<version>/oracle/<scenario>/`
- Port runs: `target/oracle/<scenario>/`

`oracle-diff dir A B` compares the trace, the capture and every screenshot that both directories have. Running vanilla twice and diffing the runs (`check-determinism`) checks that the oracle itself is deterministic. It has to be, or no comparison means anything.
